## Sol's current-screen findings

The screenshots supplied with the comments show an earlier prototype. Sol reopened the frozen corrected source in Chrome through Computer Use at 1137 × 786. The density and navigation concerns still apply. No demo state was reset, no story was submitted, and recovered drafts and existing receipts were preserved.

1. **The list loses useful space to permanent configuration and detail.** `work.css:1498–1505` reserves 212 pixels for the sidebar and 380 for the inspector while the issue row reserves another 386 pixels before the flexible title column and spacing. At 1137 pixels, titles become fragments, an existing-run link wraps almost word by word, and machine controls sit below the visible sidebar. This is observed interaction friction, not a backend safety defect. Move project/source choice to a compact context control, machine configuration to Settings and assignment, and source identity/coverage detail to an explicit disclosure. Keep a concise coverage/error indicator visible.
2. **Focus, inspection and selection are visually entangled.** `work.js:2886–2931` renders the inspector whenever a valid issue is focused; it consumes desktop width even with zero issues selected. Clicking a title changes the issue being inspected without selecting it, which is useful behaviour to preserve. Default to a closed inspector. Open an overlay drawer explicitly on title/Enter; close back to the same row and scroll position. A large modal is suitable for a short focused edit or confirmation, but a small modal should not contain the whole multi-story setup or long-running execution view.
3. **Planning already exists inside Work, but the navigation suggests a separate product area.** `work.js:3146–3216` exposes a per-item plan editor, while top-level links still expose a separate Plan and decisions page for the historical sample attempt. Keep the capability; attach it to the current draft or exact accepted attempt. The sample's plan cannot become a new request's plan implicitly. Custom story instructions are a separate missing field; the existing plan textarea is not proof that they exist.
4. **Runs duplicates the user's attention.** `runs.html:79–98` stacks scope, status and machine controls, a separate attention section and the list. `runs.js:453–477` renders attention independently of the filtered list. The same request appears in both, as observed for the unknown NEO-4830 receipt. A compact persistent attention count and an explicit attention filter can retain discoverability without repeating the full cards. Preserve the compact issue/status/progress/machine row the owner likes.

## Joint direction and Sol's final decisions

- **Work is the single operating list.** Default to All current work, with quick filters Not started, In progress and Needs your attention. Keep History reachable through a secondary view. Use In progress rather than Running for the broad filter because it includes reserved queued work and unresolved acknowledgement; Running remains an exact observed substate/filter. Machine, workflow and tracker filters use one compact filter control. A filter changes presentation, never assignment or execution authority.
- **Not started means no outstanding execution admission.** Drafts, positive refusals and preview blocks can appear with precise sublabels and appropriate actions. Accepted/queued work is already reserved and must say so. Running requires observed execution. Paused, queued and accepted work remain reachable in All and secondary lifecycle filters; they are not squeezed into a misleading Running state. Unknown acknowledgement and tracking loss appear in attention, retain their reservations and offer reconciliation rather than a new Start.
- **Needs your attention is a cross-cutting predicate.** An item can be running and need an answer. Do not make lifecycle and attention mutually exclusive. Show one row per canonical issue in the default list, with the current request/attempt and an expandable attempt history. Multiple valid work records must remain separately identifiable, including old attempts, source scopes and machines. A compact notice can identify outstanding attention outside the current filters; it must say which scope it counts and must not silently insert unrelated rows.
- **Select stories, then Configure run.** Open a spacious setup workspace in the same Work flow: Assign → Brief and plan → Review and Start. Preserve list context and an explicitly saved/recoverable batch draft. Assign shows machine and repository, exact implementer/provider instance/model/effort, inherited reviewers and permitted per-story overrides. Brief and plan shows source description/acceptance criteria, additional instructions and the plan for each story. Review pins all effective inputs and exposes per-item blocks. No step before Start launches implementation.
- **Inspect only on demand.** The closed list has no reserved detail column. Use an overlay drawer for a quick story peek and concise edits. An exact item/request/attempt detail can expand into a full-width workspace with Summary, Execution, Plan and decisions, and Evidence. These are local detail tabs, with durable deep links, not four top-level modes. A blocker notification opens the relevant decision directly.
- **Plan generation is an explicit operation.** If offered, it requires its own visible target/provider/permission scope before invoking an agent. A saved plan, generated plan or answered decision grants no execution permission. Planning remains accessible throughout the accepted attempt, not only in initial setup.

## Custom story instruction contract

Add optional batch guidance and separate per-story additional instructions. Show inherited batch guidance and the story's own text together before Start. Editing per-story text must not silently overwrite or erase batch guidance. Offer explicit reset/removal, and preserve empty text distinctly from missing/recovered data. Keep the tracker description and acceptance criteria read-only in this flow; editing instructions does not update the external issue.

Use the existing draft and preview contracts rather than a second prompt system. The effective brief includes the copied source revision, inherited guidance, per-story instructions, selected plan revision and applicable repository/workflow policy. Custom text cannot override enforced permissions, required capabilities or approval policy. Surface conflicting source requirements as a decision; do not assume later free text resolves them. Show what will be sent and its provenance.

Persist the optional text and its revision with the draft, bind its content digest into preview and the immutable accepted request, and use it in request replay/conflict checks. Changing text or inheritance after preview invalidates that preview. Later edits do not rewrite an accepted brief; they require the existing scoped amendment/approval path or a new linked attempt where policy requires one. No new work may bypass unknown admission or unfinished ownership by changing a prompt.

## Acceptance for the existing W6/W5/H/D work

1. At 1137 × 786 and 390 × 844, a user can identify the story, status and target without opening permanent configuration or a detail panel. Details are closed initially; a keyboard user can open, close and return to the same row. Long issue text and repair links remain usable.
2. From one Work list, select two loaded issues, keep selection across filters/pages, configure different machines and exact provider/model/effort pins, save and reload without dispatch. Hidden selected items and source coverage remain explicit. Unseen issues are never selected implicitly.
3. Add batch guidance plus different story instructions, edit/recover/discard them, inspect the complete effective briefs, and verify that the external issues are unchanged. Changed instructions invalidate preview; accepted snapshots remain unchanged.
4. Review a plan and answer a question within setup without visiting a separate top-level planning screen. Return to the same draft and list context. Saving either starts nothing and does not approve a held stage.
5. Start a mixed batch with accepted, refused and acknowledgement-unknown results. Each item appears in the same Work list with its exact target and receipt. Accepted queued items cannot be resubmitted as Not started. Unknown work survives reload and retains same-request reconciliation.
6. Running and Needs your attention can both match one item. Paused, failed, queued, stopped, completed, tracking-lost and unknown records remain discoverable. History retains exact attempts, immutable machine identity and stale/last-observed evidence. Filters neither duplicate rows nor hide a global attention count without explanation.
7. Opening a row or notification reaches the exact item/receipt/attempt and its Summary, Execution, Plan and decisions, or Evidence tab. A linked new attempt does not relabel the previous attempt's execution. Machine/provider changes require fresh approval and cannot silently redirect actions.
8. Unsupported or unauthenticated machine/provider/repository choices remain blocked with a repair route that returns to the draft. Machine management is in Connections; the actual machine and repository stay visible in assignment, preview and accepted detail.

These are technical acceptance requirements for future authorised changes. Static source and fixture screenshots cannot satisfy real OpenCode/DeepSeek execution, cross-server admission, fault recovery or installed core-app acceptance.

## Independent findings adjudicated by Sol

The following P2 gaps are confirmed from the current source. They are prototype correctness and interaction gaps, not evidence that production admission was exercised:

- **F1, split action ownership:** Runs reads the receipt and offers a link to secondary Work detail (`runs.js:912–914`); withdrawal/reconciliation remain in Work. Linking the data did not finish UX-05's single operating/detail journey. UX-03's immutable machine display is retained, but action integration is incomplete.
- **F2, competing status projections:** `work.js:3787–3850` and `shared.js:655–673` independently map the same receipt. Preview-blocked becomes `refused`, withdrawal requested becomes `paused`, and accepted receipts become `queued` while the Accepted filter matches only `accepted`. Some grouping choices are legitimate individually, but the surfaces do not expose one consistent semantic contract.
- **F3, unknown labels overstate execution knowledge:** `shared.js:663`, `work.js:3813` and `work.js:4100–4107` pair unknown acknowledgement/closure with “not running” or “not started”. The static demo really launches nothing, so this is not a claim that an actual agent was stopped. The simulated lifecycle should nevertheless say “execution not observed; may be running on target”, with the general demo notice separately stating that the artifact launches nothing.
- **F4, finished and never-submitted records pollute Active:** every receipt item has `history:false` (`runs.js:190–211`). Closed/refused records and blocked batch items remain in the Active scope. Preserve their evidence in history or the draft without presenting them as outstanding execution. This contributes directly to the density concern.
- **F5, incomplete attention projection:** Work's `needsYou` includes blocking gates and withdrawal requests (`work.js:3894–3925`), while Runs' request attention is created only for unknown state (`runs.js:139–151`). A blocking gate can disappear from the operating attention filter. UX-07 remains partially corrected.
- **F6, incomplete preview contract:** `work.js:1698,1873–1907` records a workflow name, but no workflow digest or permission snapshot; preview renders permissions from global fixture configuration (`work.js:3704–3709`). There is no demonstrated user-editable workflow race in this static artifact, so this is an unimplemented acceptance requirement rather than a proven live bypass. Future production preview cannot inherit that omission.

Lower-priority source-confirmed follow-ups are retained with the same existing work: F8 assigns effort to the row's model field and profile ID to provider (`runs.js:134–135`); F9 hard-codes the original scope in the “other scope” badge (`work.js:2405`); F10 overwrites a receipt error with empty-results text (`runs.js:534–537`). F7's 32-bit request-key collision/replay concern is a prototype limitation: production needs payload conflict checking under a durable request identity, not a copied fixture hash.

Two reviewer findings need qualification. **F11:** unknown admission must reconcile before ordinary withdrawal; absence of an immediate withdrawal button is not permission to assume nothing was accepted. An idempotent request-key cancellation path may be designed only where the authority supports it. **F12:** the earlier shortened-badge visual gap is now superseded by Sol's fresh [Runs capture](../../research/evidence/recon-2026-10-21/symphony-flow-review-2026-10-22/03-runs-1137.png), which shows the shortened receipt and machine chips without their previous overlap at the reviewed viewport. Overall density remains a separate problem.

### Decisions where the proposals differed

Opus recommended Not started / In progress / Finished segments and a persistent unfiltered attention strip. Sol retains the safer In progress wording, but uses one attention filter/count rather than another duplicated card list. An explicitly labelled notice points to attention outside current filters. History is secondary. Counts must state scope and coverage. A canonical issue row may group attempts, but unresolved older ownership or multiple outstanding requests must be surfaced as a conflict, never hidden by choosing the latest attempt.

Both recommend an on-demand drawer and a spacious setup workspace over a small modal. The drawer must not keep stealing focus while the user edits a prompt; list navigation can follow selection only when editing is not active. Use confirmations for consequential state transitions, not nested modal editors. Reopening/reloading setup recovers text without granting execution.

For prompts, prefer additive, visibly labelled batch guidance and per-story instructions. Do not silently replace inherited guidance when a story is edited. Reject conflicting instructions through the existing enforceable policy/approval boundaries; do not add speculative keyword warnings or claim a text scanner makes credentials or permissions safe. Tracker content is untrusted input, but its description and acceptance criteria still define the selected work's requirements. Keep that distinction from system authority. A separate reviewer-instruction subsystem is not needed for this requested slice.
