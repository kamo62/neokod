## Two flows, with separate ownership

### Normal Code thread orchestration

The current conversation's agent is the parent. The user asks it to investigate or implement using child agents, potentially through other providers. The parent discovers supported targets and invokes scoped app-owned tools; child work has isolated ownership and durable results returned to the same conversation. No Symphony project, tracker issue, separate orchestration mode or Delegate button is needed.

The accepted design remains plan 16.4/16.6, W6-C1–C6. Current source has no `contracts/src/delegation.ts`, `shared/src/delegation`, server `managedChild` service or delegation toolkit. The one `child_start` string in GitVcsDriverCore is a Git trace event, not a delegation tool. Provider-native subagents and a visual tree do not implement app-managed children. This feature remains unimplemented and unproven. The parent's existing model selector already determines its provider/model; another mandatory orchestrator selector would duplicate it.

### Autonomous Symphony

Symphony's configured workflow pulls eligible tracker work, resolves its pinned assignment, plans, implements, validates, reviews and delivers under policy. The user configures that policy once and may additionally select explicit issues for a bounded manual batch. Routine automatic items must not require a human wizard, a manually written plan or approval at every stage. The previous prototype's unavailable Automatic choice is a fixture limitation, not the intended permanent product behaviour.

Work is the quiet overview of autonomous work. The run's summary and current blocker are the first useful details. Symphony contacts the human when it needs an answer, a real permission/merge approval, or operator intervention. An inline request and reply should feel familiar from the current thread. Plan, execution map, agent lineage and evidence support inspection without becoming required navigation. Do not create a new general chat engine or a permanent free-form run composer as part of this redesign.

The server already has a Symphony Orchestrator service, but its existing runtime is a Codex worker path. Do not present a multi-agent LLM coordinator as shipped merely by labelling a panel Orchestrator. Show who actually asked, who owns the run/attempt and where the answer is routed. Symphony's request routing and ordinary-thread parent/child delegation remain separate capabilities.

## Feedback: what can be reused and what is missing

Ordinary threads use `ComposerPendingUserInputPanel.tsx`, `pendingUserInput.ts:105–120` and `ChatView.tsx:4775–4799,4883–4894`. They retain per-question IDs, options/multiple choice and custom answers, then submit an answer map against the pending request in the owning environment/thread. Reuse this interaction and the existing combined model control rather than designing a second question or model picker.

Symphony currently exposes `SymphonyRespondToUserInputInput` as `{requestId,text}` (`packages/contracts/src/symphony.ts:1220–1223`). `SymphonyApprovalActions.tsx` offers a text reply separately from approval/rejection. `ApprovalService.ts:182–198` looks up a pending durable record and routes the answer by run-attempt/request identity. `LiveRequests.ts:249–263` resolves the existing waiting Deferred. This is real source support for answering an existing question and unblocking that agent; it is not proof of a general message-to-run API, live provider parity or complete durable recovery.

**Confirmed feedback gap (S2, adjudicated P1):** `AgentRuntime.ts:119–133` maps the same single `text` to every question ID. A request asking for a branch and a validation choice cannot receive independently structured answers. The UI cannot fix that by rendering more fields alone. Preserve the question schema through the durable record, client contract, response validation and provider adapter. Reuse applicable existing question contracts; keep provider-specific response formatting in the adapter.

### Continuation rules

| Situation                                                                          | Human interaction                                                          | What happens afterwards                                                                                     |
| ---------------------------------------------------------------------------------- | -------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------- |
| Current live question; assignment, permissions and scope unchanged                 | Answer inline, using options or a custom answer                            | Resolve that exact request and continue the already authorised run; no routine extra Resume click           |
| Several questions in one request                                                   | Answer each question by ID; submit the complete validated map              | Deliver distinct answers once to the owning live request                                                    |
| Permission, command or merge approval                                              | Separate Approve/Reject card with exact action and scope                   | Continue only within the actual approved permission; prose answers are not authority                        |
| Explicitly paused run or a separate unresolved approval                            | Answer may be saved/delivered where supported                              | Preserve the independent hold; offer Resume only when it is genuinely required                              |
| Changed issue, plan, target, provider or permissions invalidates authority         | Review the scoped change and obtain the required fresh approval            | Do not use an ordinary answer to authorise broader execution                                                |
| Lost reply acknowledgement                                                         | Show sending/acknowledgement unknown, preserve text and identity           | Reconcile the same response; do not claim saved, failed or safe to resubmit elsewhere without evidence      |
| Expired/stale request, replaced attempt or restarted process with no live receiver | Keep the user's text and explain that the request is stale/unavailable     | Reconcile and obtain a current request; never inject the old answer into the latest run                     |
| No pending question                                                                | No misleading always-enabled question composer                             | Offer only separately supported operator actions; unsolicited guidance needs its own real delivery contract |
| Child agent asks in a normal Code thread                                           | Attributed question through the parent, pinned to the actual child/request | W6-C4 routes the answer to that child; human approvals remain human-owned and stale-safe                    |

These rules correct any reading of the earlier blanket “saving a decision never continues work”. A local planning note does not execute anything. Answering an existing live blocking request is intentionally a continuation of already authorised work. Scope/permission changes and explicit pause remain independently controlled.

### UI decisions

- **One Work home.** Combine Runs into its operating list. Keep the compact rows the owner liked, quick filters Not started / In progress / Needs your attention / All, and secondary History. Attention is cross-cutting. One shared semantic projection drives labels, counts and actions; preserve unknown, tracking loss and unresolved older attempts.
- **Compact context, on-demand detail.** Replace the permanent project/machine rail with a compact source and workflow-policy control. Keep coverage/freshness/errors visible; move detailed machine repair to Connections. Open story detail on request in a drawer; a roomy focused modal/setup is suitable for a bounded manual launch. Do not squeeze the entire process into a small popup.
- **Automatic delivery remains central.** Explicitly activate/edit/pause the workflow’s tracker scope, targets, eligible providers, concurrency and approval policy once. Routine automatically pulled items skip the selected-batch wizard. Selected-only setup remains optional for explicit issues. Policy detail can expand without adding another dense permanent toolbar.
- **Instructions and plans stay contextual.** Add batch guidance and per-story instructions in workflow/manual setup, separately from the tracker text and plan document. Show additive inheritance and provenance; recover drafts, version the effective brief and invalidate a changed unaccepted preview. Do not rewrite an accepted brief. Automatic agent planning does not imply mandatory human plan authoring or approval unless configured.
- **Feedback appears when needed.** Show the asking agent’s current question in exact run context, using the existing thread interaction. A supported reply continues the same authorised work. A permission approval or explicit hold remains separate. No permanent general run composer is added without a real messaging command.
- **Execution, Plan and Evidence become local detail views.** A contextual Activity view shows lifecycle and actual requests, not an invented free-form agent conversation. Keep a simple observed stage view now. Retain the richer graph/tree design for real stage/lineage contracts; label planned and observed distinctly. Repeated D-3 forms, duplicate rails, cross-page tabs, the second receipt detail and the save-then-resume ritual are removed or combined. Provider-native observation never becomes managed-child ownership by relabelling a card.

Opus’s D1–D7 identify these design contradictions; the full inventory specifies every retained/moved/combined/deferred family. F1–F6 and F8–F10 from the prior flow report remain open. F7 remains a production-admission limitation of the prototype. F11 remains reconciliation-before-withdrawal authority, not permission to cancel an unknown run. F12 remains resolved by the prior rendered shortened badge. This pass changes the interpretation of live replies and automatic intake, not those evidence boundaries.

## Implementation readiness and acceptance

The product direction is specific enough to start scoped implementation. It is not ready for a feature-complete or release claim. Reuse the existing W6/W5/H/D work and preserve the core-first gates; do not add another scheduler, chat engine or parallel task tracker.

1. **Core and existing corrections first.** Finish the source-confirmed F1–F6 state/action/attention/preview gaps and the existing core acceptance gate. One authoritative lifecycle/attention projection serves all surfaces. Do not mark the full core review complete from the selected Symphony source paths or historical unit-test counts.
2. **Symphony feedback slice, independent of thread delegation.** Fix S1–S5: stop synthetic timeout answers, preserve answer/note history honestly, and preserve structured questions and per-question answers end to end; present the request inline in exact run context using the thread question interaction. Answering continues a live request under the same authority. Tests cover distinct answers to two questions, custom/multiple choice, reload/legacy records, timeout/answer/cancel races, note persistence, duplicate reply, stale/expired request, lost acknowledgement and explicit pause/approval holds. An observed live Codex question/answer continuation is required before shipping that path. Unsupported provider or restart recovery stays unavailable with a reason.
3. **Calmer Symphony UI.** One Work list, compact source/policy control, explicit automatic-workflow activation/pause, manual selected-batch option and details on demand. Run summary/blocker is primary; plan is edited in workflow/manual setup or inspected during execution; map and evidence are contextual. A routine eligible automatic item proceeds without a human setup step. Only actual questions/approval/intervention require attention. Fresh source coverage, exact machine/repository/provider pins, policy and receipt ownership remain visible where decisions are made.
4. **Normal Code orchestration stays W6-C1–C3.** After its existing core dependencies, implement scoped tool admission, isolated child launch/stop, durable results and wake delivery. A normal prompt requests a child on a different supported provider; the child result returns once after the active parent turn. Stop/restart/unknown cases and permission ceilings must pass, followed by one observed live OpenCode run. No tree-only completion claim. Enriched parent question controls remain W6-C4, tree W6-C5 and provider expansion W6-C6.
5. **Provider and machine enablement follow real contracts.** DeepSeek V4.1 Flash New via OpenCode2 ACP remains the requested implementer for coding lanes. That does not enable it inside Symphony or as a managed child automatically. Unsupported runtime routes remain disabled until the adapter, permissions, durable admission and focused fault/live checks establish support. Multi-server scope authority remains W5/W6, with no silent target fallback or release of unknown work.

The next execution decision is therefore bounded: the Symphony feedback corrections and a calmer artifact/UI have a concrete technical brief. UI work that requires structured questions waits for its contract/persistence correction. W6-C1–C3 is still **no-go under the existing formal core exit gate**, not ready merely because Phase 1 code was merged. The core S6 correction and previously recorded core verification remain part of that gate. Multi-provider Symphony and cross-machine child routing are not a first-layout milestone.

Appropriate checks belong to each authorised implementation slice, including the repository's `vp check` and `vp run typecheck`. This review does not run compiler builds or start implementation. A readiness recommendation is not evidence that either orchestrator has been built.
