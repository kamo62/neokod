## P1: resolve before treating the flow as ready

### UX-01: two stale tabs can accept the same issue and overwrite receipts

Confirmed prototype bug. `work.js:560–594` checks and allocates receipts from tab-local memory, then overwrites the whole stored list; `:2281` loads it once. Two isolated copies of the actual functions both accepted NEO-4830 as R-1. A second case accepted different issues and retained only the second receipt. See the [reproduction result](../../research/evidence/recon-2026-10-21/symphony-ux-review-2026-10-22/cross-tab-result.txt). This was an in-memory VM check, not a live two-browser test.

Correction: serialise the prototype's entire read/check/allocate/write operation, use non-colliding receipt IDs and synchronise other tabs. Disable admission where safe serialisation is unavailable. Re-reading storage or listening for changes alone is not atomic. Production must use the canonical server-owned admission authority already specified in plan 16.11; client locks cannot provide cross-machine execution safety.

Acceptance: racing stale clients for the same issue yields one admission; racing different issues preserves both receipts. Repeat across reload. Production requires independent-client/server fault tests against the scope authority.

### UX-02: lost acknowledgement and target refusal have no distinct recovery UI

Source/design gap. `work.js:314,557–613,1532–1541` models accepted/blocked outcomes; the interface cannot demonstrate acknowledgement unknown, target refusal and preview blocking as distinct states. A user cannot tell whether retrying could duplicate work.

Correction: represent preview-blocked, refused with a typed reason, accepted and acknowledgement-unknown separately. Unknown keeps the same request key, target and reservation, offers Check status and blocks a fresh admission elsewhere.

Acceptance: simulate lost acknowledgement, reload and reconcile the same request. It remains unknown until authoritative evidence resolves it. Accepted work is not relaunched; positive refusal permits a new request. Offline or elapsed time never implies refusal or closure.

### UX-03: machine identity disappears from monitoring and approval

Observed UI plus source. Work pins a machine, but A rows/details, B/C headers and C's approval scope omit it (`runs.js:267–310,377–387`; `planning.js:277–291`). With multiple machines, Resume or Request stop does not make its destination clear.

Correction: carry immutable machine identity and label through rows, filters, details, receipts, evidence and actions. Approval includes machine, item, attempt, plan, head and decision scope. Changing a label must not change identity.

Acceptance: two similarly named runs on different machines remain distinguishable. Every approval, retry, resume and stop addresses the displayed machine and attempt. Reconnect cannot redirect an action to another server.

## P2: complete the interaction design

### UX-04: assignment uses a weaker selector than the thread view

Observed UI plus source. Work has a flat implementer select, read-only effort and fixed reviewer text (`work.js:1143–1228`). It does not expose exact provider instance, supported effort or an accessible reviewer-default editing route.

Correction: reuse the production [ComposerModelTraitsControl](../../../apps/web/src/components/chat/ComposerModelTraitsControl.tsx), including model search, provider-instance identity, traits/effort and disabled reasons. Populate it from the selected machine. Preserve DeepSeek V4.1 Flash via OpenCode ACP as the intended implementer, with Sol/Opus reviewer defaults. Show inherited reviewers and where to change them. A static prototype should depict the same control shape; that is not proof of production component wiring.

Acceptance: change machine, choose an exact provider instance/model/effort and inspect its preview pin. Missing instances stay unavailable with reasons, with no inferred replacement. Reviewer defaults and permitted overrides are visible before Start.

### UX-05: starting work does not lead into the rich A/B/C view

Observed UI. Work's local request tabs and A's Runs are separate lists. R-1 does not appear in A; the artifact explicitly admits this (`work.js:1757–1785`). Rich B/C content stays on separate pages, and saved local decisions there are not retained across page reloads.

Correction: demonstrate one shared item/attempt selection and state through Work → A → B/C. Keep the receipt as admission evidence within the run. Existing sample attempt 3 must remain clearly distinct from a new Work request; never relabel its historical activity as the new request's execution.

Acceptance: start a demo item, open it in A, visit each detail tab, return and reload without losing selection or saved state. Planned and observed nodes remain distinct. No duplicate top-level Runs concepts are required.

### UX-06: an accepted queued request has no recovery actions

Observed UI plus source. The accepted request header has tabs but no withdraw, stop or linked reassignment path (`work.js:1729–1753`). Copy requires closure before moving, but Reset demo is the only demonstrated escape from the issue lock.

Correction: show lifecycle-appropriate actions, including requesting withdrawal while queued. A request to withdraw is not closure. Unlock and offer a linked new attempt elsewhere only after positive closure/refusal or proven fencing. Unknown work stays reserved.

Acceptance: demonstrate withdrawal requested, acknowledgement unknown and closure confirmed separately. Reassignment is blocked until the last state and preserves the previous target, request and evidence.

### UX-07: questions have no visible blocking policy or stage hold

Observed UI/design gap. NEO-4830 previews as Ready with an open question, but neither preview nor its planned graph identifies a stage held for an answer (`work.js:486–494,1404,1440–1443`). Intake admission before Build approval can be legitimate; the gap is the missing gate semantics.

Correction: classify blocking/advisory questions and name the held stage. Preview should say, for example, Admits to Intake; Build held until answered. Keep saving a decision separate from granting execution approval.

Acceptance: a blocking question appears in Needs you and the held stage. Saving its answer does not silently approve execution. Advisory questions do not create invented gates. Changed plan/head/target invalidates the relevant approval.

### UX-08: source and repository selection cannot be exercised

Observed fixture limitation/design gap. Tracker/project/scope are fixed, with 7 of 9 issues loaded and no next-page action (`work-data.js:27–36`). The user cannot demonstrate another scope, repository path, loading failure or freshness change.

Correction: expose supported connection/project/scope and target repository selection. Show exact identity, coverage, fetch time, partial/error states and explicit load more. Only expose filters supported by the adapter. Refresh must invalidate stale previews where their approved inputs changed.

Acceptance: select across pages without selecting unseen matches; distinguish two scopes with similar keys. Demonstrate empty, partial, unavailable and changed-source states. Moving to a machine without the repository blocks that row with a repair route.

### UX-09: conflict and configuration messages lead to dead ends

Observed UI. NEO-4838 reports accepted work on Work PC but offers no Open existing run. The machine panel tells users to repair Settings without a route (`work-data.js:243–248`; `work.js:1270–1320`). NEO-4821 already links to attempt 3 and is not this finding.

Correction: link existing work by canonical machine/item/attempt, prevent selecting it as new work, and provide a scoped Connections repair route. Return to the draft after repair and require a fresh preview.

Acceptance: the conflicting issue opens exactly the existing run. Repairing a provider/connection returns with the selection preserved and no automatic launch.

### UX-10: narrow Work hides the identities needed for safe selection

Observed at 390 × 844. Issue IDs and machine columns disappear, the machine strip sits off-screen, and navigation/step controls clip. See [capture 17](../../research/evidence/recon-2026-10-21/symphony-ux-review-2026-10-22/17-work-narrow.png); `work.css:1584–1587,1630–1645` hides identity columns.

Correction: stack identity and machine chips within rows, provide reachable navigation/overflow controls and make workflow steps fit or scroll intentionally. This is responsive browser coverage, not a request to restore a separate mobile app.

Acceptance: at 390 × 844, identify each issue and target before selecting or acting. Reach Work, Runs, detail tabs, Preview and recovery actions without clipped controls. Check keyboard focus separately.

### UX-11: leaving an unsaved plan or draft lacks a clear outcome

Source gap. The prototype persists explicit saves, but navigation/reload can discard unsaved edits with no leave decision (`work.js:1040–1075,2309–2320`). Cross-page local decision persistence is also incomplete under UX-05.

Correction: show dirty state and choose a consistent save/discard/stay interaction or durable local draft recovery. Saving remains separate from execution authorisation and from the immutable accepted plan snapshot.

Acceptance: edit then navigate/reload. The user can recover the edit or explicitly discard it. Later edits do not rewrite an accepted request's pinned evidence.

### UX-12: the suggested machine fix hides a preference override

Observed UI plus source. NEO-4846 prefers Work PC, but its blocked state recommends Sample Mac without foregrounding that preference (`work.js:495–500`; `work-data.js:297–300`). This is a preference, not proof the Mac is incapable of valid path tests.

Correction: show the preference while blocked, offer compatible implementers on the preferred host, and label an alternative as an explicit preference override. Model required capabilities separately from preferences.

Acceptance: a preference can be deliberately overridden with clear wording. A genuinely required missing capability blocks admission and cannot be bypassed through a recommended fix.

## Decisions and refinements

Settled: one Work intake, A operating view, B/C detail; shared thread model/effort control; exact machine/provider pins; accepted is not started; saved decision is not execution approval; unknown is not stopped; no automatic fallback. These reinforce plan 16.11 rather than introduce another scheduler or product mode.

Plan inheritance is an open product decision: suggest offering Use latest canonical plan or Start fresh with author/revision/provenance, and preview the selected revision. The artifact already explains why its new plan r1 differs from original attempt 3/r5; that is not silent data loss. A new plan never inherits execution approval automatically.

Lower-priority refinements: use consistent sample timestamps, clarify who opens the PR versus who merges it, add Change in Work to blocked receipt rows, and verify the semantics of pressed controls/map nodes with assistive technology. Accessibility snapshots alone do not prove a screen-reader defect. C's narrow approval rail moves below content; it is not lost.

Keep the strengths: explicit selected-only scope and hidden-selection counts; blocked rows retained in mixed batches; honest queued/planned states; plan save separated from approval; accepted snapshot separated from later edits; current-host, unverified agent and stale evidence shown separately.
