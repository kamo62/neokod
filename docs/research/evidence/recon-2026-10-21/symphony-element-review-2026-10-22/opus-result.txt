# Symphony and thread orchestration: read-only adversarial review, 22 October 2026

## Decision

1. **Code threads and Symphony stay separate.** Agent-launched children in an ordinary Code thread belong to W6. They do not exist in source yet. Symphony is a policy-driven autonomous runner that should contact the person only when it needs something.
2. **The prototype's main interaction is wrong for Symphony.** It answers a live worker question, then makes the person press a separate Resume and an execution approval. It also disables Automatic intake, which is the central workflow. Fix both before any application UI follows the prototype.
3. **Symphony's current answer contract cannot support inline answers.** It sends one plain-text answer to every question in a request. On timeout it sends an empty answer and the agent carries on. It also discards the answer text and any rejection reason. Three small backend slices must land before an inline question card can ship.
4. **Go/no-go:**
   - Revising the static prototype: go, once you authorise it.
   - Application UI: go only for the parts the existing contracts support.
   - Backend answer-contract slices: ready to start.
   - W6-C1 to C3: still blocked by the plan's formal core exit gate.
   - Shipping: no, for everything here.
   - Compiler builds: not authorised.

This review was interrupted once so I could take in your two-flow correction. The source trace done before the interruption is kept and re-read under the corrected model. Nothing was edited, built, run or dispatched.

## Two separate flows

### Flow 1: managed children in an ordinary Code thread (W6, not Symphony)

- **Intended:** you ask the current agent to "use two agents". The agent calls scoped MCP tools. Neokod creates durable child threads, which may use another provider. Each child's result is pinned and queued back to the same conversation as an attributed turn. There is no Delegate button and no mode switch (plan 16.4 and 16.6).
- **Current source: not implemented.**
  - `McpInvocationContext.ts:10` defines only the `"preview"` capability, and `McpSessionRegistry.ts:117` grants only preview.
  - There is no `contracts/src/delegation.ts`, no `shared/src/delegation/`, no `managedChild/` and no delegation toolkit.
  - The question in 16.4/16.6 is still open.
- **Not managed children:**
  - `SubagentsPanel` shows provider-native subagents that Neokod observes but does not manage.
  - `symphony.delegateFromThread` turns a thread into a Symphony work item. That is a handoff, not a child.
- **Answering:** the existing thread question and approval UI applies unchanged. A child's question reaches the parent only after W6-C4 (`child_answer`). Approvals are only ever answered by a person, on the child thread.

### Flow 2: Symphony autonomous delivery

- **Intended:** under the configured policy, Symphony pulls eligible tracker work automatically or as an explicitly bounded "Selected only" launch. It then plans, implements, validates, reviews and delivers, and contacts the person only for a blocker, a question or an approval.
- **Current source:**
  - The "orchestrator" is a server scheduler (`SymphonyOrchestratorLive`), not an AI model.
  - Each work item gets one Codex app-server worker (`AgentRuntime.ts:31-40`).
  - There are no Symphony-managed children, no reviewer-role sub-agents and no DeepSeek/OpenCode route.
  - Run events cover lifecycle only. The appends I sampled were `issue_claimed`, `agent_started`, `continuation_turn` and validation and review events. I found no question, answer or agent-message events, but that search was not exhaustive.
  - The prototype's tree of a root agent plus managed C1 to C3 is a D-series design target. It is not a shipped capability.

## Question and answer paths compared

| Concern | Ordinary thread | Symphony |
|---|---|---|
| Structured options | Rendered as buttons with descriptions, multi-select and keys 1 to 9 (`ComposerPendingUserInputPanel.tsx:119-147,172-223`) | Flattened into prompt text as "(options: a, b)" (`AgentRuntime.ts:349-377`). The person has to retype a label. |
| Multiple questions | One question at a time, answers keyed by question ID (`pendingUserInput.ts:105-120`, `ChatView.tsx:4883-4900`) | One text applied to every question ID (`AgentRuntime.ts:119-132`) |
| Free text | The composer becomes the custom answer for the active question (`ChatView.tsx:4109-4112,4849-4881`) | Textarea only (`SymphonyApprovalActions.tsx:139-158`) |
| Contract | `thread.user-input.respond` with an `answers` record (`orchestration.ts:153,783-790`) | `{ requestId, text }` only (`symphony.ts:1220-1223`) |
| Acknowledgement | A per-request "responding" state, cleared by the server's `user-input.resolved` activity (`session-logic.ts:554`) | RPC success then a refresh. The durable row is set to `approved` (`ApprovalService.ts:195`) and the answer text is not stored. |
| Stale or restart | Removed from view when the provider's error text matches (`session-logic.ts:402-416`); fragile | A row that is not pending returns `approval_request_not_found`, shown as "no longer pending" (`ws.ts:425-426`, `SymphonyApprovalActions.tsx:15,84`). Live requests are in memory; settlement fails them on every exit path (`LiveRequests.ts:275-307`). |
| Same-scope continuation | The provider continues the same turn | The answer resolves the request and Codex continues the same turn (`AgentRuntime.ts:502-508`). No Resume is needed in the runtime. |
| Who asked | The thread's provider session | The work item's Codex worker. No orchestrator agent, no children. |
| Feedback with no question pending | The composer sends a new turn; a queued-send path exists (`ChatView.tsx:4082-4097`) | Not supported while a run is going. `requestChanges` is post-review only. `takeOver` cancels the run and hands the workspace to a Code thread (`HandoffService.ts:38-45`). |
| Cancellation | Interrupt is hidden in the run banner while a question is pending (`ChatView.tsx:5639`). The composer's stop path was not traced. | cancelRun, stopAllRuns and takeOver settle pending requests (`LiveRequests.ts:275-307`) |
| Timeout | No app-side timeout in the traced web path | After 30 minutes by default (`Config.ts:48`), the agent receives an empty answer and continues (`AgentRuntime.ts:431-444,502-505`) |

Your questions answered:

- **Is the plain-text reply contract sufficient?** Only for a single free-text question.
- **Does it apply one answer to several questions?** Yes.
- **Do answering a pending question and sending a message need separate paths?** Yes. Answering a pending question resolves a live request. Sending unsolicited feedback is a different command, and Symphony does not have one mid-run today.

## Continuation and approval rules

| Situation | Rule |
|---|---|
| Live question in the same scope, no hold | Answering resolves the request and the worker continues. No Resume and no execution approval. |
| Approval request (command, file change, privilege, tracker write, merge) | A separate card with Approve and Reject. It is never answered by free text. A parent agent can never approve. Only offer a note field if the note is actually delivered or stored. |
| Stale, expired or interrupted request | Refuse with a typed reason. Keep the person's typed text locally. Show it in history. No automatic retry. |
| Answer that changes the plan, scope, permissions, target or machine | This is not an answer. It goes through the amendment path or a new linked attempt with a fresh preview (16.11). |
| Human pause or policy stage hold | Resume is its own command, scoped to the exact attempt and machine. This is the only case where Resume appears. |
| Cancel or take over | Pending requests settle as interrupted. The answer box closes. |
| Feedback with no question pending | Only through a supported command: Request changes at review, Cancel, or Take over in Code mode. Never through the pending-answer endpoint. |
| Question timeout | Proposed: hold the run and keep it in Needs your attention. Never send an empty answer. |
| W6 child question | `child_answer` from the parent (C4), or a person opens the child. Child approvals are answered only by a person on the child thread. |

## Recommended interaction design

1. **Work is the single Symphony home.**
   - A project policy strip at the top shows: Automatic or Selected-only, eligibility rules, concurrency, approval and merge policy, and an Edit link.
   - Automatic items flow in without a wizard. "Configure run" appears only when you select stories for a bounded launch.
   - Quick filters: Not started, In progress, Needs your attention, All. History is secondary. Every count states its scope and coverage.
   - Rows keep their machine and repository pins. Unknown and tracking-lost stay visible and are never shown as idle.
2. **Opening an item gives one detail view with local tabs:** Activity (the default when something needs you), Execution, Plan, Evidence.
3. **Activity is a contextual run log, not a chat.** It shows:
   - lifecycle events;
   - question cards inline, with structured options, several questions handled one at a time, and free text, reusing the `pendingUserInput.ts` logic;
   - approval cards kept separate from questions;
   - stale and expired history.

   There is no permanent free-form composer. "Request changes", "Cancel" and "Take over in Code mode" appear only where their commands exist.
4. **Execution** shows planned stages and observed progress. The detailed graph and the agent tree are deferred until the D-series contracts exist.
5. **Plan** is a single editor with revisions, and it binds into preview and the accepted snapshot.
6. **Machines** live in Settings > Connections.
7. **Code-thread W6** stays in ChatView: a Managed children section next to `SubagentsPanel`, with attributed wake turns, and nothing in Symphony.
