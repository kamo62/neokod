# Chopin review for Neokod (read-only, 21 October 2026)

## Decision

Chopin should not be ported. Neokod should take three narrow ideas from it:

1. Pin the exact revision of whatever triggered the work.
2. Treat replays of lifecycle reports with the same key and payload as harmless, and reject the same key with a different payload as a conflict.
3. Show progress only from real events.

All three fit existing slots: W6-C1 to C3, D-1/D-4, and W6-C5/D-5. None needs a new core card. The core-first order in plan 16.4 to 16.8 stays as it is. Phase 1D and 1E finish first, and nothing here starts before the core exit gate.

Chopin's own source contradicts its approval story. Its docs say "a person reviews and approves that exact graph". In the code, one Build press drafts the task graph and then starts it without a separate review. Its living-document mode lets a classifier start rebuilds. Rebuild reports from the coding agent become "approved" graph versions. Neokod must not copy any of that.

## Gaps in Neokod that this review exposed

1. **Plan provenance.**
   - `SourceProposedPlanReference` carries only `{threadId, planId}` (`packages/contracts/src/orchestration.ts:270-273`). Plan text can change under the same id.
   - `implementedAt` is set when the implementation turn starts (`ProviderRuntimeIngestion.ts:1650-1656`), not when it completes. It means "implementation started".
   - The web app uses it correctly, only for "actionable" (`session-logic.ts:667-671`). It must never be shown as "implemented".
2. **Symphony attempt provenance.**
   - `RunAttemptSchema` (`contracts/src/symphony.ts:276-292`) has no base commit and no workflow-content digest.
   - `WORKFLOW.md` reloads on file modification time only (`symphony/Workflow/Loader.ts:176-180`).

## Recommendation

**Now:** no implementation. Finish Phase 1D and 1E. If the owner authorises it, record this review as a report addendum plus a short note in plan 16.

**Next:** three slices, in order, each inside an existing slot. All start after the core gate.

1. **W6-C1/C2: provenance in the delegation contract.**
   - `DelegationReceipt` stores the parent thread and turn, the base SHA, the policy snapshot and the environment.
   - It may also store an optional `sourcePlan` with `{threadId, planId, observedUpdatedAt, sha256}`.
   - If the plan digest has changed, `child_start` is refused with `source_stale`.
   - Same key and payload returns the receipt. Same key with a different payload returns `request_conflict`.
   - Selecting a plan or accepting a request never moves a task past `accepted` without evidence. `stopped` requires engine evidence.
   - Table-driven tests cover: stale plan, conflict, restart during launch giving `launch_unknown`, and unconfirmed stop giving `orphaned`.
2. **D-1/D-4: attempt provenance and the stage view (image 1).**
   - At dispatch, the attempt records its base SHA and a SHA-256 of the `WORKFLOW.md` front matter and body.
   - Validation and review carry the head SHA and a clean-tree flag.
   - If the workflow changed after dispatch, the attempt shows "workflow changed since dispatch". Its evidence is neither silently reused nor marked green.
   - A missing base shows as unknown.
   - Stage nodes show their revisions and are not counted as agents.
3. **W6-C5/D-5 plus 16.7 images 2 and 3: agent tree and review feedback.**
   - Phase labels come only from events: no auto-advance and no percentages. Tool detail is collapsed and keyboard-accessible.
   - Terminal elapsed time freezes. Orphaned rows say "last observed". A stale running row reads unknown, not interrupted.
   - Repair rows show "round n/2" with the head SHA and mark superseded results.
   - Cost shows as not reported.
   - Agent counts exclude stages.
   - Check with Computer Use at 220, 280 and 360 pixel widths, in light and dark themes.

**Later (W5/M-series):**

- Every accepted job pins the target machine.
- A job moves to a new connection only if it is the same machine and the same token principal.
- Unattended work needs a stored opt-in per machine, off by default.
- Chopin keeps that consent only in memory; Neokod should store it.

## What not to take, and why

- **One press that approves a graph nobody has seen yet, and agent reports that become approved versions.** Both are inferred approval.
- **Classifier-driven rebuilds and decisions** (`LIVE_BUILD`, `CONVERSATION_PLAN`). They let plan edits flow into execution without a person deciding.
- **Recording `failed` on stop, disconnect or restart before closure is confirmed.** It erases evidence of an orphaned process.
- **Agent-reported PR state and verification counted as delivery.** Neokod's host-derived evidence is already stronger.
- **Tool-kind-wide "always allow" and the `--allow-all` default.** They break Neokod's inherited permission ceilings.
- **GitHub App, hosted Planner, pairing, PostgreSQL multi-user tenancy, Yjs or MDX editor, Chopin UI.** They conflict with local-first, single-owner Neokod and with the policy against porting other apps' UI.
- **Executable or unrestricted MDX.** Even Chopin's own MDX is render-only.
