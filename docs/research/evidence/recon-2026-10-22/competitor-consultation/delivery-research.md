# Delivery mechanisms refresh, 22 October 2026

This is fresh source research for Neokod's ordinary-chat delegation and separate autonomous Symphony path. Keep Neokod's two entry points. Adapt Paseo's explicit destination and shared tool route, Omnigent's recoverable results and durable occurrence claims, Orca's fenced mailbox and effective-launch receipt, and bb's child-result presentation. None of these source samples proves a competitor's live tracker-to-PR delivery, nor Neokod runtime support.

## Proposed Neokod combination, not a competitor feature claim

Keep entry points separate. Code uses human-owned threads and app-managed child threads initiated from ordinary chat. Symphony remains a daemon that claims eligible tracker stories and continues to validation/evidence/PR under workflow policy, contacting a human only for a real decision, missing capability, exhausted recovery or policy-required approval. Sharing execution admission, exact pins, receipts and recovery does not require sharing planners, queues or product screens.

1. At acceptance, the server records an immutable dispatch envelope: operation identity; Code parent thread or Symphony work-item/attempt; exact machine identity plus accepted connection identity revision; canonical repository identity and workspace lease; provider/model/effort and capability revision; privilege ceiling; permitted delivery actions; instruction snapshot/hash. A label or recently active host is never an execution identity. Missing or changed pins hold dispatch; they do not choose another host.
2. Let users select provider, model and effort in the same thread-shaped picker used for chats. Add an adjacent machine and workspace pin with capability/status evidence. Symphony can have workflow defaults, story-specific instructions and a per-story override, but all accepted values become an attempt snapshot. Show requested versus effective values when different or unverifiable. Do not claim the model from its selector alone.
3. Persist the composed brief used for the attempt: repository rules and workflow instructions, exact tracker story content/revision, custom story instructions, acceptance criteria, validation commands and bounded delegation policy. Preserve provenance of each source. Tracker prose can shape the work but cannot grant a new machine, tool permission or delivery action. Edits made after acceptance apply to a later attempt or require an explicit policy-defined re-acceptance.
4. Put outbound dispatch and child-result wakeup in a durable outbox, identified by parent + child + attempt + result revision. Use a claim/fence for startup and receiver-side receipts. After acknowledgement loss, inspect that operation on the pinned target before a retry. Retain unknown outcome when evidence cannot establish delivery. Distinguish accepted, provider-started, result-available, result-consumed, validation-passed and delivered-PR; do not collapse them into completed.
5. Derive calm Work views from the same server projection: needs-you first, running, ready-for-review and recent completed items, with one concise expandable story/run/thread row. No Kanban is required. Machine/provider/model pins and the latest meaningful evidence stay readable. Batch routine child results per parent from the outbox; wake the parent once per new cohort. Notify the human only for a new actionable state or meaningful completion, never each poll, heartbeat or ordinary child message.
6. Carry structured delivery receipts across the planes: validated commit, checks and exact scope; intended source-control operation; external PR ID/URL after acknowledgement; unresolved or unknown mutation status after a crash. Symphony can finish its own policy-led run. Code remains under the initiating person's instruction and should not acquire extra tracker/merge authority by creating a child.

## Failure acceptance required before claiming this works

| Injected failure / scenario                                                                                                         | Required observable result                                                                                                                                                                                                                                  |
| ----------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Destination machine is offline, identity changes, or same path exists on two machines                                               | The exact accepted machine remains pinned; dispatch waits/fails clearly; no fallback, local cwd inference or ambiguous source selection.                                                                                                                    |
| Requested model/effort unavailable, changed during a fork, or a host lacks override capability                                      | Fail/hold or show a policy-approved substitution with requested/effective receipt. Never label requested settings as observed runtime settings.                                                                                                             |
| Crash before claim, after claim, before send, after receiver accepts but before reply, and after result queueing but before consume | At most one accepted receiver operation per ID; durable unknown/starting state survives; recovery inspects target; one parent-consumed result. Do not claim exactly-once provider work unless the provider contract establishes it.                         |
| Old runner reconnects after replacement                                                                                             | Runtime fence rejects its writes and wakes; it cannot close or overwrite the current attempt.                                                                                                                                                               |
| Parent goes idle, /clear occurs, route drops or app restarts before child completion                                                | Qualified lineage and results remain durable; follow current valid lineage; closed/orphaned/unverifiable remain distinct.                                                                                                                                   |
| New story instructions or workflow settings arrive during a run                                                                     | Accepted brief remains reproducible; subsequent work uses an explicit new revision/attempt; privileges do not silently expand.                                                                                                                              |
| Agent finishes while a tool/workflow/remote child may still run                                                                     | Host projection says surviving/orphaned/unknown work; no false all-done or stopped label.                                                                                                                                                                   |
| Tracker fetch, build tool, source-control permission or PR acknowledgement is unavailable                                           | Preserve unavailable/unknown evidence, action needed only where recovery/policy requires it. No fabricated pass, zero unresolved reviews or invented PR URL.                                                                                                |
| A healthy eligible story runs with configured autonomy                                                                              | Daemon claims, isolates, executes, validates, builds evidence and opens the authorised PR without step-by-step human prompting; no human notification for ordinary progress. Prove this with a real bounded tracker-to-PR fixture before production claims. |
| Many workers complete at once, parent wakes repeatedly, or long run loses telemetry                                                 | Durable cohort deduplication; bounded excerpts with result links; one semantic state and no repeated notification storm. Age alone cannot author termination.                                                                                               |

No implementation or runtime acceptance was attempted here. The failure table is a proposed Neokod validation contract. Existing local canonical implementation and verification status must be taken from the main task's fresh repository review, not this research note.
