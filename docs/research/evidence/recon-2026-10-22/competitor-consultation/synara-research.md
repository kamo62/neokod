## What Synara actually implements

### Coordinator and cross-provider work

The shipped-source Hub is an explicitly configured project/container with one designated coordinator conversation and a persistent work queue. Its playbook asks that coordinator to answer small questions, queue follow-ups to existing threads, and create one worker per independent task. It explicitly tells the coordinator not to write application code itself. This is a real coordination product, but a different entry/role model from Neokod's current normal agent delegating from any Code conversation. Do not transplant the special coordinator restriction, Hub setup or shared-library requirement into W6. [Playbook lines 10–30](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/projectAgent/projectBotPlaybook.ts#L10), [Hub guide](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/docs/hubs.md#L78).

The server resolves original human messages and attachments from the coordinator thread, separately from the agent's brief. It checks source references against that frozen request, fingerprints the exact plan, derives task IDs from source scope and task index, and inserts durable queued work before dispatch. The source-of-authority distinction is useful: relayed agent text and generated memory are context, not fresh human authorisation. Repository work defaults to worktrees; explicit worktrees on a non-Git folder are refused before cards/source binding are persisted. [Gateway lines 213–283](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/agentGateway/hubWorkGateway.ts#L213), [service lines 196–298](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/projectAgent/hubWorkService.ts#L196).

Cross-provider permissions are resolved against the selected target. #1861 makes unsupported inherited Auto fall back to approval-required while leaving explicit requests subject to validation. The explicit privilege ceiling remains checked. Adapt the discovered-capability check and effective-mode recording; retain Neokod's settled rejection of unsupported requested combinations, rather than silently changing requested modes. [Creation lines 608–635](https://github.com/Emanuele-web04/synara/blob/39a745feaccf942f43aae154373fe375a20a0e4d/apps/server/src/agentGateway/creationCoordinator.ts#L608), [PR1861](https://github.com/Emanuele-web04/synara/pull/1861).

### Native observation is separate

Native Claude/Codex children are materialised from provider events with the root parent plus actual source child, prompt-derived titles and invocation-scoped outcomes. #1741 repairs reused native tool IDs so an old stopped/failed outcome is not attached to a new invocation. The materialisation cap is 20 per parent/turn; excess children keep running while their work is not shown, with a notice. That is a display bound, not admission control or a concurrency cap. Keep observed native work visibly distinct from app-managed durable children, and report incomplete visibility. [Ingestion lines 2348–2495](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/orchestration/Layers/ProviderRuntimeIngestion.ts#L2348), [PR1741](https://github.com/Emanuele-web04/synara/pull/1741).

### Questions, approvals and stops

#1704 reuses the existing worker approval component above the coordinator composer. It subscribes only to workers whose shell says approval is pending, routes the response by worker thread/request/lifecycle generation, and clears the same request in both views. There is no agent-callable approval tool. This is an excellent intent to adapt to Neokod's own components. It is approval parity; this component does not establish a complete parent-view structured multi-question answer flow. Preserve the Neokod 16.15 feedback fixes instead of claiming Synara solves them. [Component lines 1–143](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/web/src/components/chat/group/HubPendingApprovals.tsx#L1), [PR1704](https://github.com/Emanuele-web04/synara/pull/1704).

Queue cancellation and stopping active execution remain separate. `synara_hub_cancel_work` only cancels queued/idle tasks and explicitly requires interrupting an active worker first. Lifecycle logic retains held slots while a cancelled task's thread still has live work or a pending request. Adopt evidence-led capacity release; do not show Cancelled as evidence the provider terminated. [Gateway lines 358–380](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/agentGateway/hubWorkGateway.ts#L358), [lifecycle lines 44–89](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/projectAgent/hubWorkLifecycle.ts#L44).

### Completion and recovery

#1975 is the most valuable recent correctness change. A non-Git research/writing worker could finish but never emit a Git checkpoint, so it never released capacity or woke its coordinator. The repair requires a persisted completed turn that started without Git, no active/pending/newer turn, a ready session and a positive accessible non-Git check against live or saved runtime cwd. It uses an exact-turn stable inbox identity, claims settlement transactionally, recovers report/evidence delivery, and only wakes through a contiguous ready inbox prefix. Git workers keep the checkpoint barrier. Adopt the semantic distinction: provider completion, artifact availability, validation and parent delivery are separate evidence, and a task must not wait for an inapplicable Git artifact. [Completion predicate lines 506–579](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/projectAgent/Layers/ProjectAgentService.ts#L506), [claim/delivery lines 5760–5960](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/projectAgent/Layers/ProjectAgentService.ts#L5760), [PR1975](https://github.com/Emanuele-web04/synara/pull/1975).

Do not copy its entire recovery ladder. The Hub guide and service use silence thresholds, then nudge, interrupt and re-send the original task, bounded by attempts and protected from user-owned turns/running tools. Neokod should first establish exact provider ownership and stale/unknown evidence; general automatic retry from inactivity is outside W6-C1–C3. Also reject treating the non-Git output scanner as exact ownership: its own comment says overlapping shared-root turns may both claim the same file. Files can be real without exclusive attribution. [Recovery lines 896–1418](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/projectAgent/Layers/ProjectAgentService.ts#L896), [output reactor lines 1–24](https://github.com/Emanuele-web04/synara/blob/299fd573b1d6520c323a87c78d30be74e87e53e1/apps/server/src/orchestration/Layers/HubOutputReactor.ts#L1).

#1971 closes a scoped-MCP failure relevant to W6: a terminal turn can tombstone its write bearer before a runtime event carrying the persisted rotation marker is dropped. Writes then fail during a valid new turn while reads work. Synara consults the adapter's authoritative retired state as well as the durable hint, rotates credentials, and exposes a diagnostic; it never reauthorises the retired bearer for a new turn. Adopt this threat/failure fixture when adding child tools, without widening Neokod's existing credentials. [PR1971 with source patches](https://github.com/Emanuele-web04/synara/pull/1971/files).

#1797 ensures OpenCode stop cleanup despite cancellation and refuses adoption of retained stopped contexts. #1866 protects exact active provider turn ownership and keyset-pages reconciliation so healthy first-page work cannot starve later abandoned work. Both are useful source patterns for stop/restart evidence; neither is a reason to import a replacement engine. [PR1797](https://github.com/Emanuele-web04/synara/pull/1797), [PR1866](https://github.com/Emanuele-web04/synara/pull/1866).

### Issue intake and review routing

The inspected GitHub Send to agent / Fix findings / Resolve conflicts flow prepares a destination branch/worktree and opens a fresh draft with an issue/PR context card. Its implementation explicitly sends nothing to a provider. Do not call this automatic issue assignment or tracker-to-PR delivery. Its useful idea is retaining the exact issue/PR context and target checkout while preparing a manual handoff. Neokod Symphony automatic pull/dispatch remains its own workflow-led path; per-item composer review is optional manual intake only. ## Three practical Neokod proposals

These are proposed refinements, not implemented capabilities or extra Phase 1 cards. They should attach to the existing W6/D/S2 work only after its dependencies and authorisation.

1. **Preserve the authorising request beside the delegated brief.** At `child_start`, freeze bounded source message IDs and immutable original text/attachment references, the parent's server-resolved active turn, the agent's task brief and policy snapshot separately. Hash the exact admitted payload for replay conflicts. Display a single compact “Asked by parent” disclosure in the child. For Symphony use the selected tracker revision plus workflow version as original authority, without inventing a parent chat. This addresses constraint loss and provenance confusion without adding another coordinator product. Acceptance: changed/deleted original attachment fails explicitly; a retry cannot quietly widen the brief; generated text cannot become new authorisation.
2. **A small delivery receipt that outlives the view.** Pin one immutable result for each child attempt, then record parent queue acceptance and eventual delivery separately. The collapsed card can say “Finished · result queued” until the parent's next turn owns it. A non-code task can deliver text/artifacts without a Git checkpoint; code completion keeps its configured validation/HEAD evidence. When the parent has several children, update one request summary, with failures/waits visible individually. No active turn steering. Acceptance: crash between result pin and parent queue receipt produces one delivery; no code-validation green claim from an assistant's completion; stale attempts cannot replace a newer result.
3. **One human attention card per live request, wherever the owner is watching.** Reuse the corrected existing structured question and approval components with server-owned request/attempt identity. Expose the same request in the parent's Code view or Symphony run inspector, with actual asking agent/provider/target and distinct action types. Only pending owners get detailed subscriptions. Keep global UI quiet while a compact count opens the queue; stable ordering prevents rows jumping under a click. Answering a live question continues the authorised attempt automatically, subject to independent holds. Timeout preserves a hold; it never fabricates an empty answer. Acceptance: answer from either surface clears both, stale generations refuse, and a hidden child's request remains discoverable. This combines Synara's targeted parent approval subscription with Neokod's 16.15 structured-answer correction rather than creating a second chat engine.
