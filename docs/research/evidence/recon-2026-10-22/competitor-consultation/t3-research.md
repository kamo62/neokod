# T3 Code fresh implementation review, 22 October 2026

Retain Neokod's chosen ordinary-conversation entry and engine. T3 supplies useful working source mechanisms for provider-neutral managed children, durable identities and results, but its current default of shared checkouts, provider-ranked permissions and optional active-turn steering should not become Neokod defaults. Code orchestration remains separate from Symphony's autonomous tracker workflow.

## Mechanisms inspected in current source

1. **Entry and model selection: adopt intent.** Normal conversation agents receive `orchestrator_capabilities`, `delegate_task`, status/cancel and explicit product instructions. App-owned children are distinguished from new top-level chats. A fresh review round has a new task/request ID; retries reuse that round's ID. Native same-provider subagents are preferred only when they can honour model and options. See [shared instructions](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/packages/provider-core/src/server/orchestrationInstructions.ts#L8-L39). Neokod should keep its app-owned path authoritative for managed work; native cards alone prove no managed admission. Tools use the same live model catalog as the composer. Current [bounded catalog projection](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/mcp/OrchestratorMcpService.ts#L2084-L2143) preserves selected/custom/favourite models and exposes search/omissions. Catalog discovery does not prove provider execution.

2. **Provider wiring: adapt per protocol.** [Session manager](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/ProviderSessionManager.ts#L435-L497) grants scoped orchestration/worktree/PR capabilities and reuses a still-valid credential. [OpenCode2](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/packages/provider-opencode/src/server/v2/adapter.ts#L3120-L3155) adds the authenticated remote MCP entry, conditionally emits orchestration instructions and writes them via a session instruction entry. [Codex application context](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/provider/CodexDeveloperInstructions.ts#L201-L227) splits numbered entries to survive mode-prompt replacement/entry caps. [ACP wrapper](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/packages/provider-core/src/server/orchestrationInstructions.ts#L72-L104) adds app instructions only when mode/tool availability changes, preserving slash-command position; its documented CLI bridge is a transport fallback, not evidence that all ACP agents expose MCP natively. Neokod must record live tool visibility, round trip and mode behaviour per provider, including OpenCode2, before claiming parity.

3. **Admission/authentication: adopt and tighten.** [MCP access](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/mcp/McpToolAccess.ts#L88-L115) rejects read-only mutation clients and checks a live caller. [Delegation](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/mcp/OrchestratorMcpService.ts#L2145-L2259) requires a parent active run/root node owned by that credential's provider; derives retry-stable command ID; resolves enabled provider/model/options; dispatches the managed request. [Orchestrator](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/Orchestrator.ts#L6957-L7054) derives child/task/message/item IDs and persists child linkage. Preserve Neokod's required payload-hash conflict check, depth/concurrency caps and recorded launch intent. No claim is made that T3 has Neokod's exact caps or policy guarantees. [Numeric mode ceiling](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/mcp/OrchestratorMcpService.ts#L670-L720) permits unknown provider mode support and can choose a narrower inherited supported mode. Neokod should require affirmative mode support and report requested/effective/provider-verified evidence separately.

4. **Workspace/machine scope: adapt, reject shared-write default.** [Target contract](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/packages/contracts/src/orchestratorMcp.ts#L96-L122) selects provider instance/model/options; it does not select a remote machine. [Delegation contract](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/packages/contracts/src/orchestratorMcp.ts#L164-L199) defaults isolation to shared. [Worktree resolver](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/mcp/OrchestratorMcpService.ts#L2183-L2214) resolves the parent checkout's local HEAD, verifies the project contains that commit and binds a new worktree strategy before launch; it does not copy dirty parent edits. Adopt bound workspace-before-start, retain Neokod's isolated-worktree default. Do not infer cross-machine child support from T3's saved connections or remote UI. Neokod's parent target/environment remains pinned; cross-machine children remain excluded in C1–C3.

5. **Questions/approvals: adopt identity and restrictions; parent approval UI still needs Neokod work.** [Result contract](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/packages/contracts/src/orchestratorMcp.ts#L200-L248) returns pending-question and oldest live approval identity and ends a blocking wait early. Questions can be read/answered using child thread plus request ID; the contract explicitly grants no approval authority. [Fresh lookup](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/mcp/toolkits/thread/handlers.ts#L51-L79) distinguishes already answered from missing/stale. [Active-thread UI hook](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/web/src/components/chat/usePendingThreadRequests.ts#L107-L126) is scoped to the active thread; this pass did not establish a T3 parent-view inline approval workflow. Do not cite T3 as proof of Synara-style parent approvals. Preserve structured question/answer maps and provider restrictions. Neokod's parent agent may answer permitted questions, while only the human can approve, with attempt/session generation fencing and fresh callback capability checks.

6. **Results/wake: adopt durability, reject active-parent steering.** [Task result finalisation](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/Orchestrator.ts#L10712-L10790) deduplicates by child run source point and writes a result context transfer. [Completion mailbox](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/Orchestrator.ts#L10380-L10580) reserves generations, coalesces queued siblings and persists claimed/pending/delivered/disposed state under parent locking. But [dispatch](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/Orchestrator.ts#L5106-L5142) actively steers a running parent if the provider reports steering without tool interruption. Neokod explicitly queues behind the active turn; stopped/interrupted/failed parents retain a waiting result for deliberate delivery. Keep original task/result identity independent of later child turns. Do not transplant T3's broader continuation semantics.

7. **Failure/throughput: adapt new fixes.** [Abandoned-turn recovery](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/ProviderTurnStartService.ts#L574-L640) interrupts the prior failed run's running native turn before continuation. [Ingestion failure](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/RunExecutionService.ts#L1457-L1503) attempts interruption even when event consumption cannot continue. [Claude parent-death watcher](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts#L317-L353) blocks on a server-owned pipe and terminates its POSIX group on EOF; it does not solve Windows cleanup. [Main-only shell filtering](https://github.com/pingdotgg/t3code/blob/22840ab943b8418744b48223411e46ba4fdcef1a/apps/server/src/orchestration-v2/ShellStream.ts#L109-L133) keeps child run/request facts globally visible while focused subscriptions carry child transcript updates. This reduces fan-out before replay/live buffering. Its PR's reported 39-thread incident is author evidence, not a Neokod benchmark or a measurement repeated here.

## Useful Neokod designs beyond copying one competitor

- **Separate result and attention mailboxes.** Queue coalesced immutable result references behind the parent turn. Route live question/approval attention immediately to the parent UI, with child, environment, run attempt and request identities. A permitted parent-agent question reply and a human approval travel through separate handlers. Resolving attention resumes the existing child wait; it does not start a duplicate parent/child turn. Limit: no inline approval until lifecycle fencing and live response capability exist; no synthetic timeout answer.
- **One launch receipt that proves the target.** Return requested/effective provider/model/options, pinned environment/worktree/base SHA, policy version, dirty-input exclusion and evidence level (`accepted`, observed running, provider enforcement verified/unknown). Use the same receipt in agent tool output and parent child panel. Pair this with the compact searchable catalog. Limit: it describes Neokod observations, not a promise of identical provider permissions; unavailable OpenCode external MCP or unsupported modes stay unavailable.
- **Demand-driven child visibility with durable outcomes.** Subscribe all clients to child status/attention and parent result references; subscribe only viewers to full child transcripts. Bound and replay each lane separately so a many-child stream cannot starve approvals. Preserve a restart-reconcilable mailbox before notification. Limit: source inspiration only; Neokod needs overflow/reconnect fixtures and a measured live run before claiming throughput improvement.

For Symphony, reuse these contracts and attention/evidence concepts where they fit the existing runner. Once a workflow is explicitly configured and activated, eligible tracker work is pulled, validated and delivered automatically; human contact is reserved for actionable missing input, policy decisions, failure or completion requiring action. No conversational coordinator or mandatory per-item wizard is introduced. T3's thread tools/scheduler are not proof of Neokod Symphony integration.
