- Keep T3's entry from the active ordinary conversation: app-scoped MCP capabilities, deterministic durable child identities, explicit task targets and pinned results. Keep Neokod's engine, worktree-by-default, depth-one cap and queue-behind-parent policy. T3's live steering and shared-write default are deliberate rejects.
- Adapt Synara's original human-request/agent-brief separation, exact-attempt completion, persistent results and parent-view approval intent. Do not require a Hub/coordinator-only chat. Its GitHub send-to-agent is draft preparation, not automatic tracker delivery. Remote prerelease does not establish passive cross-machine child return; managed Cloudflare/WorkOS fails our owner-direct policy.
- Adapt Paseo's host-qualified routing/parent lineage and Orca's admission versus observed execution/receipt distinctions. Keep W5 cross-machine work later; a connected machine or available model is not accepted work. Never fall back to a different machine/repository/home directory.
- Adapt Omnigent's recoverable results and claim-before-start ideas, but its new scheduling implementation is not wired into current main startup. Reject elapsed-age-as-proof-of-failure. Do not build another scheduling engine.
- Adapt bb's compact result cohorts and exact project-machine selection. Its notification batching is process-local, so cannot supply Neokod crash durability. Latest tag SHAs matter more than stale published_at.
- Adapt PandaCode's inherited team guidance, exact existing model catalog, immutable ongoing assignments and bounded check/repair concept. Drop mandatory Team mode and unlimited fan-out; file scopes are advisory, not a sandbox. Its repair budget is a process-local Set; our server-owned attempt budget must survive restart. Keep automatic checks policy-controlled and obey the owner's no-build instruction.
- Adapt Chopin's distinction between live waiter answers and durable saved decisions, question IDs, generation checks and coalesced idle-planner answer turns. Do not adopt arbitrary saved prose as execution permission or transplant its planning product. A current live blocking reply is immediate; do not impose a five-second batch delay or a second Resume click.
- Harp supports compact stable rows and contextual attention. Superset's newest queue heading reduction shows control surfaces can appear only when useful. Do not copy their UI or global tab/sidebar styling.
- GOAT's current agent-surface doc explicitly labels its registry/meta-evaluator/handoff design a proposal. Do not call it implemented or add a 100-tool grammar/DSL to this scope. Closed Conductor/Maestri give documented UX ideas, not code or durability proof; no hosted relay/canvas port.

## Five proposed Neokod combinations

These are our proposed combinations, not world-first inventions or completed app features.

1. **Delegate in the conversation; return by receipt.** Human: “Use DeepSeek to implement this in an isolated worktree and Opus to review.” Current parent calls supported scoped tools; one collapsible children summary shows actual target/status. The exact child result is pinned and queued behind the current parent turn. “Finished · result queued” differs from “delivered to parent”. Failed/stopped parents retain undelivered outcomes for deliberate handling. Provider-native cards remain observational. No Team/Delegate mode or coordinator-only parent restriction.
2. **A quiet autonomous Work home.** Explicit workflow activation sets tracker scope/eligibility, target/repository, provider/roles actually supported, review/repair/merge policy. Symphony pulls items and performs ordinary steps without a wizard. Compact rows and Not started/In progress/Needs your attention/All plus secondary History. Expand Activity, Execution, Plan, Evidence locally. Custom workflow guidance and per-story overrides are separate from tracker text and an agent plan; pin effective guidance at admission. Manual selected-issue setup remains optional. Unknown older attempts stay discoverable, not hidden under the latest issue result. Detailed graph waits for observed contracts, not for a new layout framework.
3. **Answer where you already are.** One existing question/approval interaction rendered in parent Code or exact Symphony detail. Every request retains actual asker, target, run/attempt and question IDs. Human can answer from either view; only the exact live request resolves. A question is not a permission grant. Scope changes and explicit pause retain independent holds; normal same-scope reply continues immediately. No always-on run chat composer. Result mailboxes and attention delivery stay logically separate but reuse existing stores/notifications/components; no new generic inbox engine unless an actual missing boundary requires it.
4. **One who-and-where summary, with an honest effective brief.** Reuse the thread provider-instance/model/effort control, next to an exact machine/repository pin. Show inherited values and intentional per-story/child overrides. First C1-C3 is local-only; remote choice appears later when W5 can enforce it. Capabilities are target-scoped and searchable. Freeze original source identity separately from the agent's derived brief, including exact plan/workflow revision and allowed delivery scope. Unavailable is not substituted. Active accepted assignments never change because defaults were edited.
5. **Bounded repair, evidence-led review.** A configured failed check may queue one authorised repair and then escalate rather than loop. Persist the attempt budget and preserve user Stop. Existing workflow can choose a different finite budget; do not hard-code Panda's policy as universal. Review is a fresh round with explicit brief, result/diff/check pins and prior objections; it does not automatically reopen a completed child. Summarise what changed since the approved plan/head/target/policy. Human approval is required for material authority changes, not routine replies. Checks are repo-configured and cannot silently launch compiler builds contrary to instruction.

## Integration and delivery boundaries

Reuse W6-C1-C6, W5/H/D and plan16.15; no new roadmap IDs or universal scheduler. The shared reuse is contracts/pure projections, effective settings and existing question/model components, not a claim that Code engine and Symphony runner share a real admission boundary today. Authority remains enforced at each existing plane's dispatch path.

Immediate order: correct core/feedback S1-S6 and lifecycle/attention F1-F6 at existing gates, then minimum calm Work UI against honest current Codex Symphony runtime; independently finish formal core acceptance. Then W6-C1-C3 for local isolated children, C4 structured child feedback, C5 contextual tree, C6 providers. W5 owner-direct remote and richer Symphony reviewer/role graph wait for their contracts and live proof. Do not indefinitely serialise all design UI behind unrelated future provider work; disable unsupported routes honestly. This is research/readiness advice, not authorisation to build or ship.

Acceptance before claiming: two distinct answers survive reload; timeout fabricates no reply; note text isn't discarded; current answer continues without duplicate Resume; old request cannot reach replacement attempt; same key/payload replays one admission and changed payload conflicts; accepted versus running versus result available/delivered remain distinct; crash after result pin and before delivery produces one consumed result; Stop/restart doesn't free uncertain children; non-code result doesn't depend on Git checkpoint; requested/effective/observed model distinctions visible; offline target never falls back; mutable instructions don't change accepted work; many completions don't flood parent; live OpenCode W6 result and separately live tracker-to-PR Symphony fixture required. No source inspection is runtime proof.

## Questions for midpoint consultation

- Should first W6 keep the settled depth-one 3/6 bounded cap and no hidden admission queue, or change it now? My choice: retain first-slice bounds; defer persistent backlog semantics until needed.
- Are separate attention/result mailboxes a semantic distinction only or a new subsystem? My choice: existing request tables/components plus W6 result outbox; avoid generic inbox work.
- Preserve ordinary live question immediate response, with coalescing only for non-waited decisions/results? My choice: yes; borrowed planner batching must not delay a live tool callback.
- Is “one repair” a default or universal rule? My choice: policy-controlled finite attempt budget, normal Code opt-in; do not overtake current user instruction or force every repo to run a build.
- Which gates can proceed in parallel? My choice: bounded Symphony contract/source corrections and honest lightweight UI; W6 still waits for formal core gate, remote/graph later. No freeze of all UX on future cross-machine work.
