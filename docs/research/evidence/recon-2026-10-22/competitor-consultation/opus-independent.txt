# Independent Opus assessment: thread delegation and Symphony (22 October 2026)

My recommendation is to keep the roadmap's W6 design for ordinary-thread children. It needs four changes, all backed by T3's newest merged code. For Symphony, the W4 Kanban plan should become one Work list with filters, and new runner providers should go through the same launch path as children. Everything below was read-only. I did not run any competitor, build anything, or read Sol's new files or plan sections 16.9 to 16.15.

## B. Adopt, adapt or drop

### Ordinary thread delegation

| Mechanism | Source | Strength | Limitation | Verdict |
|---|---|---|---|---|
| Agent-called `delegate_task`, `task_status` and `task_cancel` with `clientRequestId` idempotency and a live model catalogue | T3 `tools.ts` | No button or mode needed; replays are safe | There is no machine target in `OrchestratorMcpTarget`. I found no fan-out or depth cap in `OrchestratorMcpService.ts` (searched for depth and limit constants), and nesting is allowed (`waiting_for_children`) | Adopt the shape. Keep Neokod's depth 1 and caps |
| Authority bound to a live run: a provider token acts only while its thread owns a live run (`assertLiveCaller`) | T3 `threadAccess.ts` | Authority ends with the run, so an expired credential cannot act | It is tied to T3's thread model | Adopt. Replace Neokod's 30-minute idle / 8-hour credential expiry (gap 3) with run-bound validity |
| Mode ceiling re-checked under the target's lock; escalation is refused | T3 `McpToolAccess.ts` `writesThreads` | Closes the race where the user changes modes during a call | T3's own text says the rank does not prove the provider's permissions are narrower | Adopt. This matches 16.4's "rank is not a guarantee" |
| A child is settled only when its leftover background work settles, via a re-check listener | T3 #22709 | Fixes children that stay "running" forever, and parents that never wake | Depends on a provider exposing a background roster | Adopt. This changes W6-C3 (section D) |
| Results delivered by a queued message with a 16 KB inline budget; larger results stay intact behind a status pointer | T3 #22117 | Avoids context-budget failures on long parents | T3 also steers into active turns | Adopt the budget plus a pointer. Keep queue-only delivery |
| Question wake: server tells the parent about a child's pending question, with a deterministic command ID, and cancels the queued wake once the question is answered | T3 `DelegatedTaskQuestionReactor.ts` | Idempotent, and the parent never answers a stale question | The text instructs the agent; it grants no approval | Adopt into W6-C4 |
| Child approvals shown in the parent, human-only, answered in either place | Synara #1704, `hubs.md` | Fewer clicks, and agents get no approval tool | I saw no lifecycle-generation fencing in the PR | Adopt with Neokod's fencing, as 16.4 already says |
| Inherit the parent's provider, model and effort only when the provider matches | bb #6120 | Predictable defaults | None significant | Adopt (it is the W6 permission rule) |
| Automatic machine placement onto whichever host has a checkout | bb #6054 | Convenient | Violates "machines explicit" | Drop |
| Child address of (serverId, agentId); one-hop routing; existing RPCs | Paseo #7370, #7507 | A clean address model for owner machines later | The PR's non-goals list durable notifications and host-aware permissions | Adapt for later. Neokod keeps the durable record on the parent's server |
| Owner-side child reservation with caps from a frozen root policy, bound to the parent's verified pid and birth | Hermes #141944 | Server-owned admission; no worker self-spawn | Kanban-specific | Adopt the frozen-policy idea (already in the W6 policy snapshot) |
| Short model list for agents | T3 #22889 (title only) | Keeps capability discovery cheap | None | Adopt in `child_capabilities` |

## C. Proposed designs

**C1. Delegation that settles honestly, in an ordinary thread**
- Normal journey: the human types "have a reviewer on Opus check this and a tester write cases". The parent calls `child_capabilities`, then `child_start` twice. Each child appears as one attributed row in the parent transcript ("Review · Opus 5.5 · working"), which expands on request. Each child's result is pinned. When both have settled, the parent receives one queued roll-up turn after its current turn ends.
- Unknown and error states:
  - `cap_reached` returns the active count and tells the agent to end its turn.
  - An unsupported provider returns the reason.
  - A turn that has ended while background work continues shows "waiting for background work". A provider with no background roster shows "background work unknown", which is never shown as complete.
  - A launch that fails after the turn may have started stays `launch_unknown`.
  - A stop that is never confirmed shows "may still be running".
- Value: T3's tool shape and background-settle fix, combined with Neokod's queue-only delivery and evidence-typed states.
- Not to implement: steering into active turns, nested children, a Delegate button, or cost figures before usage data exists.

**C2. Answer in place, without a third page**
- Normal journey: a child or Symphony run asks a question. A card appears inline in the parent thread, or under the "Needs you" filter of the Work list. Answers given in either place clear both. Several answers saved close together become one resume turn (the Chopin rule). Approvals are answered only by the human, through a fenced action carrying a lifecycle generation.
- Unknown and error states: a stale generation is refused with "this request has ended". A question answered first by the human cancels the queued parent wake, as T3's reactor does. An answer arriving after a restart is delivered from storage. The human's own turns are never nudged or interrupted.
- Not to implement: a separate inbox page, agent-callable approval, or treating text such as "approved" as permission.

**C3. One calm Symphony Work list**
- The list has one row per work item, with filters: Needs you, Running, Queued, Ready for review, Done, Failed. Rows sit in the filter that the server lifecycle derives; no row can be moved by hand.
- The detail drawer opens on demand and closes. It holds the evidence bundle, attempts, PR state, the execution graph (only stages and children that actually exist) and a per-story guidance box.
- Guidance precedence is workflow, then story. It is capped in bytes, recorded as a hash per attempt, and can never widen autonomy or approvals.
- The model selector reuses the composer's thread picker. A manual batch means selecting rows and choosing Run, with no wizard.
- Error states: tracker read failure shows the last good data with a banner. A refused dispatch shows its reason in the row. An item that is not eligible shows why.
- Not to implement: Kanban columns, drag and drop, a column-layout editor, a permanent detail panel, or a separate Board page.

**C4. Symphony runners through the ordinary provider engine**
- Journey: a workflow names an OpenCode/DeepSeek runner. The run attempt launches a managed thread through W6's launch path: deterministic command IDs, the permission ceiling, and positive-evidence states. Approvals, stop and restart therefore share one implementation with children.
- The Codex `AgentRuntime` stays until the new path passes the `SMOKE.md` live run.
- Unknown state: the provider-support table marks a provider "unverified" until a live probe is recorded.
- Value: removes the Codex-only limit without building a second runtime.
- Not to implement: claiming non-Codex Symphony support before a probe, or deleting the Codex runtime early.

**C5 (later, after W5 slice 3). Explicit machine targets for children**
- Journey: `child_capabilities` lists only connected, enabled machines. The human or agent names the machine, and it is shown and pinned on the child row before the child is admitted. Routing is one hop. The durable task row and result mailbox live on the parent's server.
- Unknown state: an unreachable machine shows "unreachable, last seen at …". The child keeps its unknown state and is never moved automatically. Non-loopback connections require a token.
- Not to implement: automatic placement, multi-hop routing, relay, or account linking.

## D. Roadmap changes and delivery order

**Should change**
1. **W4 4.2 to 4.4 and 4.8 (column layout, presets, drag and drop):** replace them with C3's filters. Keep 4.1 (merged-PR detector), 4.5 (honest status), 4.6 (actions, moved into the on-demand drawer) and 4.9 (accessibility). I have not read 16.10, which may already cover this; Sol should reconcile.
2. **W6-C3 result pin "on first settlement of the original child turn":** pin only once the turn has settled and there is no live background work. Otherwise use `waiting_for_background`, or a "background work unknown" flag for providers with no roster. Add a re-check listener, per T3 #22709.
3. **Gap 3 (MCP credential expiry):** bind delegation authority to the live parent run and issue credentials per turn, so idle time is not treated as proof.
4. **W6-C4:** add cancellation of the queued question wake and a pointer for truncated results.
5. **Symphony parsed-but-unenforced approval keys:** fail closed. A workflow at `deliver` autonomy that sets them should refuse to activate, or at least require an explicit "not enforced" acknowledgement shown in its detail.
6. **Symphony Codex-only:** add C4 as the planned path after W6-C3.

**Should stand:** depth 1, caps of 3 per parent and 6 per environment, no hidden queue, queue-only delivery, worktree-only isolation in C1 to C3, the OpenCode-first allowlist, the 16.4 approval rule, W5 staying deferred, the merge gate, and the core-first order.

**Delivery order**
1. Finish Phase 1D and 1E (stands).
2. W6-C1 to C3 with amendments 2 to 4. Acceptance:
   - Fake-provider closure test: exactly one wake.
   - Kill during launch and during delivery: no duplicate.
   - Background-settle regression that fails on revert.
   - Live layer-boot probe.
   - One observed live OpenCode run with the result returned durably.
3. C3 Work list UI in disjoint `apps/web` files, using fixtures after C1. Acceptance: logic tests plus a visual check against the human's references.
4. Symphony `SMOKE.md` live run with Codex against a throwaway tracker.
5. W6-C4 plus C2. Acceptance: a stale approval is refused, the parent cannot approve, and answers survive a restart.
6. C4 OpenCode runner probe.
7. Machines (W5), then C5.

**Boundaries that hold throughout:** unit and integration tests are not live proof. A tree UI alone does not count as the feature. Competitor facts are static reads.

## E. Points to put to Sol

1. **Reject at cap or queue durably.** Synara holds excess tasks in a visible persistent queue (default 3, maximum 8). I prefer rejection for children, because it keeps fan-out explicit and the next wake re-enters the parent naturally. A queue suits Symphony, which already has one.
2. **Steer or queue.** T3 steers results into active turns where the provider supports it. I would keep queue-only, including for question wakes.
3. **Silence recovery in unattended Symphony.** I would never interrupt on silence alone, and retry only after positive death evidence: absent from the live session list and the process identity is gone. Sol may argue an unattended run needs one automatic nudge. I could accept a nudge, but not an interrupt.
4. **One runner engine (C4) or two.** Unifying reduces duplicated approval and stop logic, but it adds migration risk to a path that has never had a live run.
5. **Worktree-only children.** Reviewers cannot see the parent's uncommitted edits (T3 documents the same limit). This conflicts with "review my current changes". Options are a later read-only shared mode with plan mode enforced, or a snapshot commit. I'd defer, and the child result must state the limit plainly.
6. **The execution graph.** It should only draw nodes for real child rows and real stage events. Is a graph worth building before C3 exists?
7. **Per-story guidance.** It is text, so it must never change autonomy or approvals. We should agree that it is versioned per attempt.
