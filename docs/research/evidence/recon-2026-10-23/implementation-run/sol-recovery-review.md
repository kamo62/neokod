## Must fix

1. [P1] The next poll releases the ownership that startup or Stop deliberately held (`Orchestrator/Reconciler.ts:105-141`; `Layers/SymphonyOrchestratorLive.ts:819`). A legacy/recycled/unreadable owner retained by startup has no activeAgents registration. For a terminal attempt Reconciler immediately calls releaseClaim; for a non-terminal attempt it does so after the configured stall timeout. An unconfirmed Stop also removes its active registration during dispatch cleanup and enters this path. The same poll can then launch queued work in the still-owned workspace. Apply the same closure/claim authority requirement to reconciliation, and cover recovery-hold followed by reconciliation, rather than only testing recovery in isolation.

2. [P1] Stop for a historical attempt can stop or cancel a newer attempt (`Runner/Dispatcher.ts:736-786`; `Persistence/Layers/WorkItemRepository.ts:690-710`). cancelAttempt loads the requested old attempt, then the current work-item claim, with no latest-attempt or claim-generation check. If A has ended and B is preparing with ownerPid null, cancelRun(A) reports closed and releaseConfirmedStop(itemId) cancels/releases B. If B has valid stored identity, the closure helper can signal B's process group while settling A. The old latestForWorkItem guard was removed, and the new SQL release is item-ID-only. Bind Stop to the exact current attempt and ownership fence before any signal or state change, and fence the final release again. Reject stale Stop requests harmlessly.

3. [P1] Non-Stop failure and forced interruption still release possibly surviving work (`Runner/Dispatcher.ts:225-277, 653-688`). stoppingAttempts protects only explicit cancelAttempt. An error can transition retry_scheduled in markFailed before process closure, and dispatch's ensuring block releases the claim on any interruption without checking the child/group. The runtime's child is scoped to the outer dispatch scope, while ensuring runs inside the inner dispatch fiber, so cleanup is not evidence that the child has already exited. On an error or outer scope interruption, the scheduler can accept new work before the old process/descendants are confirmed closed. Require positive execution/process closure before retry/release for those exits too; hold unknown ownership rather than converting it to queued.

4. [P1] Production cannot produce or reload the identity accepted by the new Stop/recovery policy (`Runner/AgentRuntime.ts:207-223`; `Runner/Dispatcher.ts:433-450`; `Persistence/Layers/WorkItemRepository.ts:32-63, 240-253, 614-633`). AgentRuntime spawns without detached/group-leader semantics and calls a PID-only callback. setClaimOwnerPid persists only owner_pid; its row schema/SELECT/decoder omit ownerPgid and ownerBirthToken. The contract contains optional fields, but no production persisted identity is actually populated. Thus every real recorded PID is held even after an ordinary successful interrupt. The new confirmed-Stop test uses an in-memory repository that manufactures the identity on PID recording, so it does not exercise this missing production path. Coordinate the spawn seam and migration owner, capture and persist true supported group/birth identity, and verify it through the real repository seam. Do not fabricate PGID from a bare PID.

5. [P2] The public cancellation result still claims confirmed cancellation after a held Stop (`Layers/SymphonyOrchestratorLive.ts:1887-1907`; `Runner/Dispatcher.ts:848-859`). cancelAttempt returns void for stop_unconfirmed; the orchestrator unconditionally records run_cancelled and sends “Run ... was cancelled”, while stopAllRuns increments its stopped count. A legacy owner that was deliberately held therefore produces a false terminal notification/count. Return a structured confirmed/held acknowledgement and adapt these existing callers so a hold stays visibly unconfirmed.

## Further affected race to cover with the above correction

Stop takes its work-item snapshot before interrupting, discards the five-second Fiber.await timeout result, then treats ownerPid null as no_owner_recorded (`Dispatcher.ts:739-770`). A Stop that overlaps lazy spawn/PID recording can therefore use an obsolete null-owner snapshot. Re-read and fence ownership after tracking settles; a timed-out tracked execution cannot be proven closed merely because the earlier snapshot had no PID. This is part of findings 2/3, not a request for another ownership framework.
