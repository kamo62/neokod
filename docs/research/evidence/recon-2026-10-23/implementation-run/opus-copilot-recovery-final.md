## P2 findings

1. **A Stop can be confirmed while the dispatch is still starting** (existing gap, made visible by the new `stopClosure`).
   - **Trigger:** Stop arrives after the attempt row is created (`Dispatcher.ts:618`) but before the run is registered as active (`:1010`).
   - **What happens:** `registered` is undefined, no child process is recorded yet, so closure reads as `no_owner_recorded`. The item is released to `cancelled`, `stop_confirmed` is written, and `getRun` now shows a confirmed closure.
   - **Impact:** the dispatch then carries on. On the committed-handoff resume path (`:788-811`) the finalizer still runs validation and creates a PR, and takeover may already have handed the workspace to Work mode. The normal path is safe because recording the child fails and the runtime aborts.
   - **Fix:** mark the attempt as starting before `runAttempts.create`, and have `cancelAttempt` return `held("dispatch_not_registered")` while it is starting but not yet registered. Re-check the claim fence immediately before `finalizer.finalize` on the resume path.

2. **Recovery still has a timestamp-based release when it cannot read the attempt** (existing; widened by this range).
   - **Trigger:** at `Recovery.ts:263-283`, a failed `latestForWorkItem` read is treated as "no attempt". After `STALL_WINDOW_MS` the claim is then released by `claimedAt` age with no closure check, even if a child process is recorded.
   - **Why it is wider now:** `rowToAttempt` now fails on an undecodable accepted-guidance column.
   - **Fix:** treat a read error as a hold, not as absence. Allow the age-based release only when no attempt exists and `ownership.ownerPid === null`.

3. **The early-failure path swallows a failed binding write** (in range, fails closed).
   - **Trigger:** at `Dispatcher.ts:524-530`, `failEarly` ignores the error if the `issue_claimed` write fails.
   - **Impact:** `markFailed` then records `claim_binding_unverified`, and the item stays in `preparing` permanently, although no child ever existed.
   - **Fix:** if the write fails, move the item straight to `failed`, as the main dispatch path already does at `:655-671`.

4. **The Stop RPC reports success when it cannot decode the outcome** (in range).
   - **Trigger:** `stopResultFrom` in `ws.ts` returns `{ ok: true }` when the outcome does not decode. The code's own comment and the contract say `ok` is not proof of a stop.
   - **Impact:** an unknown result is reported as success. The web client currently ignores the result, so there is no visible effect today.
   - **Fix:** return `{ ok: false }` in that case.

**Minor:** the comment at `Dispatcher.ts:703-706` says the ownership-failure path "never releases the claim". In fact, `markFailed` sees no recorded child (`no_owner_recorded`) and schedules a retry before the dispatch scope stops the briefly spawned, idle child. The window is small because of the retry backoff. Correct the comment, or hold the claim on `AgentRuntimeChildOwnershipError`.
