Admission must preserve evidence boundaries. The exact instance exposes `snapshot.getSnapshot` and `snapshot.refresh` already. A ready/authenticated snapshot with a nonempty advertised/custom catalogue can establish “listed for this instance”, not successful structured generation or account entitlement. Configured custom models are valid candidates and are already appended to Codex snapshots (`CodexProvider.ts:258–281`, 432–445). Do not reject them merely because they are custom, infer support from another instance, or treat a null `capabilities` field as unsupported.

For an absent slug, use at most one existing exact-instance refresh before refusing it as “not advertised by the current provider catalogue; refresh or choose a model in Text generation model”. This avoids executing a known absent default and avoids treating an old cached omission as final. If refresh/probe fails or gives incomplete/empty evidence, report verification unavailable with retry guidance, not “model unsupported”. `refresh` may die (`makeManagedServerProvider.ts:156`), so contain that failure as a typed generation error. No new polling, durable negative cache, invented freshness threshold or registry-wide refresh is needed. For a listed/custom model whose provider still refuses execution, retain the real typed failure and present safe actionable auxiliary context. Catalogue membership must never be labelled a live capability PASS.

The existing `TextGenerationError` shape suffices. Existing activity contracts allow a string kind and unknown payload (`orchestration.ts:330–340`), and `session-logic.ts:696–711`, 905–960 already renders generic activities. No shared contract, persistence migration, provider driver SPI, lifecycle outcome policy or default-model constant change is required. If a focused rendering regression exposes a real gap, add only `apps/web/src/session-logic.test.ts`; otherwise leave it alone.
