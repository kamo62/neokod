# Independent audit: T3Code nightly reuse and Neokod thread orchestration (Opus 5.5 high, read-only)

## Bottom line

- **There is no published T3 "council" skill.** T3 ships generic `delegate_task` / `orchestrator_capabilities` tools. A user-written council would sit on top of those, and I can't confirm the engine from the screenshot.
- **Only 3 upstream commits are worth porting now**, all small, in code paths Neokod actually has: git output parsing (`9a6380263`), terminal clipboard scanning (`9f660d384`), and the shell-stream update intent (`fd1063ba7`/`d7a8d6f32`). The last one needs a measurement before any code changes.
- **Two items need investigation first, not a port.** Both are hypotheses tied to Phase 1E, not confirmed Neokod defects: a Claude CLI possibly surviving a `kill -9` of the server (`5ffe04593`), and what happens when runtime-event ingestion fails mid-turn (`6f6f68ad2`).
- **Upstream's delegation and Stop fixes have no Neokod equivalent**, because they live in upstream's V2 engine. They are useful as extra acceptance criteria for W6-C2 to C4. W6 itself remains absent from Neokod source and its formal core exit is still closed.

I wrote no plan file: this session had no Write tool, so the full report is below.

## How upstream delegation works vs current Neokod

**Upstream (T3) normal-thread delegation:**

- The agent calls `delegate_task`, which creates a T3-owned child thread.
- Default isolation is **`shared`**: the child works in the parent's checkout. `worktree` isolation does not copy uncommitted edits.
- The default mode is `async`. A finished child's result is **steered into the parent's active turn** where supported, otherwise queued.
- This differs from Neokod's 16.4 decisions (isolated worktree by default; results queued, never steered). Both differences are deliberate on Neokod's side and should stay.

**Neokod as it exists today:**

- `apps/server/src/mcp/` registers only the preview toolkit. `McpInvocationContext.ts:10` defines `McpCapability = "preview"`.
- There are no child/delegation tools, contracts or service anywhere in source. The only grep hit for `child_start` is a git trace2 event name at `GitVcsDriverCore.ts:510`.
- **W6 is absent, as the plan already records.**
- The Neokod MCP endpoint is injected into Codex (`CodexAdapter.ts:1660`), Claude (`:3801`), Cursor, Grok, Kiro and ACP sessions.
- OpenCode is injected only when Neokod spawns the server itself (`OpenCodeAdapter.ts:1339-1353`, `if (mcpSession && !server.external)`). Spawned servers are per session (`opencodeRuntime.ts:1222-1246`), so one thread can't overwrite another's credentials.
- Copilot uses its own MCP config path (`copilot/CopilotMcpServers.ts`). I did not trace whether it gets the Neokod endpoint.

**Three kinds of orchestration to keep separate:**

1. **Provider-native tasks**, such as Codex collab agents. Neokod maps them to `task.*` events in the Subagents panel (`CodexAdapter.ts:529-600, 765-818`). Neokod has no admission control, durable result or ownership for them.
2. **App-managed W6 children.** Not implemented.
3. **Symphony's autonomous tracker pull.** A separate plane with its own runner, recovery and feedback (PR151 and PR152).
