## Ranked reuse candidates

### 1. Large terminal control strings: port a scan-offset fix

Upstream [PR23819](https://github.com/pingdotgg/t3code/pull/23819), commit [`9f660d38456f5234b6b1c359732746597cfc83e4`](https://github.com/pingdotgg/t3code/commit/9f660d38456f5234b6b1c359732746597cfc83e4), changes `apps/server/src/terminal/Manager.ts` and its existing test.

Concrete local gap: Neokod `Manager.ts:998–1100` joins `pendingControlSequence + data` and calls `findStringTerminatorIndex` from the control-string start on every chunk (`1045`, `1091`). `1999–2003` calls this in the PTY output path and retains the pending string. A long OSC52 clipboard or DCS string split across many chunks therefore rescans the accumulated prefix repeatedly. This same code shape remains present at the inspected head. Existing tests cover chunk-split control sequences but lack the long pending-string scan bound.

Port only the upstream offset idea: begin the terminator search at the new bytes, retaining the last pending character so ESC/backslash split termination still works. Keep Neokod's strip rules, output ordering, persistence and reopen behaviour. Upstream's diff is about 12 production lines and a focused integration-style regression, without a contract or UI change.

Evidence: upstream reports a deterministic regression falling from 1,368,175 character reads to 123,066, against a 262,242 bound; a real node-pty/server fixture reports roughly 24.4 million visits versus roughly 349,700 for a 349,536-byte sequence, with identical persisted history. This is parser-work evidence, **not measured UI latency**, and PTY chunks vary. No Neokod benchmark has run. String concatenation itself remains; do not promise globally linear memory/copying from the scan optimisation alone.

Risk/checks: preserve BEL, C1 ST, split ESC/backslash, later controls, mixed stripped/preserved sequences, persisted bytes and reopened history. Adapt the upstream focused long-sequence regression alongside the existing Manager suite. During implementation run the focused suite plus required `vp check` and `vp run typecheck`; no compiler build is needed for this server-source port.

Plan fit: existing terminal reliability/performance scope, historically X-14; it introduces no W6 capability and closes no formal core/live Stop gate. A separate small change can be reviewed without changing held PR152's acceptance status.

### 2. Git output without progress callbacks: skip unused line buffering

Upstream [PR23953](https://github.com/pingdotgg/t3code/pull/23953), commit [`9a6380263b0304494151d297a53210c10b1d07ef`](https://github.com/pingdotgg/t3code/commit/9a6380263b0304494151d297a53210c10b1d07ef), changes `apps/server/src/vcs/GitVcsDriverCore.ts` and its existing test.

Concrete local gap: Neokod `collectOutput` at `610–688` always appends decoded output to `lineBuffer`, scans for newlines, slices it, and flushes it (`665–666`, `682–683`) even when `onLine` is undefined. Callers in `executeRaw` pass optional `input.progress?.onStdoutLine/onStderrLine`; most `runGitStdout` status/diff/file-list calls supply no callback. NUL-separated file lists or long newline-free patch output repeatedly scan an unused growing line buffer. Output bytes and caps still need collecting, so only line handling should be conditional.

Port only `if (onLine)` around the append/scan/flush work. Keep Neokod's current UTF-8/truncation semantics. Upstream has a newer auxiliary line decoder; do not import that unrelated difference.

Evidence: upstream PR's synthetic/real-Git harness reports medians of 12.509→2.549 ms for 1 MiB NUL data, 113.981→2.615 ms for 4 MiB, and 167.961→37.659 ms for real `git ls-files -z` over 20,000 synthetic indexed files. These are upstream-reported host/workload measurements, **not Neokod timings**. The PR explicitly reports a callback-control median regression, 140.247→153.416 ms, and declines a universal speed or allocation claim. The production callback path is unchanged by this fix.

Risk/checks: callback-present and absent output equality, UTF-8 split at arbitrary byte boundaries, NUL/newline content, trailing lines, byte caps with/without truncation marker and existing commit progress callbacks. Adapt its focused fake-spawner regression to Neokod; retain existing integration tests. Required repository checks follow if implemented.

Plan fit: backend performance in existing VCS scope, no UI transplant or orchestration rewrite. Coordinate with the independent Git-safety work already mentioned by the parent; this audit authorises no overlapping edits.

### 3. Optional observability follow-up: meter checkpoint Git attempts

Upstream [PR24218](https://github.com/pingdotgg/t3code/pull/24218), commit [`e340aaeeb98bc6ac623c2e70ac8eca8bcbddfe1b`](https://github.com/pingdotgg/t3code/commit/e340aaeeb98bc6ac623c2e70ac8eca8bcbddfe1b), changes `VcsProcess.ts`, `GitVcsDriver.ts`, and tests.

Local gap: Neokod core `GitVcsDriverCore.execute` has `gitCommandsTotal/gitCommandDuration` metrics, but checkpoint commands in `GitVcsDriver.ts:786+` go through its `gitCommand` helper (`375+`) into `VcsProcess.run`; that process service has no corresponding metrics. The existing dashboard therefore omits this class of work. This is an attribution gap, **not a speed optimisation**.

Upstream places instrumentation at each actual spawn/retry/fallback, uses a bounded label set and distinguishes allowed nonzero exits from failures/interruptions. The PR reports eight capture attempts and eight duration samples through a real synthetic server/exporter fixture; it explicitly bypassed provider lifecycle/outbox scheduling. Reuse that measurement contract if profiling shows checkpoints are relevant. Preserve cardinality, retries, cancellation and no-double-counting with the already-instrumented core. Neokod's VcsProcess has a different contract and no upstream streamed output mode, so do not copy the whole diff.

Priority lower than the two confirmed compute-waste fixes. Existing observability scope only; no user-facing feature or W6 gate credit.

## Council: custom policy over real app-owned primitives

The owner's screenshot description explicitly calls council a custom skill reviewing with Opus, Muse and Sol and shows three subagents. Public source at this nightly supports the underlying cross-provider orchestration, but does **not** establish a bundled council skill or built-in council product mode. Muse injection is explicit in `packages/provider-muse/src/server/adapter.ts:1410`; the shared ACP adapter applies `t3AcpPromptWithInstructions` at `packages/provider-acp/src/server/adapter.ts:7171+`.

- Public skill tree lists `.agents/skills/contribution-triage`, `test-t3-app` and `test-t3-mobile`; `.claude/skills` points into this shared skill area. Source/doc search for `council` outside vendored repositories and transcript fixtures returned no matches. This proves absence in the inspected public tracked scope, not absence from a user's private/global skill directory. We did not inspect or obtain that private skill.
- `packages/provider-core/src/server/orchestrationInstructions.ts:8+` injects general instructions: discover `orchestrator_capabilities`, choose actual provider/model IDs, use `delegate_task` for cross-provider or explicitly T3-owned children; native subagents are preferred only where chosen model/options are supported. Worktree isolation is explicit; uncommitted changes are not copied. Each delegated review round is a fresh task with its own ID and original brief/findings/objections. No hard-coded Opus/Muse/Sol council or fixed three-reviewer requirement occurs there.
- `apps/server/src/mcp/toolkits/orchestrator/tools.ts` defines actual tools; `handlers.ts` obtains the authenticated invocation scope and calls `OrchestratorMcpService.delegateTask` through `McpToolAccess.actsAsCaller`.
- `OrchestratorMcpService.ts:2145+` requires an active parent run owned by this provider session, resolves target/modes and stable command ID, and dispatches `delegated_task.request` through ThreadManagementService with parentThread/run/root-node, selected model, runtime/interaction mode and wake policy. It requires an `app_owned` subagent event and returns taskId/childThreadId. `readTask` validates origin and parent ownership; task status and result paths retain that attribution. This is a stronger claim than a UI showing three names.
- A screenshot alone cannot establish that those three particular executions used these tools or returned accepted durable results. Model selection, task receipts and provider output would be required. Source proves the available path, not that screenshot's runtime provenance.

Neokod's corresponding capability remains **unimplemented/gated**: this head's MCP credential registry grants `preview` only; no orchestrator toolkit, delegation contract or managed-child service exists. Provider-native roster observation remains separate. The existing canonical W6-C1–C6 plan already covers admission, managed children, durable result return, feedback, tree and provider expansion. Council can later be a reusable policy/skill on that foundation. It does not require a new mode, a Symphony rewrite, wholesale T3 V2, or bypassing the formal core exit.

## Recommendation and limits

Prioritise only terminal scan offset and Git no-callback line parsing as small source ports when implementation is authorised. Keep checkpoint metering as optional profiling support. Do not transplant V2 persistence or claim a general upstream speedup. Preserve the held PR152 live feedback gate, formal Phase1 exit, then W6-C1–C3 before C4–C6 and later machines/providers. This audit changes none of those states.

Not checked: Neokod runtime or benchmarks, upstream evidence archives/hash verification, private council skill, actual screenshot execution receipts, Windows or Linux runtime, or every delta commit semantically. Required `vp check` and typecheck were not rerun for this read-only audit; existing source acceptance is neither invalidated nor extended.
