### S01: Command receipt reuse does not validate aggregate or request identity

Priority: P1. Source-confirmed acceptance defect; conflicting-retry scenario unrun.

WS dispatch normalises a wire command and invokes the serialized engine. processEnvelope looks up getByCommandId before deciding the command. An accepted stored receipt returns its resultSequence immediately; aggregateKind/aggregateId are present in the stored row but never compared with commandToAggregateRef. The receipt schema has no canonical request fingerprint. Thus reusing a command ID against another thread, or with another command/body on the same thread, can return success for work that was never accepted.

This violates command idempotency and makes a transport retry receipt unsafe as an aggregate-specific acknowledgement. Serialization prevents a concurrent race but does not repair identity mismatch. It also means a correction using the same previously rejected ID will remain rejected, which is correct only if the caller knows IDs identify immutable intents.

Minimum maintainable direction: Keep the serialized transaction. Before reusing a receipt, compare target aggregate and command kind; bind immutable caller intent with a canonical input hash if semantic replay is supported. Make conflict a specific error, preserve original receipts and avoid upsert-overwriting a receipt’s identity. Do not hash resolved defaults that may legitimately change across an honest retry.

Focused regression gate, not run: Two threads: accept ID X on A, submit X on B and assert explicit conflict with no events on B. On A, submit X with changed body/type and assert conflict; exact retry returns the original sequence and one event set. Exercise accepted/rejected receipts and transaction rollback. Existing engine/receipt tests are the narrow target; no new infrastructure needed.

### S02: Durable command acceptance is separated from provider launch by a volatile effect path

Priority: P1. Current recovery design limit; crash/duplicate-work scenarios unrun.

The engine atomically writes events/projections/receipt, then broadcasts events through an in-memory PubSub. ProviderCommandReactor.start subscribes only to the live stream; it has no persisted consumer cursor or replayed effect claim. Its 10,000-entry/30-minute handled-turn cache is process-local, set before sending. processTurnStartRequested forks ProviderService.sendTurn and does not pin the returned provider turn against a durable launch intent. ProviderSessionReconciler settles projected/live binding differences but does not establish that a committed unobserved send never reached the provider.

A crash after accepted turn intent but before consumption can leave accepted content without a send. A crash after the provider starts but before the corresponding ingestion commit leaves ambiguous execution. Blind replay is unsafe: a domain receipt proves acceptance, not external side-effect idempotency. Symphony has the same recovery class through a different path: Dispatcher reads agent.pid before the lazy runTurn spawn, usually gets null, and has no later setClaimOwnerPid caller. Reconciler trusts the volatile activeAgents registry and, after a stall threshold, releases claims without proving surviving child-process termination. No claim-after-restart overlap was run here.

Minimum maintainable direction: Introduce the smallest durable execution intent and outcome contract at the existing engine/runner boundaries: accepted, starting, confirmed provider thread/turn, failed or launch-unknown. Classify replay-safe local effects separately from process-bound sends. Resolve ambiguous sends through provider-native correlation and confirmed stop, not a TTL resend. Record child incarnation only after spawn and make claim recovery prove ownership/termination or quarantine it. Preserve authoritative Code and Symphony attempts rather than mirror one into the other.

Focused regression gate, not run: Crash fixtures at commit-before-consume, send-before-provider-response and response-before-binding write. Exact retry cannot produce a second provider turn; ambiguous state stays explicit. Symphony fixture returns pid=null before spawn and a concrete PID afterward, then restarts with a surviving fake child: do not requeue while ownership is unresolved. Include claim-without-attempt recovery so it neither races a live preparer nor remains permanently stranded.

### S03: Terminal history drain can report success after a failed write; stale callbacks are PID-scoped

Priority: P1 durability; P2 incarnation scenario. Source-confirmed swallowed persistence error; PID-reuse scenario unrun.

Terminal output updates in-memory history, enqueues a keyed coalesced save and emits output. The persistence process sleeps 40 ms, writes the target file directly and catches a filesystem failure as only a log warning. persistHistory then drains the key, which means no pending worker item, not successful persistence. KeyedCoalescingWorker removes the active value and clears active state when the process returns success; the caught write therefore leaves no failed generation for retry. PTY callbacks capture processPid, and enqueue/drain check only the current numeric PID/status, not the captured process object or incarnation.

A transient last-write error followed by idle/close can lose the latest terminal tail while flush returns normally. Direct replacement is also weaker than atomic temp-file rename on crash. If a restarted process reuses the same PID and a queued old callback arrives, its guard can admit output/exit into the replacement; that is an unrun scenario, not an observed failure. Unsubscribing handlers and process-object killFibers are useful existing safeguards, but queued callbacks still need the stronger identity.

Minimum maintainable direction: Retain a dirty history generation until an atomic write succeeds, surface failure through explicit persistence evidence, and retry with bounded backoff without suppressing live output. Compare callbacks/drain against the captured process object or monotonic incarnation. Preserve coalescing; do not write every output frame synchronously.

Focused regression gate, not run: Inject one write failure then recovery with no further PTY bytes; drain must not masquerade as a successful saved generation. Close/reopen must retain the final output and existing target on partial-write failure. Restart using a fake reused PID; old data and exit callbacks must not mutate the new process. Use existing Manager and KeyedCoalescingWorker fixtures.

### S04: EOF classification waits for child exit, and Symphony completion is not pinned to a turn

Priority: P1 EOF; P2 waiter contract. Source-confirmed closure/correlation gaps; process-alive EOF and unrelated-completion scenarios unrun.

The local Codex package does handle clean input EOF; earlier shorthand that it simply ignores EOF would be inaccurate. Its success path calls handleTermination with makeTerminationError(handle), whose effect awaits handle.exitCode. handleTermination fails pending requests and ends outgoing only after that classification effect returns. A child that closes stdout while staying alive can therefore leave all pending requests unresolved. Separately, Symphony waitForTurnCompletion consumes a queue of raw notifications, accepts any turn/completed without thread/turn correlation and leaves its forkScoped consumer running after Deferred resolution.

The EOF gap is specifically clean stream end before process exit, not the already-handled process-exit case. The Symphony consumer’s lifetime is the wider dispatch scope; if runTurn is reused, consumers compete for one queue. Current real runtime returns completed=true or failure, so Dispatcher’s continuation loop normally does not reach a second turn; do not present stolen second-turn completion as a reproduced current normal flow. Unrelated/native-child completion and unscoped errors remain correlation scenarios to test.

Minimum maintainable direction: Fail outstanding transport work on EOF immediately with an EOF error; enrich it with exit status only when available and bound subsequent process shutdown. Pin Symphony waiting/interrupt to the accepted thread and turn, end each waiter on settlement, and own one notification router per runtime with per-turn subscriptions. Keep existing typed protocol decoding and process-exit handling.

Focused regression gate, not run: Fake child emits a final complete/partial line, closes stdout and keeps exitCode pending: requests must fail within the explicit EOF bound, independent of process exit. Preserve final-line decoding. Feed an unrelated turn/completed before the pinned one and require the wait to remain open. Reuse the runtime for two turns in a focused unit fixture and verify one active consumer, no stolen completion and no leaked waiters.

### S05: Checkpoint rewind mutates the whole resolved workspace without proving exclusive ownership

Priority: P1 data-loss scenario. Current destructive scope is source-confirmed; shared-CWD overwrite scenario unrun.

thread.checkpoint.revert validates only that the thread exists, then the reactor resolves a live provider session’s cwd and calls restoreCheckpoint. Git restore operates on dot with --worktree --staged, then git clean -fd dot removes untracked paths; reset adjusts staging afterward. The reactor rolls back the conversation only after the filesystem restore. It has no conversation-only variant or canonical workspace ownership check before restore, and multiple Code threads may resolve to the same project root.

Restoring files is the current advertised command semantics, so its existence alone is not a defect. The missing ownership proof matters when another thread, terminal or Symphony attempt writes that cwd: one thread’s checkpoint can overwrite another’s tracked changes or remove newly untracked work. A filesystem-success/provider-rollback-failure also leaves a partially applied cross-system operation; no runtime reproduction was attempted.

Minimum maintainable direction: Define conversation-only and conversation-plus-files as separate contracts if both are wanted. For file restore, acquire/fence canonical workspace authority and reject or quarantine conflicting writers. Preserve capture’s isolated temporary index. Persist the restore operation and partial outcome so a failed provider rollback cannot look like an entirely successful rewind; do not automatically delete recovery evidence.

Focused regression gate, not run: Two threads sharing one canonical/symlinked cwd: B creates tracked and untracked work after A’s checkpoint; A’s restore must be refused until the declared exclusive-ownership condition holds. Verify isolated worktree restore remains correct. Inject provider rollback failure after successful file restore and require explicit partial outcome/recovery evidence. Never execute this test against the user’s working tree.

### S06: Default transport posture contradicts the README and Plan 20’s current-auth claims

Priority: P1. Source-confirmed security/documentation mismatch; no live attack or listener probe.

CLI config resolves strictTransport to false by default and only mints a loopback bearer when strictTransport=true (unless a desktop bootstrap supplied one). Router-wide LocalTransportAuth.validate returns before Host/Origin checks when strict is false. CLI tests explicitly expect default serve to have no token. README says headless serve/start require a per-launch token and Host/Origin validation happens on every request; Plan 20 repeats that assertion.

The actual default local listener exposes the broad RPC surface to callers that can reach it without the documented token/Host/Origin gates. Loopback binding still limits ordinary remote access; WSL bearer remains a separate required path. Browser exploitability depends on concrete browser/DNS/network conditions and was not established. This is not evidence that every installation is unauthenticated: strict or bootstrap-token configurations differ.

Minimum maintainable direction: Make the intended product default an explicit decision, then align code, README, self-hosting guidance and Plan 20. If strict is the required default, change it deliberately and preserve explicit proxy configuration. If open loopback remains intentional, document it accurately and show the actual posture. This cannot be repaired by adding an MCP-only permission wrapper or changing desktop technology.

### S07: Governed admission and common Code/Symphony attempt authority are not implemented

Priority: P1 prerequisite to agent-controlled delegation; existing opt-in design gap. Source-confirmed architecture limit; not an unauthenticated exploit claim.

Authenticated/otherwise admitted WS and HTTP callers normalise commands then reach engine.dispatch. Commands do not carry a server-derived actor/lineage/ceiling context. decider runtime-mode changes, approval responses and checkpoint reverts require the target thread but not an agent-aware capability decision. Default RuntimeMode is full-access, while invalid persisted mode deliberately falls back to approval-required. ProviderCommandReactor binds Code threads to a driver; Symphony builds its own Codex runtime and records separate RunAttempt/LiveRequests state without dispatching through that engine. config.agentProvider labels the Symphony attempt, but factory.make still spawns config.codexCommand.

The current trusted-developer local app is not a shipped governed delegation engine. Calling a wrapper “the single choke point” would overstate coverage. RuntimeMode, Symphony autonomy and Codex sandbox/approval policy are different vocabularies, not one safe cross-provider rank. Config parses before_push/before_pull_request/protected_paths/policies but the runner does not consult those fields. Those are documented non-gates, not new secretly missing enforcement. Provider-native subagents are observed rather than admitted as app-owned children.

Minimum maintainable direction: Keep independent authoritative execution attempts; add a small durable request/result link and server-derived admission context first. Route every external entry and later mutation through engine-owned admission when governance is enabled; explicitly instrument Symphony or adapt its execution onto the common provider service. Capability checks compare provider-specific effective abilities, preserve unknown and retain Kiro restrictions. Enforce or reject parsed-only controls before presenting them as guards. Do not build a third state machine that mirrors Code and Symphony lifecycle.

### S08: Symphony reintroduces scrubbed tracker secrets when spawning its child

Priority: P1. Source-confirmed credential-boundary defect; no secret values read or child run.

Runner/Live resolves the selected tracker’s secretEnvironmentNames and supplies process.env to makeCodexAgentRuntime. spawnAppServer removes those names with scrubEnvironment, then passes the resulting env to ChildProcess.make with extendEnv:true. Environment-backed tracker credentials present on the server are inherited by the coding child despite the documented promise they are scrubbed. Inline YAML secrets not present in process.env are a different case. Pure scrubEnvironment tests cover removal from a JavaScript object but not the final spawned environment. This does not require an attacker or remote access to be a defect: it contradicts an explicit child credential boundary.

Minimum maintainable direction: Pass a complete scrubbed environment with extendEnv=false at both resolution and spawn. ### S09: Chat delegation is a new manual item, and tracker eligibility can overstate complete dependency evidence

Existing WorkItemRepository uniqueness on project/tracker-kind/opaque ID and fenced claims are reusable, but random manual IDs evade canonical intake dedupe.

## What is good and reusable

Keep the core transaction and its serialized decision boundary. The engine commits domain events, projection updates and command receipt together; failed commit does not expose a half-projected successful command. RuntimeReceiptBus is intentionally ephemeral milestone signalling, especially for tests, and should not be confused with the persisted command receipt or proposed provider-effect receipt. Typed schema normalisation, server-owned runtime-item closure/startup reconciliation, per-provider adapters and instance-bound session directory provide real boundaries to extend rather than replace with generic provider guesses.

Keep the lightweight command/shell snapshot separation and the atomic per-thread snapshot sequence. Keep coalescing for terminal persistence, explicit provider stop outcomes, Kiro’s supervised restrictions and provider-dependent approval vocabulary. Symphony claims use stable project/tracker/native identity, owner tokens/generations and legal lifecycle transitions; workspace ownership uses canonical paths/generations. Those are useful primitives, although current checkpoint and process-recovery consumers do not prove complete coverage.

Keep tracker and source-control integrations independent. Validation/evidence comes from host checks separately from agent-authored handoff material; merge requires affirmative CI, review and mergeability evidence. ## Minimum direction and replacement decision

First freeze and correct current truth: the actual transport default and documentation mismatch, credential spawn boundary, aggregate-safe receipts, EOF and rewind ownership. Implement each as a narrow shared contract with its focused regression fixture. Do not defer these behind a desktop-shell programme.

Next add durable intent, accepted provider attempt and outcome/link records on the existing command/runner boundaries. Governed provenance and capability ceilings are server-derived at admission, preserved through later mutations. One ordinary-chat request can resolve to a Code execution or Symphony canonical work item; each execution plane retains its own authoritative attempt and maps outcomes to the common request. A request/result link is shared coordination, not a duplicate attempt lifecycle.

Choose explicitly between adapting Symphony execution onto the common provider service and retaining two planes with equivalent admission/instrumentation. Do not introduce a third runner or mirror authoritative Code/Symphony states to make a unified UI. Prototype only the smallest cross-plane scenario: submit one canonical tracker item from chat, accept durably, start once, stop the pinned attempt, restart, and deliver one linked result under existing review/workspace policy. Include a second provider and unknown capability evidence before calling it provider-neutral.

A replacement engine becomes justified only if that pinned prototype shows the existing seams require sustained duplicated authority or obstruct the required lifecycle, and a replacement demonstrably simplifies it. Compare actual contracts, provider coverage, cancellation, accepted/started/unknown semantics and migration of copied history, with rollback and equivalent workload budgets. Competitor source elegance, file count or a new shell alone is not evidence for an engine rewrite. No replacement feasibility benchmark was run.

A desktop-shell change can affect packaging, startup cost, window processes, native notifications, PTY implementation and rendering overhead. It cannot repair receipt identity, send-after-commit ambiguity, leaked credential inheritance, raw-command admission, tracker canonicalisation, unsafe Git restore, incomplete dependency reads or synchronous server storage cost. Shell-native capabilities still require ownership, generation and evidence contracts. Keep the engine and shell decisions separate; do not present either as free.
