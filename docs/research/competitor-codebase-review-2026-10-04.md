# Competitor code, current issues and Neokod implementation direction

Research dated 4 October 2026. Local baseline: `80334a4c8a6badd9a0014bbc34af4bcb346c3cff`, with the owner's existing Symphony changes preserved. This report answers the B-and-above comparison, Synara's last three calendar months, current competitor issues, ordinary-chat orchestration, optional workstreams across delivery applications and the fresh-core alternative. The expanded scope includes frontend, desktop, terminal, history, search, memory, startup, notifications and delivery-app integration.

## Decision

Keep Neokod's existing event-sourced engine as the default. Build durable, governed task and result linkage that ordinary chat can use. Keep Symphony as the optional tracker/scheduler/validation/review destination. The most useful competitor ideas strengthen acceptance, delivery, ownership and recovery. Importing a complete competitor engine would discard working local contracts while still requiring these invariants.

The proposed user journey is: discuss work in chat, create bounded children when useful, inspect attributed progress and evidence in that conversation, and say “Send this task to Symphony” using a configured delivery connection. Jira ABC-123, Linear NEO-42, a GitHub Project item and an Azure Boards work item are examples of the same flow, with different native identities and capabilities. The action can queue or claim the existing item and return a linked result without forcing a mode change. Symphony's board, workflow and approval policy remain valuable. Current Neokod does not yet implement that exact reference-based intake and durable originating-chat/result link.

A replacement remains a credible option if a small prototype demonstrates a simpler shared lifecycle, provider parity, recoverable migration and measured benefit. The present source evidence supports targeted evolution; it does not prove a rewrite impossible or more expensive. The comparison below identifies the evidence that could change the decision.

## What each competitor does well, and what we would use

### T3 Code Nightly

V2's important contribution is a real execution/lifecycle substrate: durable queued work, run/node/attempt lineage, result transfer, replay classification, schedules and watches. Delegation can happen inside an existing provider conversation. It does not inherently require a second LLM coordinator, separate mode or QuickJS runtime. The captured latest nightly is `v0.0.46-nightly.20261004.2644`, commit `737993303d36e10674c54b95e5bd3826682c99c7`; stable `v0.0.45` predates V2. See the [nightly and PR assessment](upstream-nightly-review-2026-10-03.md).

Use the concepts through Neokod-owned commands and persistence. First address local destructive rewind, receipt identity, lost terminal persistence, process guards, exact SQLite semantics and provider EOF/auth/config truth. The full inventory covers 3,233 closed PRs since the latest published Neokod release proxy and 1,059 open PRs. That proxy is v3.6.0 on 10 August; the installed/deployed version was not established. Eight capped/inconsistent file inventories remain deferred. The ledger is exhaustive inventory and path triage with selected deeper comparisons, not 4,292 complete semantic diff audits.

Sol independently checked all 100 substantive PR findings and 17 broader claims. It rejected the earlier reason for excluding #12847: all four indexes exist in local migrations. This is now a conditional query-plan investigation. It also narrowed #9000 to client snapshot materialisation, clarified that conversation-only rewind would be a new local contract, corrected #11773's fallback anchor, and distinguished normal CLI live-RPC use from its direct-DB fallback. The path classifier now excludes sampled relay/connect/fixture leaks and desktop composer UI, while remaining explicitly mechanical. The [corrected findings appendix](t3-corrected-findings-2026-10-04.md) gives replacement wording and finite gates for all 60 qualified PR findings and seven qualified broader claims.

### Omnigent and Paseo

Omnigent separates saved child results from an ephemeral inbox and can recover undelivered outcomes by dispatch identity. Its stale-callback guard is useful, but its false-idle completion window is a warning: receipt dedupe does not make a guessed terminal result correct. Paseo exposes managed child controls from ordinary chat, distinguishes those sessions from provider-native observations, restores workspace facts before resuming and flushes coalesced deltas at semantic barriers. See the [source and issue detail](competitor-tier-sb-evidence-2026-10-04.md#omnigent).

Use a server-owned result inbox and register the completion recipient before provider start. [Omnigent #8874](https://github.com/omnigent-ai/omnigent/issues/8874) reports premature completion and lost real results; [Paseo #5928](https://github.com/getpaseo/paseo/issues/5928) identifies a fast-child watcher-registration race with fix PRs still open. The separate missing-parent report in [Paseo #5884](https://github.com/getpaseo/paseo/issues/5884) is contested for injected, agent-scoped MCP and must not be generalised to all creation. Preserve caller identity and show capabilities actually available to that caller.

### OnOrca and Agent Orchestrator

OnOrca persists accepted dispatch, receipt, parent/depth and starting options before launching a worker. It retires authority only against positively completed runtime inventory. Agent Orchestrator provides durable worker reports with claim/ack tokens and messages queued through cold provisioning. Its current earliest-item retry path can starve newer reports after one permanent delivery failure. The [A-tier source investigation](competitor-tier-a-evidence-2026-10-04.md) traces the transactions and actual callers.

Use acceptance stages and durable attributed reports, with per-recipient failure isolation and bounded retry/backoff. [OnOrca #25084](https://github.com/stablyai/orca/issues/25084) reports written-but-unsubmitted prompts: terminal ready and input accepted are not provider started. [AO #6119](https://github.com/Untrivial-ai/agent-orchestrator/issues/6119) reports starvation despite durable rows, corroborated by the source scheduling shape. Do not copy either a readiness heuristic or queue policy that preserves rows while blocking progress. AO's mandatory Chat/TUI product choice is not required for our ordinary-chat experience.

### CodexHost and Hermes

CodexHost treats native session identity, effective model/permissions and capability differences as real per-harness contracts. It distinguishes actual native compaction from a summary prompt and declines unsupported unattended inbound delegation. Hermes represents cancellation as requested until a result arrives, publishes completed siblings independently and preserves worktrees when dirty/commit inspection is unknown. These are useful semantics. CodexHost reuse is licence/architecture conditional; Hermes's in-memory one-hour registry and silent isolation fallback cannot supply Neokod durable ownership. See [their source and issue sections](competitor-tier-a-evidence-2026-10-04.md#codexhost).

[CodexHost #319](https://github.com/BytePioneer-AI/codex-host/issues/319) reports the first child events lost because provisional and canonical IDs disagree. [#431](https://github.com/BytePioneer-AI/codex-host/issues/431) is explicitly source analysis of reconnect allowing duplicate native-session writers, not an executed corruption test. Its local ownership lesson is valid even though SSH infrastructure is excluded. [Hermes #42176](https://github.com/NousResearch/hermes-agent/issues/42176) corrects an initial fixed claim: the merged change only addressed TUI, not the desktop cancellation route. Test the actual local caller before declaring a bug solved.

### Superset and Oh My Pi

Superset bounds/coalesces refresh work per workspace and fences delayed sweeps against a new session binding. Its timeout-based assumption that unreachable PTYs died should be rejected. Oh My Pi anchors context estimates to usable observed provider usage, invalidates stale anchors after rewriting and records process start identity for worktree ownership. Missing owner markers and PID-only fallbacks cannot authorise Neokod cleanup. See [the detailed sections](competitor-tier-a-evidence-2026-10-04.md#superset).

Build Neokod equivalents of bounded refresh and usage evidence in its existing shared projections. [Superset #8031](https://github.com/superset-sh/superset/issues/8031) has a meaningful correction: its own reported average API share was about 15%, not the main drain, and actual queried scope differs from the initial description. [OMP #14287](https://github.com/can1357/oh-my-pi/issues/14287) has collaborator reproduction of killed processes represented as exit zero. [#14288](https://github.com/can1357/oh-my-pi/issues/14288) confirms different warm/cold replay payloads. Validation and replay must retain the real terminal reason and provider payload contract. Competitor timings are not Neokod measurements; Superset ELv2 also rules out treating this as an unrestricted code-copy exercise.

### Traycer and Conductor

Traycer's public protocol distinguishes reference, read and send authority; its public client wrappers compose stream and transport lifetime, and its recovery governor treats uncertain process liveness conservatively. Its private Host prevents tracing actual provider execution/delivery. Conductor's official local workspace docs explain parallel task branches and the difference between separate landable work and review/testing in a shared checkout. Only Conductor release notes/issues are public in the identified repository. See [Traycer detail](competitor-tier-a-evidence-2026-10-04.md#traycer) and [Conductor detail](competitor-tier-sb-evidence-2026-10-04.md#conductor).

[Traycer #2243](https://github.com/traycerai/traycer/issues/2243) reports accepted late follow-ups not delivered; [#2254](https://github.com/traycerai/traycer/issues/2254) includes socket-resource measurements, but linked merged launchd/sign-in fixes do not prove provider-stream draining repaired. [Conductor #27](https://github.com/meltylabs/conductor-releases/issues/27) reports an unanswerable pending question after an idle process sweep; [#21](https://github.com/meltylabs/conductor-releases/issues/21) reports overnight work lost on restart. Use these as focused lifecycle/retention acceptance cases, not confirmed current universal defects. Do not infer private backend correctness from marketing or public UI.

### OpenCodeX and bb

OpenCodeX preserves execution uncertainty when deciding retries/failover, bounds retained stream queues and diagnoses malformed tool shapes without recording argument values. Its API routing is a different product layer from managed chat orchestration. bb exposes verified runtime capabilities, checks busy siblings before shared-process recovery, rejects foreign managed workspace paths and persists queue claims. Its unknown-policy-to-full default is unsuitable here. See [OpenCodeX and bb source/issue details](competitor-tier-sb-evidence-2026-10-04.md#opencodex).

Reuse Neokod provider capability and stop-result contracts; do not automatically hop providers after possible execution. [bb #4797](https://github.com/get-bb/bb/issues/4797) reports stale ACP permissions on follow-ups/steers, and [#4424](https://github.com/get-bb/bb/issues/4424) has project confirmation that child notices omit who initiated the turn. [#1706](https://github.com/get-bb/bb/issues/1706) is narrower than its title: maintainers partly reproduced hidden claims and missing delivery receipts, without establishing permanent dropped work. This supports explicit accepted/claimed/delivered/unknown states rather than alleging universal data loss.

### Pi, HarnessRouter and Maestri

Pi keeps session facts and branch/context lineage distinct and separates steering, follow-up and compaction semantics. Its optional subagent example supplies finite bounds but is not a built-in governed scheduler; its core permission stance cannot replace Neokod policy. HarnessRouter reserves semantic request identity and uses SQLite CAS, yet its observe/fail-open lease mode admits work without exclusive ownership when storage fails. Its recovery copy can fail while live write still succeeds. Maestri official docs offer explicit peer connections and optional platform-specific copy-on-write floors, but documented response monitoring depends on which agent is selected. Source/tracker for Maestri remains unidentified. See [the detailed source and official-doc sections](competitor-tier-sb-evidence-2026-10-04.md#pi).

Adopt typed queue semantics, cycle detection, canonical receipts and visible degraded recovery. Reject focus-dependent result delivery and fail-open writer claims. [Pi #10411](https://github.com/earendil-works/pi/issues/10411) reports durable mutual-wait deadlock; [#10299](https://github.com/earendil-works/pi/issues/10299) reports malformed tool calls poisoning history. [HarnessRouter #375](https://github.com/HarnessRouter/harnessrouter/issues/375) is a collaborator report of endpoint identity leaking across provider switch. Those are concrete conformance cases. CoW acceleration is conditional on measured platform support, exclusions and recovery; it is not a reason to copy `.env` or assume worktree isolation is a security sandbox.

### Most useful source patterns

1. **Shared GitHub read admission, #1484, merged 2 October.** [The read gate](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/git/githubReadGate.ts) uses six active slots and shares a rate-limit pause across participating reads. It checks the pause again after acquiring a slot, preventing already-queued reads bypassing a new pause. Certain reads and mutations deliberately bypass it; pending waiter count is not proved bounded. Neokod GitHub source-control and Symphony tracker reads could share a credential-scoped budget while preserving mutation priority and fresh merge evidence. Measure call counts/latency first. This is a credible near-term candidate, not a claim all Synara GitHub calls are centrally limited.
2. **Replay-safe message chunks, #1097, merged 10 September.** [Current chunk storage](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/persistence/messageTextChunks.ts) appends event-sequenced text in transactions, suppresses applied-event replay and reconstructs ordered text including unusual Unicode. It avoids rewriting growing prefixes. Neokod's current delta projection rereads/concatenates/upserts the entire message. First compare the smaller T3 SQL-append design; adopt a chunk schema only if migration, reconstruction/compaction and equivalent workloads justify it. No local speed or memory gain has been measured.
3. **Startup ordering and journal ownership, #580/#1115/#1307, merged August–September.** [Startup wiring](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/effectServer.ts) starts journal replay before stale-turn settlement and later background reactors. [Turn reconciliation](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/orchestration/startupTurnReconciliation.ts) uses normal domain terminal/interaction closure. Neokod already has runtime-item closure/reconciliation; verify ordering and one persistence owner rather than duplicate that policy. A blocked journal page can yield before the full replay fence and retry later: test a persisted terminal behind a blocked earlier page before claiming the startup order prevents false interruption. Provider state lost in memory is not evidence every detached OS process died. Thread-scoped high-water replay is a reference for the existing capped replay/gap snapshot path.
4. **Process signal identity, #1270, merged 19 September.** [Process-tree controller](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/platform/processTreeController.ts) validates roots, captures descendants and rechecks identity before delayed signals. It preserves incomplete inventory. This is narrower than a universal spawn registry/root incarnation fence; a separate #1267 proposal remained unmerged. Pair the local immediate process-group guard with isolated platform proof before designing a full durable process ledger.
5. **Durable Hub work, #1490, merged 2 October.** [Service](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/projectAgent/hubWorkService.ts) and [repository](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/persistence/Layers/HubWorkRepository.ts) combine request fingerprint/idempotence, durable records, revision/claim fencing and bounded worker intent. [Source-message admission](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/agentGateway/hubWorkSource.ts) accepts only durable human dispatch messages from the current source turn, not arbitrary agent-authored text claiming human permission. [Lifecycle](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/projectAgent/hubWorkLifecycle.ts) waits for current result evidence and can retain a worker slot while a cancelled record still has a busy worker. These are valuable source/result/ownership lessons. Groups/Hubs are explicitly [beta gated](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/projectAgent/groupsBetaGate.ts); merged code is not stable feature availability. Keep Neokod's existing authoritative Code/Symphony attempts, with one shared delegation request/result link rather than mirrored Hub attempts.
6. **Same logical thread, fresh target provider, #1494, merged 3 October.** [The handoff reactor](https://github.com/Emanuele-web04/synara/blob/5f2ee77ae9fc60993db47e81419c1171a99a5c32/apps/server/src/orchestration/Layers/ProviderCommandReactor.ts) refuses incompatible live background work, clears the source resume cursor, starts the target fresh, registers bounded transcript bootstrap for the next turn and records outcome. Failure returns selection and a fresh source bootstrap because the old cursor was already cleared. `bootstrapStatus: completed` is written after target startup, before next-turn context consumption; it does not prove the target received the briefing. This supports keeping handoff in the visible chat, but native continuity, permissions and tool/approval transfer must be disclosed separately.
7. **Other selected references.** #613 queued promotion, #764 desktop/process resource work and #1332 persistent model catalogue caching merit bounded caller/expiry/identity review. ### What I would investigate first

1. **Streaming and input responsiveness.** The current Markdown path re-highlights a changing code block and parses the full text while streaming. Profile that path with a growing fence and a large completed prefix; preserve sanitisation, selected text, grammar state, non-append edits and completion. Measure synchronous work, long frames and input-to-paint latency. The settled cache already exists and does not solve this streaming cost.
2. **Terminal bounds and consumer pressure.** The current server history cap is line-based and persisted history is read before capping. Add byte/tail-loading correctness to the plan before tuning rendering. Separately measure parser batches, output acknowledgement, transport queues and hidden addons with one stalled reader. Hiding a pane must neither stop PTY processing nor discard authoritative terminal results.
3. **Lifetime of unused data and background work.** Neokod retains live thread streams for a five-minute idle TTL, while cache persistence uses a 500 ms debounce. Measure stream ownership, encoding/write cost and retained warm data separately. Reuse codecs where they are rebuilt; pause optional presentation clocks and polls while hidden, with one fresh update on return. Agent work and result delivery remain server-owned.
4. **Large change sets and filesystem churn.** Measure the existing diff-worker queue and visible sections, including one enormous file, rather than add a worker pool. Profile native index/watcher lifetime on focus/branch changes and generated trees. Ownership, overflow recovery, cancellations and stale generations matter alongside watch counts.
5. **Search and navigation.** Add deliberate project-scoped conversation/snippet search only if wanted, through shared query ownership and stable message/sequence anchors. Current path search already has a native index. Measure cold/warm results, index completeness and server responsiveness separately; moving SQL to a worker cannot be called a general speedup if cold latency regresses.
6. **Packaged startup and resource use.** Time compile/import, database/replay, listen-ready, renderer content and provider discovery separately. Measure the complete process tree at idle, during a fixed task and after settling. Physical RAM, owned-cache estimates and parent-process RSS are different budgets. Native platform and energy claims need actual packaged evidence.

Broader product improvements belong beside those measurements: native work without a connected tracker; effective model/mode capability and configuration provenance; precise review/evidence navigation; stable drafts and paste identity; event-specific notifications; and optional, inspectable project facts linked to their source. These should fit ordinary chat and existing modules. Synara's memory scorer lacks demonstrated retrieval superiority, so a small curated-note/search comparison comes before any new subsystem.

### Measurement gates before selecting a performance change

Freeze the candidate's local source/build, machine/OS/runtime, copied dataset, cache state, workload and budgets in the existing plan before a comparison. Use matched baseline/candidate runs and distinguish cold from warm. Record input/result latency, long tasks, actual process-tree RSS/heap, owned/queued bytes, requests/IO and resource counts relevant to that change. Appendix fixtures and improvement thresholds are proposals for a future implementation plan, not tests executed here or automatic new completion requirements.

Every selected change must preserve the declared correctness contracts: zero cross-scope/stale publication, no lost output, no false terminal result, no extra provider launch and no second workspace writer. Measure the primary bottleneck rather than importing a source timer or source budget as an optimum. If the baseline is unstable, improve attribution first.
