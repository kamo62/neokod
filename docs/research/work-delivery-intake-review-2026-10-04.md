# Chat intake across work-delivery applications

Source assessment: 4 October 2026, against the current Neokod checkout, including its pre-existing uncommitted Symphony work. This is a proposed design and a capability assessment. No tracker request or worker was dispatched. The [canonical plan](../../.plans/20-orchestration-direction.md) owns execution status; this document does not introduce another work tracker.

## Product direction

“Send to Symphony” should work with the delivery application the developer already uses. Jira is one example. Linear, GitHub Issues, GitHub Projects, Azure DevOps Boards, GitLab and Asana already have registered adapters in the local source. The target is an extensible intake path for other delivery applications too, with each integration declaring and proving the operations it supports. A generic label must not imply universal working support.

The normal conversation remains the place to discuss the task, delegate research, refine the acceptance criteria and receive the outcome. The explicit handoff chooses an existing connection and Symphony project, resolves a task reference, checks that project's policy and returns the linked work item. The board remains available for project-wide dispatch, review and delivery.

Keep delivery and source control independent. A Linear, Jira, Asana or Azure Boards task can concern a repository hosted elsewhere. The task application's adapter identifies and reads the work; the repository's source-control integration supplies branches, review and PR operations. Neither connection establishes the other's capability.

## What exists, and what does not

The [registry](../../apps/server/src/symphony/Trackers/Registry.ts) constructs all seven adapters. The [tracker contract](../../apps/server/src/symphony/Trackers/Adapter.ts) exposes configuration validation, candidate listing, refresh by opaque dispatch ID, single-item lookup, credential-environment exclusions, a probe and an adapter profile. Its scheduler callbacks are reads. Optional provider-native tools can supply mutations; there is no common host write-back interface or guarantee that every agent can update every tracker.

The [current handoff](../../apps/server/src/symphony/HandoffService.ts) validates a source thread, finds an attached workflow and creates a random manual work item. It does not resolve an external task reference or durably record the originating chat/message for that item. Jira's existing `getIssue` happens to pass its argument to an API that accepts keys or IDs; Linear's equivalent query filters native UUIDs. That difference is a reason to put reference resolution in the adapter, not infer universal key support from `getIssue`.

The [work-item repository](../../apps/server/src/symphony/Persistence/Layers/WorkItemRepository.ts) already deduplicates `(project_id, tracker_kind, tracker_issue_id)` and has fenced claims. Preserve that boundary. A reference resolver must return the same canonical identity that polling uses. It must also record the configured connection/scope used for admission, so changing an endpoint or project configuration cannot silently reinterpret an old accepted request. The current repository key does not itself include a connection ID or external endpoint; verify project/configuration binding before deciding whether a schema extension is necessary.

## Smallest useful shared intake

Extend the existing tracker boundary with reference resolution and explicit evidence about supported operations when implementing this flow. A resolver accepts a task reference in a **selected, server-owned connection and scope** and returns canonical native identity, display reference, URL, current issue data and checked scope. Return ambiguous, unavailable, out-of-scope and unsupported outcomes distinctly. Do not create a manual duplicate to conceal failed resolution. URLs are references to parse against the configured service, not arbitrary destinations for credentialed requests.

Use the existing eligibility calculation for active/terminal states, labels and dispatchability, plus the existing scheduler's pause/concurrency/claim and workflow policy. Adapter-specific dependencies need capability/completeness evidence: unavailable, truncated and known-empty must not collapse to the same fact. Only require a dependency check where the selected workflow relies on it; disclose unsupported policy rather than pretend every adapter implements Jira semantics. Refresh immediately before admission or use a revision-conditioned check where available.

Persist a bounded delegation request containing source chat/message, request ID and semantic fingerprint, selected connection/project/scope and canonical native target. Link it to the existing work item and attempt/evidence; persist result-delivery acknowledgement back to the source conversation. Code and Symphony keep their own authoritative attempt states. A retried reference, polling race or second chat targeting the same item can add a request/subscriber link while reusing one work item; it must not silently create another active writer.

Use a separate worktree or the existing exclusive ownership-transfer mechanism. Stopping the chat, cancelling the delivery task and detaching a subscriber are different actions. Respect the selected workflow's attempt/retry/review/merge policy. Tracker write-back, comments and state transitions need their own capability and authority; read authentication alone grants none of them. Current Symphony execution remains Codex-only, separate from multiple configured review providers.

Apply this same small contract to future delivery apps. Add an adapter only with demonstrated native identity, scoped reads, reference resolution, state mapping, pagination/completeness, error/rate semantics and credential isolation. Add write operations only when required and actually supported. Reuse the present registry and contracts; an integration marketplace or generic plugin framework is not necessary to make these seven apps work.

## Finite acceptance criteria

1. For each supported adapter, a display reference/URL and its native ID resolve to the same polled work item in the configured scope. Identical short IDs on different hosts/projects remain distinct. GitHub Project items retain their selected membership, rather than collapsing into repository issue identity.
2. Lookup refuses a valid item from the wrong Jira project, GitHub Project or Azure project. Ambiguous short references require selection; revoked credentials and unsupported item types return honest outcomes. Custom Azure states and Asana tasks without sections do not silently dispatch under guessed semantics.
3. A chat request, retried request and simultaneous scheduler poll admit at most one active claim. A second chat receives the existing link or an explicit already-running outcome. Configuration changes cannot reinterpret a persisted target.
4. Crash after acceptance, before/after launch and before/after result delivery preserves the request and eventually returns one acknowledged outcome. Unacknowledged external sends remain unknown unless provider correlation proves execution. No browser-mounted watcher owns delivery.
5. Complete, truncated and unsupported dependency evidence have distinct policy results. Frozen fixtures cover Linear relation overflow, GitHub Projects draft/PR cards, Azure state mappings and large candidate inventories.
6. Measure polling/lookup calls, result latency and rate-limit recovery per configured credential/scope. Preserve fresh evidence before mutation/merge; deduplicating reads must not cache stale authority. Prove cancellation and workspace recovery without an orphan or second writer.
7. Run one controlled tracker-to-PR flow for each advertised live integration, retaining canonical task, branch, attempt, validation/evidence and PR linkage. Until then label source/fixture support separately from live proof.

No runtime performance gains or end-to-end support are claimed by this assessment. It defines the small changes and proof needed to deliver the user's cross-application workflow.
