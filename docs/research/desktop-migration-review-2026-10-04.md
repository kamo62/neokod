# Neokod desktop runtime migration review

Source review captured 4 October 2026. Recommendation: investigate Tauri 2 through one bounded desktop proof while retaining the current server and React client. Keep Electron as the delivery baseline until that proof establishes compatibility, packaged operation, recovery and a worthwhile resource improvement. A licence concern alone does not justify a shell rewrite on the evidence available.

This review is read-only. It inspected current Neokod at `80334a4c8a6badd9a0014bbc34af4bcb346c3cff` plus the working tree, the frozen T3 pins used by the existing research, and current primary framework documentation/repositories. No framework was installed, no app was launched, no build or provider/tracker operation was run, and no repository file was edited. Source evidence establishes migration seams and obstacles; it does not establish performance, provider parity, installability or security of a finished replacement. [Source and status manifest](/Users/kamogelo/Code/t3code/docs/research/evidence/desktop-migration-source-manifest.json) records captures, hashes, pins and unavailable URLs.

## Decision and limits

Tauri 2 is the first candidate because its existing desktop command, sidecar and distribution facilities let Neokod retain the server independently of the shell. Select a stable 2.x release and pin plugins independently. The current release list contains [Tauri 2.12.1](https://github.com/tauri-apps/tauri/releases/tag/tauri-v2.12.1), published 30 September. The repository's generic latest-release endpoint returned `tauri-v3.0.0-alpha.4` despite `prerelease=false`. The tag name and release line must therefore be checked; a generic latest lookup is not an acceptable version selector.

Electrobun deserves a secondary evaluation if remaining in TypeScript is decisive, but the current 2.x runtime/toolchain and target matrix add specific migration costs. Wails 3 is a lower-priority Go alternative; its current documentation calls it beta. Rewriting the application with native widgets is a separate product and engineering decision. None of these three shells automatically turns the React conversation, terminal, diff or preview UI into native controls.

Do not combine a desktop migration with a server rewrite, a wholesale Bun conversion, UI redesign, upstream UI port, or provider expansion. Retaining the server preserves its contracts, persistence, orchestration and CLI adapters, but packaging them under a new runtime still needs proof. Keep normal chat and optional work-delivery handoff as the product model already selected; framework capabilities do not dictate a mode switch.

## Preview is the major functional obstacle

The app's main renderer uses `contextIsolation=true`, `nodeIntegration=false`, `sandbox=true`, and enables Electron webview tags. The guest preview deliberately has a separate policy: sandbox enabled, Node integration off, context isolation off for the picker preload. [DesktopWindow.ts](/Users/kamogelo/Code/t3code/apps/desktop/src/window/DesktopWindow.ts:292) gates attached webviews by the preview partition. This is not a claim of universal security; it is the actual policy to preserve or improve.

[ElectronBrowserHost.tsx](/Users/kamogelo/Code/t3code/apps/web/src/browser/ElectronBrowserHost.tsx:17) mounts [HostedBrowserWebview](/Users/kamogelo/Code/t3code/apps/web/src/browser/HostedBrowserWebview.tsx:1) for the active preview sessions. [PreviewManager](/Users/kamogelo/Code/t3code/apps/desktop/src/preview/Manager.ts:701) uses Electron WebContents/debugger commands for screencast frames, input and browser control; registration verifies the guest belongs to the main window. [PlaywrightInjectedRuntime.ts](/Users/kamogelo/Code/t3code/apps/desktop/src/preview/PlaywrightInjectedRuntime.ts:18) explicitly selects Chromium and reads injected code from playwright-core. [BrowserSession.ts](/Users/kamogelo/Code/t3code/apps/desktop/src/preview/BrowserSession.ts:12) provides scoped persistent browser partitions, cookie/cache controls and sessions.

A WKWebView or WebKitGTK page is not an Electron WebContents and does not expose this CDP path. Windows WebView2 being Chromium-based also does not establish compatibility with these Electron APIs. Loading the React UI in a replacement shell can succeed while preview automation, recording, annotation, focus, selection and cookie separation fail.

Decide preview requirements before committing to replacement. Options to prove are: implement the required functions against each system WebView; keep a separately isolated Chromium browser process for the preview; or explicitly defer preview functions in an opt-in prototype. The second retains Chromium's download/process cost and requires a new ownership/control boundary. It may still improve the main app, but the total benefit must include that browser. Removing preview from a benchmark without disclosing the feature loss would invalidate the comparison. Electrobun's embedded native webview element and optional CEF are interesting seams, not demonstrated substitutes for Neokod's CDP, picker and Playwright implementation.

## Keep-server design to prove

The proposed Tauri arrangement is a small Rust desktop shell, the existing built React frontend, and the existing Neokod server bundle running under a separately packaged supported Node runtime. Provider CLIs, PTYs, persistence, tracker adapters and orchestration remain server-owned. Native dialog/menu/theme/update/secure-storage operations remain shell-owned. Server events still use the existing connection runtime.

Package Node and the server dependency/resource tree for each target; launch by absolute bundle path, with the correct cwd, imported shell environment, canonical Neokod home and private bootstrap. Replace `ELECTRON_RUN_AS_NODE` and ASAR paths. Tauri's [external-binary mechanism](https://v2.tauri.app/develop/sidecar/) supports target-specific binaries, process IO and narrowly scoped spawn permissions. It does not package JavaScript dependency graphs or prove that node-pty/SQLite/provider runtime files work. FD 3 bootstrap is a Neokod contract, so prove handle inheritance on each platform or deliberately use the existing stdin delivery form with a supported server argument. Never place bearer credentials in the command line, stable config or logs to simplify launch.

The first primary-only proof may supervise the server directly from Rust. Production must additionally preserve the existing readiness/restart/quit semantics and WSL pool. If translating those into Rust would duplicate a large amount of TS policy, evaluate retaining the existing Node desktop-host lifecycle logic behind focused native adapters instead. That adds a host process and must be measured. The review does not choose an extra generic host framework before this dependency is demonstrated.

Keep `DesktopBridge`'s meaningful operations as a compatibility facade initially, but make backend topology a resolved initial snapshot with updates. Avoid pretending an async native invoke is synchronous. Replace Electron-specific preview fields locally when preview design is chosen. Keep package contracts schema-only and avoid platform types leaking into the server. This follows the current state/evidence architecture rather than inventing a parallel state model.

## Security and update proof boundaries

Current desktop configuration generates 24 random bytes for each resolved primary start and delivers `loopbackAuthToken` in bootstrap. Renderer bootstrap exposes the credential through the trusted bridge. WSL similarly receives its bearer. [WslBearerAuth.ts](/Users/kamogelo/Code/t3code/apps/server/src/transport/WslBearerAuth.ts:88) enforces configured credentials and single-use expiring WebSocket tickets independently of strict Host/Origin validation. This desktop path must not be described as universally unauthenticated.

Separately, [CLI config.ts](/Users/kamogelo/Code/t3code/apps/server/src/cli/config.ts:355) defaults `strictTransport` to false, and ordinary web-mode token minting is conditional on that flag. [LocalTransportAuth.ts](/Users/kamogelo/Code/t3code/apps/server/src/transport/LocalTransportAuth.ts:98) returns early when it is false. The README's unconditional Host/Origin/token description is stale for this current source. A new shell should preserve the desktop credential and explicitly choose strict transport with the replacement renderer's exact origin. This is a proposed launch policy change to verify, not proof of a running setting or exploit.

Tauri [capabilities](https://v2.tauri.app/security/capabilities/) can narrow native plugin access by window/WebView and scope. Custom commands registered through `invoke_handler` are available to all app windows/WebViews by default unless configured through the app manifest. Configure those commands deliberately; “Tauri permissions” is not sufficient proof. These controls do not restrict Neokod's independent HTTP/WebSocket RPC after a client obtains its backend credential. Broad authenticated RPC authority and agent-aware admission remain server concerns.

Keep untrusted previews out of the privileged bridge and away from the primary token. Prove navigation/new-window/file URL handling, external-link validation, initialisation scripts, event source identity and capability isolation. The current IPC registration decodes payloads but ignores the Electron invoke event; payload validation does not independently prove caller identity. This is a migration boundary to specify, not an assertion that arbitrary external pages currently reach the bridge. Review the new CSP against actual workers, blob assets, preview origins and local/WSL endpoints. Prefer bundled UI assets/custom protocol to exposing privileged frontend assets over a general localhost plugin; the retained backend API listener is a separate requirement.

Tauri's [updater](https://v2.tauri.app/plugin/updater/) requires signed update artifacts; this verification cannot be disabled. Its update signatures are separate from platform code signing, notarisation and the signing of nested Node/native libraries. Use the [macOS](https://v2.tauri.app/distribute/sign/macos/) and [Windows](https://v2.tauri.app/distribute/sign/windows/) distribution paths, and test child cleanup before installer replacement. Retaining electron-updater feeds does not automatically update an Electron installation into a Tauri artifact. Plan a reviewed handoff installer/bridge release and a rollback path.

Electrobun's [architecture](https://framework.blackboard.sh/electrobun/guides/architecture/overview/) describes transactional replacement and rollback, but its [updates page](https://framework.blackboard.sh/electrobun/guides/updates/) explicitly distinguishes the routing hash from content authentication. Its [signing guide](https://framework.blackboard.sh/electrobun/guides/code-signing/) currently supports macOS signing/notarisation and says Windows signing is outside Hutch's packaging pipeline. Do not equate verified extraction or a matching hash with publisher authentication. A Windows signing and authenticated-update path is an explicit Neokod release gate. Wails advertises an updater with signature verification in current docs; its beta implementation and Neokod's packaging still require separate verification.

## Finite acceptance gates

These are proposed gates for an authorised implementation phase, not measurements already obtained. Freeze the exact targets, fixture corpus, requirements and thresholds before collecting results.

1. Baseline and inventory: capture one reproducible Electron artifact per supported target, client/server revision, dependency/runtime versions and child-process tree. Inventory bridge callers, bundled native files, paths, licence notices, preview requirements and persisted stores. Establish whether resource pressure comes from the renderer, previews, server or agents. Stop if there is no material shell-attributable opportunity.
2. Primary server proof: package a pinned supported Node runtime and unchanged server bundle; prove SQLite APIs, PTY load/open/resize/exit, search native files, CLI environment/path discovery, private bootstrap, readiness, restarts and descendant cleanup. Use controlled local fixtures first. No feature or provider parity claim from successful spawn alone.
3. WebView and bridge proof: replay the same conversation/history/terminal/diff/search workload on WKWebView, WebView2 and the selected Linux WebKitGTK. Exercise keyboard/IME, clipboard, selections, focus, virtual lists, resize, workers, uploads, drag/drop, schemes, menus and initial topology. Test corrupted/unavailable settings storage and exact startup ordering. Keep the same server contracts and payloads.
4. Preview decision: exercise navigation, partitions/cookies, devtools policy, picking/annotations, screenshots, recording and automation on the chosen replacement. Either preserve the agreed requirements or document an explicitly accepted prototype limitation. A mandatory feature without a proved implementation blocks migration.
5. Windows/WSL and storage proof: exercise both native and WSL backends, WSL-only and dual mode, unavailable distro/ports/preflight, fallback and restart. Preserve distinct Linux/Windows homes and databases. Copy existing data into a test migration, verify server history/settings, and specify origin-bound browser state plus encrypted catalogue handling. Never have Electron and the replacement write the same SQLite state simultaneously during comparison. Repeated migration and rollback must not discard or duplicate state.
6. Security and distribution proof: negative tests for absent/wrong credentials, replayed/expired tickets, prohibited renderer origins when strict mode is enabled, untrusted preview command access, malformed native messages and dangerous URLs. Prove package install, offline start, nested code signing, macOS notarisation/Gatekeeper, Windows signing, Linux dependencies, updater authenticity, interrupted downloads/replacement and rollback. Testing a dev build is insufficient.
7. Whole-application comparison: on each OS/architecture, compare matched release artifacts and identical data using 20 controlled cold starts, 50 warm starts, a 30-minute idle period, a fixed stream/history workload, and preview-off plus preview-on cases. Record installer and installed bytes including sidecars; launch-to-visible, launch-to-server-ready and launch-to-interactive separately; median/p95 and worst observed times; renderer responsiveness; total process-tree memory/CPU; handles/processes; server throughput and recovery. Use platform-appropriate memory metrics and compare within each OS, not unlike macOS/Linux/Windows accounting totals. Keep measurement commands, raw samples and machine/runtime context.

Suggested economic gate, to approve before the experiment: at least a 20% reduction in total steady-state application process-tree memory or installed application bytes on the primary target, with no greater than 10% regression in median startup-to-interactive and no material loss of responsiveness, reliability, features or supported targets. These are proposed decision thresholds, not framework performance claims. Include optional Chromium previews and the packaged Node/runtime files in totals. A tiny empty-shell number is not a Neokod result. A server-bound bottleneck, agent-heavy workload or retained Chromium preview could produce little total improvement even if the shell becomes smaller.

Stop after one primary candidate completes the bounded proof or hits a decisive compatibility gate. Evaluate Electrobun only when the failed gate or maintenance comparison gives a concrete reason. Do not build three production replacements to choose one. A successful Tauri prototype authorises no deployment; production replacement remains conditional on the full supported-target evidence and distribution handoff.

## Outstanding evidence
