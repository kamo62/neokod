## T3 Code: six additional items

### T1. Incremental streaming rendering and truthful warm navigation

**Status and evidence.** [#11193](https://github.com/pingdotgg/t3code/pull/11193), [#11196](https://github.com/pingdotgg/t3code/pull/11196), [#11198](https://github.com/pingdotgg/t3code/pull/11198) and [#11169](https://github.com/pingdotgg/t3code/pull/11169) were merged on 11 September. Frozen `markdown-incremental.ts:34–85` caches a completed top-level fence prefix, reparses the suffix and clones pristine prefix nodes before mutable transforms. `lib/incrementalHighlighting.ts:13–73` resumes grammar state after completed lines and invalidates non-append changes. `HighlightedCodeLines.tsx` preserves completed-line DOM. The cache is renderer-owned and has fallback paths; this is a correctness-sensitive parsing strategy, not simply memoising the full response.

**Measurement boundary.** The PRs report alternating production Chromium fixtures: parser median 21.5→17.4 ms, incremental highlighter 170.8→120.3 ms, and stable-line layer 118.9→103.6 ms. These are successive parent comparisons, so do not add percentages. The heavy growing-code workload remained slower than a smooth frame budget. #11169 separately reports six counterbalanced rounds, cached switches 252.475→178.500 ms and sampled blank switches 48/48→0/48; remembered prior-thread content is paint-only until the requested thread is ready. These are client fixture results, not provider throughput or Neokod timings.

**Local caller and recommendation.** Neokod [ChatMarkdown.tsx](/Users/kamogelo/Code/t3code/apps/web/src/components/ChatMarkdown.tsx:640) bypasses completed HTML caching while streaming, calls `codeToHtml` for each changing code value at line 688, and passes the full text through ReactMarkdown at line 1546. Its own sanitisation, file links, tables, skills and clipboard behaviour must remain authoritative. Study incremental parsing/highlighting against those components. Neokod already virtualises its message list; #11169 is useful for the separate navigation ownership invariant. Any temporary retained paint must disable actions and never identify previous content as the destination thread.

**Finite gate.** Compare existing and candidate production rendering in six alternating rounds for completed-code-plus-prose and a 200-line growing code fence. Record synchronous update median/p95, long frames, retained heap and selected-text/DOM survival. Check non-append edit, CRLF, references, footnotes, embedded grammars, sanitisation and completion. Separately perform 20 cached switches among three large threads and require correct destination/action identity on every switch. Profile first; no whole-renderer replacement or upstream layout port follows from these measurements.

### T2. Bound terminal history and stop hidden presentation work without stopping execution

**Status and evidence.** [#9748](https://github.com/pingdotgg/t3code/pull/9748) and [#9718](https://github.com/pingdotgg/t3code/pull/9718) were merged on 4 September; [#13686](https://github.com/pingdotgg/t3code/pull/13686) on 26 September. **Measurement boundary.** #9748 reports synthetic correctness and cost checks: 1,000 1 KiB appends 0.15→0.35 ms, and one 12 MiB Unicode append 4.68→13.68 ms. Bounds add work; they are a reliability tradeoff, not a universal speedup. #9718 provides focused real-core headless tests, not a browser CPU comparison. #13686 provides source reasoning and a manual atom-count procedure, not an independently measured memory reduction.

**Local caller and recommendation.** Neokod [terminal/Manager.ts](/Users/kamogelo/Code/t3code/apps/server/src/terminal/Manager.ts:855) retains a string, splits it to apply a line cap and reads full persisted files before capping them at lines 1429 and 1468. [ChatView.tsx](/Users/kamogelo/Code/t3code/apps/web/src/components/ChatView.tsx:520) calls `useThread` in the mounted terminal surface; hiding the wrapper at line 807 does not itself establish subscription release. Adopt byte bounds and metadata-only hidden ownership deliberately. Use xterm's own lifecycle for hidden painting; do not transplant Ghostty internals or pause PTY parsing/child execution.

**Finite gate.** Exercise a long line above the selected byte cap, Unicode split boundaries, a legacy oversized history file and attach/reconnect sequence parity. Measure peak server/renderer memory and append cost for one busy terminal plus nine hidden terminals. Verify terminal replies, reveal/refit, selection, archived/draft metadata fallback and uninterrupted live output. A retained byte bound must also govern disk loading and attach payloads, not only the final rendered buffer.

## Generic work-delivery intake: concrete design implications

The intake must support manual work and configured tracker kinds uniformly. A lightweight reference attached to chat and a request to execute that work are different user intents. “Discuss Linear ENG-123” can add context; “Send Linear ENG-123 to Symphony” explicitly requests admission. The default agent remains in normal chat. A bounded briefing plus a task/result link can delegate to Symphony's current Codex executor; its separate runtime must not be represented as seamless continuation of whichever provider handled the source chat.

Reuse the existing `NormalizedIssue` and adapter profile instead of introducing a second issue model. Resolve `(integration/project scope, tracker kind, URL or display locator)` server-side into opaque canonical ID plus `nativeRef`. Keep display identifiers for the user. For Linear that is UUID versus `ENG-123`; Azure Boards uses work-item ID with organisation/project scope; GitHub Projects uses project item ID and must retain the linked issue identity. Current local draft/PR cards are unsupported and need an explicit capability decision. A repository issue number cannot stand in for a project-item ID. Resolve ambiguity visibly; do not guess across integrations.

Record an immutable context snapshot with source URI, canonical ID, display identifier, revision/fetched time, scope and selected acceptance criteria. Tracker descriptions and comments are task data. The server remains responsible for permission/workspace/provider limits, dispatchability and prerequisites. An adapter's successful read does not establish writeback, and authentication does not certify every listed tool capability. Keep provider/tracker secrets outside the briefing. Return actual unavailable/partial capabilities through the existing profile/error contract.

Admission should use a stable request identity and canonical work key so repeated chat sends, retries and adapter polls converge on the same accepted work rather than creating a manual duplicate. Preserve request fingerprint, originating chat/message, accepted work/attempt identity, workspace owner and result receipt. Existing tracker work and a new manual task must be distinguishable; the current generated-ID delegate path should remain a manual path, not pretend to resolve an external item. Common ownership and cancellation semantics apply whether the executor is a child in chat or Symphony.

Tracker-specific writes stay behind each provider's supported operations and the user's authorised intent. Generic intake must not imply automatically updating state, publishing a PR or closing a ticket. The product should let users inspect what was accepted, why a task is blocked, where it is running and which result satisfies the originating request, from the normal chat surface. UI design remains Neokod-owned.

## Finite recommendation and proof boundary

The most immediate source matches are incremental streaming work, byte-bounded terminal history, terminal metadata subscriptions, codec reuse, and command-catalogue rendering. Profile these existing callers first. Startup query/compile policies need packaged phase evidence. Search, project memory and generic work intake include deliberate product additions, so establish the specified contracts and bounded fixture comparisons before choosing implementation. Open competitor memory/resource/tracker proposals remain references.
