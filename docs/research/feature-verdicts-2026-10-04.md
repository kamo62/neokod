The required journey is discussion on the laptop, explicit continuation on a server, the right repository/code/context on that server, and progress/results linked back to the originating chat. A remote connection picker alone does not satisfy that journey. Shared multi-user servers are a later scope.

## Decision

T3 leads Neokod in implemented in-chat orchestration and new-run environment selection. Paseo is another strong orchestration reference and explicitly documents cross-host execution. MonoCode is a strong additional reference for integrated own-machine remote sessions and durable request receipts; Orca offers broader supervised cross-host dispatch. Synara is the strongest inspected reference for presenting task context, delivery and children around a central chat. Empryo contributes code intelligence and explicit child briefings, with a material public-v2/private-v3 boundary. Superset and Agent Orchestrator offer different board strengths. Orca has a stronger explicit terminal flow-control design. No evidence establishes one overall winner in speed, recovery, security or reliability.

The model/usage dashboard review below covers all twenty products. T3 is the strongest combined history/limits/environment reference; Oh My Pi leads on deeper local analytics. Agent Orchestrator and OpenCodeX contribute stronger accounting provenance, while Synara, Paseo and bb inform account freshness. Neokod has a genuine historical-usage gap and should retire the unused quota and financial-projection paths as the feature lands.

Choose the best demonstrated mechanism for each Neokod capability. Retain Neokod's existing ownership, evidence, provider and client-runtime machinery where it already solves the problem. New UI remains an independently designed Neokod UI. Remote access is now a deliberate product assessment, rather than being discarded under the earlier local-only filter.

## T3: what its new orchestrator actually gives us

Current selected source was fetched at `b3b6ae2cebbae39a706038911dbb8c85c7120be7`. T3's positive reception is a useful signal to investigate, not measured reliability evidence. Its product lead is real in the inspected paths.

The provider conversation can delegate through MCP. The service validates the active parent, resolves a registered provider/model and records the parent thread/run/node. Deterministic IDs create child threads/task nodes; event and effect persistence provides a durable execution path. Results have delivery and acknowledgement states. No separate coordinator model or mandatory orchestration mode is inherent in this mechanism. [Delegation service](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/server/src/mcp/OrchestratorMcpService.ts#L1369), [child lineage](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/server/src/orchestration-v2/Orchestrator.ts#L6318), [durable effects](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/server/src/orchestration-v2/EffectOutbox.ts#L199).

Machine selection is a separate path. Environment-scoped clients and composer project matching select where new work runs. Populated/active threads lock that environment. Its current delegate target carries provider/model/options, with no `environmentId`; children inherit the parent's project/workspace. Therefore new-run machine selection is established, but automatic cross-machine children or seamless active-session migration are not established by this API. [Composer environment binding](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/web/src/components/ChatView.tsx#L2944), [inherited child workspace](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/server/src/orchestration-v2/SubagentProjection.ts#L42).

T3 supports endpoint, SSH and relay targets. SSH includes remote bootstrap/version checks and a local forward to the remote loopback listener. That is substantially more complete than a pasted URL alone. It is worth comparing to other competitors, rather than adopting its transport wholesale. [Connection types](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/packages/client-runtime/src/connection/model.ts#L9), [SSH implementation](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/packages/ssh/src/tunnel.ts#L1100).

Current issue metadata still marks [plan-mode authority widening](https://github.com/pingdotgg/t3code/issues/15503), [child notices cancelling queued Claude tools](https://github.com/pingdotgg/t3code/issues/15351), [queued/waiting keep-alive](https://github.com/pingdotgg/t3code/issues/15289) and [child usage attribution](https://github.com/pingdotgg/t3code/issues/15429) open. These are qualified reports, not reproduced failures here. Keep their acceptance lessons without dismissing the feature lead.

The inspected [dispatch path](https://github.com/proxysoul/Empryo/blob/28802a4f169abcc378032e0a4774bc162c12a00c/src/core/agents/subagent-tools.ts#L419) waits for dependencies before acquiring concurrency slots, a useful deadlock-avoidance mechanism. [Archive writer](https://github.com/proxysoul/Empryo/blob/28802a4f169abcc378032e0a4774bc162c12a00c/src/core/agents/agent-results.ts#L90).

Workspace coordination also has limits: same-batch code agents can be serialised around shared files, while cross-tab claims warn and proceed. Preserve Neokod's exclusive ownership rather than adopting advisory claims. The local daemon's claim catches flush/close failure, removes its live entry and returns success; that is a recovery warning, not a cross-machine protocol. [Advisory claims](https://github.com/proxysoul/Empryo/blob/28802a4f169abcc378032e0a4774bc162c12a00c/src/core/coordination/tool-wrapper.ts#L33), [local surface claim](https://github.com/proxysoul/Empryo/blob/28802a4f169abcc378032e0a4774bc162c12a00c/src/hearth/daemon.ts#L550).

The distinctive intelligence path is demonstrated in [repo-map](https://github.com/proxysoul/Empryo/blob/28802a4f169abcc378032e0a4774bc162c12a00c/src/core/intelligence/repo-map.ts#L170) and [semantic edit rollback](https://github.com/proxysoul/Empryo/blob/28802a4f169abcc378032e0a4774bc162c12a00c/src/core/intelligence/backends/ts-morph.ts#L1089). This is not a multi-file transaction or a concurrent-writer guarantee. Empryo's published speed/cost comparisons are publisher-run experiments, without a matched Neokod run here; no performance winner follows from them. [Benchmark methodology and caveats](https://empryo.com/benchmarks).

The published desktop preview was viewed on the website. A code map beside chat offers useful task context, but neither that preview nor the private v3 UI warrants ranking it above Neokod across ordinary workflows. Synara remains the more extensively inspected visual reference. Current [workflow documentation](https://empryo.com/docs/agents/workflows), [goal review](https://empryo.com/docs/agents/goal-loop) and [phone boundary](https://empryo.com/docs/surfaces/phone) remain product claims rather than executed acceptance evidence.

## MonoCode: a close own-machine remote reference

Inspected SHA: `271b66ded71e795e0569db77c9bbf599219c8cdc`, committed 4 October 2026 at 10:35:15 UTC. It is a desktop agent-CLI workbench with an experimental remotely owned host runtime and an [MIT licence](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/LICENSE). Its integration is closer to Neokod's proposed desktop workflow than CodexMonitor's global remote-host mode.

| Area           | What MonoCode does better than current Neokod                                                                                                                                          | Boundary                                                                                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Remote setup   | Desktop OpenSSH configuration, host-key checks, a release-matched host package and loopback forward; host sessions own provider processes and history.                                 | Experimental. Providers must already be installed/authenticated remotely. Automatic installation changes service state and is not a required first Neokod slice. |
| Reconnect      | Persisted command ID/payload receipt; retry returns the same acceptance instead of sending another first turn. Host restart marks uncertain work interrupted rather than replaying it. | Acceptance is not provider start or completion.                                                                                                                  |
| Workspace      | Host-side directory/worktree, files and Git views in the normal session interface.                                                                                                     | No working-directory synchronisation. Remote terminals and several local capabilities are absent.                                                                |
| Local operator | A thread-enabled app CLI can create/read/send sessions, with active-turn and project checks. Bounded local orchestration has dependency/scope admission.                               | Remote operator and orchestration are explicitly unimplemented. Explicit child permission overrides need their own ceiling.                                      |
| Handoff        | Local provider switching offers a reviewable recap; deterministic fallback has a 1,800-character brief budget.                                                                         | Does not transfer local HEAD/dirty code or move the current chat to another machine.                                                                             |

The strongest inspected mechanism is [host admission](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/engine.ts#L414). It hashes the parsed command, checks an existing receipt, atomically saves the session mutation and receipt, then starts the effect. Conflicting payload reuse fails. This directly supports Neokod's accepted-versus-started distinction and uncertain-reply recovery. [Effect ordering](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/engine.ts#L690), [receipt conflict](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/store.ts#L238), [restart handling](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/engine.ts#L270).

Per-device credentials are hashed and revocable; server authentication precedes body processing and checks the persisted host identity. Native storage keeps the token outside renderer metadata, accepts HTTPS or loopback HTTP, and uses a restricted file rather than an OS keychain. Credentials still grant the host OS user's authority. [Device credentials](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/store.ts#L277), [server checks](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/server.ts#L200), [native connection storage](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/src-tauri/src/remote.rs#L40).

Its local orchestrator records dispatch before resource creation and bounds workers, tasks and mutating receipts. However, result wakeup marks a result delivered before submitting a lead continuation, with failure callbacks restoring the flag. There is no inspected recipient acknowledgement token; this is not the cross-host result-delivery contract Neokod needs. [Local admission](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/src/features/orchestration/model/orchestration.ts#L1465), [result wakeup](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/src/features/orchestration/model/orchestration.ts#L1980).

The remote transcript uses changed blocks and bounded consistent-revision chunks, a useful network/refresh pattern. Transfer slots retain entire serialised revisions in memory, so per-response caps do not prove bounded total memory or superior performance. [Sync transfer](https://github.com/hardbeat920/monocode/blob/271b66ded71e795e0569db77c9bbf599219c8cdc/host/sync-transfer.ts#L12). ### The user's “throw context to my server” workflow

1. Discuss/plan in a local chat. Select Continue on… and choose a registered execution environment and target checkout/worktree.
2. Review an explicit manifest: task and acceptance criteria, source thread/result provenance, repo remote plus exact commit, selected dirty patch/untracked assets, contextual messages/files, target provider/model and effective authority. Never imply a transcript recap is complete provider-native state.
3. Quiesce the source execution if this is continuation, capture a recovery checkpoint and offer the manifest under a durable handoff ID. The remote host resolves its own credentials and validates repository identity and transfer integrity.
4. Prepare the exact base checkout, apply selected changes, verify the resulting tree and acquire its workspace ownership. Fetch failures, missing commits, conflicts or unavailable providers return actionable refusal/preparation states.
5. The target durably acknowledges preparation. The source records a transfer grant bound to that target, manifest hash and ownership generation; the target accepts it once and creates one attempt/new native session. There is no cross-server SQL transaction. Lost acknowledgement means unknown until reconciled, not permission to launch again elsewhere. Returning execution locally requires target settlement/release and a new grant.
6. Show target-machine progress, approvals, diff, tests and PR evidence through links in the originating chat. Return one acknowledged outcome. Disconnecting the laptop does not implicitly cancel the server job; Stop remains a routed, confirmed action.

Do not automatically copy a live provider home, credentials, ignored files or an entire working directory. Do not auto-commit/push merely to make transfer easier. Selected uncommitted changes can travel as a bounded, hash-verified bundle; fetching an existing committed revision is the simpler first subcase. An unpushed/inaccessible base commit needs explicit transfer or refusal. Remote credentials remain remote.

This design combines environment selection, deliberate context handoff and existing ownership/evidence. It does not require a whole engine rewrite or a hosted Neokod cloud.

### Mechanisms worth taking, and defects worth avoiding

T3 separates history scans from account-limit refresh and lets environments finish independently. Its source fingerprinting avoids repeatedly counting shared files; Cursor account totals deduplicate when the same account is accessible on two machines. It discloses unpriced activity and API-equivalent cost. Preserve these ideas when adding Neokod's machines. Do not sum an account-wide endpoint over machines, and do not treat the arithmetic average of two plans' utilisation as available capacity. Its fork-copy timing rule is useful evidence to investigate, not the durable event identity Neokod should promise. [History service](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/server/src/usage/UsageService.ts#L224), [environment merge](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/packages/shared/src/usageMerge.ts#L195), [pool arithmetic](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/packages/shared/src/usageLimits.ts#L422), [fork parser](https://github.com/pingdotgg/t3code/blob/b3b6ae2cebbae39a706038911dbb8c85c7120be7/apps/server/src/usage/usageTranscripts.ts#L197).

Add one Usage destination with Overview, Limits and Models views. ### Mechanisms worth taking

- **Idempotent dispatch keys with payload comparison.** `request_duplicate` returns the existing worker for the same key and payload, and refuses the same key with different arguments ([architect.rs L1389-L1403](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/architect.rs#L1389-L1403)). This matches Orca and MonoCode, and the W6 request table.
- **Generation fencing.** Tool calls fail when `team.generation` differs ([L1137-L1142](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/architect.rs#L1137-L1142)), so late calls after pause, cancel or restart are rejected. Useful for Symphony cancel.
- **Plain-language queue reasons.** "Waiting for a dependency", "Waiting for an available worker slot", "Waiting for X to finish editing shared files" ([L999-L1013](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/architect.rs#L999-L1013)). Good wording for the node projection.
- **Host-bound identity in agent mailboxes**, with 1,000 messages of 2 KiB per team and 200 checkpoints per worker ([doc L109-L145](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/docs/architect-workers.md#L109-L145)). Checkpoints report progress and never mark completion.
- **Silence watchdog.** A turn with no output for 20 minutes is stopped, but a turn waiting on the user never counts as silent ([L101-L103](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/docs/architect-workers.md#L101-L103)).
- **Clean-merge refusal.** The local merge needs a clean worktree and clean tracked main, aborts on conflict and names the files ([workspace.rs L994-L1032](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/workspace.rs#L994-L1032)).
- **Evidence preview.** Jev says that if evidence changes between preview and run, it must be prepared again ([jev.md](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/docs/jev.md)). This is an invalidation rule Neokod should apply to review and approval evidence.
- **Failed queued sends are restored, not dropped** (issue #7, fixed in `ef54ba9` per the maintainer comment). Relevant to phone follow-ups.

### Weaknesses and what not to adopt

- **Shared dirty checkout.** Workers use the parent's checkout and Unlimited parallelism is the default for new setups. Scopes are "not an operating-system filesystem sandbox", and other apps and terminals can still edit ([doc L60-L78](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/docs/architect-workers.md#L60-L78)). This does not provide the package isolation and integration evidence Neokod would need for image 1.
- **Weak completion gate.** `pandacode_finish_team` checks that every worker is `completed` or abandoned. No validation command, revision or CI is consulted in that function ([L1358-L1376](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/architect.rs#L1358-L1376)). The local merge also runs no tests and does not compare a reviewed revision.
- **Positional chat approvals.** A reply of `yes` removes the oldest pending request for the session and applies to it, and if answering one fails it silently moves to the next ([gateway.rs L293-L312](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/bots/gateway.rs#L293-L312)). The prompt shows no request ID ([L284](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/bots/gateway.rs#L284)). A late `yes` can approve a different request from the one the user saw. `always` writes a wildcard rule from the first three words of the approval text ([guard.rs L94-L99](https://github.com/aicodeking/pandacode/blob/d9c1ac0284db3de24890b3af6e04933ca588fca6/src-tauri/src/bots/guard.rs#L94-L99)). This is a direct counter-example for Neokod's stale-approval rule.

**Semantics every phone mutation must meet.**

- The target host is shown on every screen and sent with every command. A lost connection never redirects to another host.
- Approve, deny, stop and follow-up carry a command ID and the revision the user saw. The server answers with the authoritative snapshot. An approval that is resolved, superseded or expired is refused with the current state shown. This is the check PandaCode's desktop path has and its chat path lacks.
- A lost reply shows "unknown, reconciling", then re-reads host state. A retry reuses the same command ID and gets the same receipt (MonoCode pattern). Nothing is resent with a new ID.
- Approvals are never queued offline. An unsent follow-up stays a visible local draft and is sent only by an explicit tap after reconnect.
- On resume from a locked screen the client reads the host snapshot and may not claim progress it did not receive. An unreachable host shows last-observed time and `unknown`, never "Working" (T3 #4852).
- App data stays on the host. The phone holds only a token and cached snapshots.

### The three images

Provenance of all three is unverified and they are used as visual inspiration only. Nothing is claimed about the systems they depict.

#### Image 1: architect, critic, packages, integrate, review facets, human merge

Interpretation: a staged flow with bounded loops (design critique, fix then re-review) and parallel packages that converge at an integration gate.

What exists: sequential execution on one worktree with up to `max_turns`; host-run validation with a retry loop up to `max_attempts` (`ExecutionFinalizer.ts:189-216`); evidence bundle; model review bound to `headSha` and compared with the PR's latest commit at merge (`SymphonyOrchestratorLive.ts:297-323`); fresh PR evidence and human `approveMerge` (L1806-L1930). What does not exist: a design stage and critic, parallel packages, per-facet findings, a separate integrate stage, and a head revision on validation results (search of `Validation/` and `Evidence/` found none; this is inference from absence).

Fit and sequence:

- **Fits existing sequential execution.** Design critique, review facets and fix-then-review. Each is a stateless generation call or one more turn, recorded as an artefact bound to a head SHA and a round number. A design critic that returns "9/10" is advisory; the gate is an `approve` verdict on a named digest. The loop stops at a fixed round count (proposed 3) and then goes to a human.
- **Needs a durable multi-agent runtime.** Only parallel Implementer/Tester packages. They need a worktree per package from one base SHA, serialised merge-back into an integration branch, tree-wide concurrency and budget limits before spawn, and transitive cancel. Separate Implementer and Tester workspaces must identify the exact candidate revision under test; an integration merge invalidates earlier results. Plan 20 point 6 already records that Symphony lacks these. Defer, and run packages as ordered sequential turns for now. Independent testing comes from host-run validation, not a second agent.
- **Stale tests.** Every validation and review result records the exact HEAD SHA and a clean-tree flag. After an integrate merge or any later commit, earlier results show as superseded and do not count. Parallel workers never share a dirty checkout (PandaCode's pattern, above).
- **Code mode.** Offer "run a review facet on this diff" reusing the existing review service, with the result shown against the thread's head. The full stage projection stays in Symphony.

#### Image 2: generate, self-verify, second review, checks, all clear

"All clear" is a server predicate and never model confidence. It is true only when, at one exact head: every required validation passed; the configured review requirement is satisfied (`all-approve`, `any-approve` or `advisory`); no unresolved blocking finding; CI is `success`; mergeable is confirmed; no approval is pending. It makes the item eligible for human merge approval and never merges. Unknown or unavailable evidence is not clear (state-and-evidence "fail-closed").

- **Resolvable** means a deterministic failure from a configured check, or a reviewer finding anchored to a file. It returns to the agent as a repair attempt starting from the current head. Proposed initial repair budget: 2 rounds within the existing `max_turns` and `max_attempts` ceilings. Track the repair round separately so it cannot reset or multiply those limits. This is a planning default, not a new owner approval prerequisite.
- **Novel** goes to a human with the evidence attached. Triggers: budget exhausted; the same failure signature twice; unknown evidence; a a permission request outside the enforced policy, or a protected-path rule once that rule is implemented; reviewers disagreeing under `all-approve`. Then back to the agent only on the human's instruction.
- **Invalidation.** Any new commit supersedes validation, review and any pending merge approval for the older head. A human approval stays bound to its request ID and head. I did not verify whether a push after `ready_to_merge` demotes the item; that needs a test.
- **Cancellation.** Scope is the work item's current attempt. It stops the run, the repair loop and queued repairs. Late results from a cancelled attempt are discarded (generation fence). Open human requests close as cancelled.
- **Exists:** retry on validation failure, one bounded review-comment round, merge gates. **Proposed:** failure classification, a separate repair budget, a "needs human, novel" state mapped onto existing `blocked` or `waiting_for_approval`.

#### Image 3: agent tree with per-node status, cost and aggregates

Three different graphs must stay separate. **Delegation lineage** is who started whom (parent, attempt, host). **Workflow dependency** is what must finish first. **Evidence gates** are what proves closure. The picture's tree draws the first and implies the other two.

Proposal: reuse the existing lifecycle and runtime-item projections in Code and Symphony. Derive tree relationships and presentation from those facts; introduce a shared pure helper only where both surfaces need the same rule, with the clock injected. Each node carries authoritative `nodeId`, `parentNodeId`, `attemptId`, `hostId`, `environmentId`, requested and effective provider/model, and these evidence-typed fields:

- lifecycle: the existing active, terminal, orphaned or unknown union; attention (needs-user from open approval/input items) and host availability (including offline with last observation) remain separate fields
- elapsed: frozen when terminal, ended at last observation when orphaned
- cost: `actual`, `estimated`, `unpriced` or `unmetered`, never a bare number
- cancel scope: node, subtree or run
- dependency: plain-language "waiting for…" reasons, borrowed from PandaCode

Agent counts cover each distinct agent node once, including orchestrators; workflow stages and review artefacts are not counted as agents. Show unknown and orphaned counts explicitly. Lifecycle, attention and host availability remain separate dimensions, so an offline host does not erase a node's last observed state. Parent settlement does not prove descendant termination: retain its own authoritative outcome and expose active or orphaned descendants separately. Parent cancellation does not mark children stopped without provider confirmation. Sum canonical attributed cost facts once across parent, child and retry work, excluding overlapping provider aggregates; show actual and estimated subtotals separately, plus unpriced or unmetered coverage.

**Deliberate delivery difference.** T3 delivers automatic completion notifications by steering the active provider turn where the provider supports it, and queues otherwise. The pinned gate is `supportsActiveSteering` without `activeSteeringInterruptsTools` ([Orchestrator.ts:5119-5122](https://github.com/pingdotgg/t3code/blob/1688f965682d331da16a8c39f049592361f69c8d/apps/server/src/orchestration-v2/Orchestrator.ts#L5119-L5122)), as reported by the T3 flow investigation. Sonnet confirmed the gate itself without tracing every notification path. Neokod's settled policy queues behind the active parent turn and never steers. That is a Neokod decision, not T3 behaviour, and it is consistent with T3 issue #15351 (a child notice cancelling queued Claude tools, a dated and unreproduced report).

**Permissions.** T3's own contract says that a runtime-mode rank does not guarantee equivalent provider permissions or a read-only child ([contract](https://github.com/pingdotgg/t3code/blob/1688f965682d331da16a8c39f049592361f69c8d/packages/contracts/src/orchestratorMcp.ts#L188)). Neokod's adapters confirm the point. Kiro rejects every mode except `approval-required` (`KiroAdapter.ts:453`). Cursor treats `approval-required` and `auto` identically (`CursorAdapter.ts:232`). Claude maps modes to its own permission settings. The child record therefore stores requested mode, effective mode and `providerEnforced: "unverified"`. It does not claim a capability lattice.

**Limits.** Depth cap 1. Bounded concurrency (planning defaults: 3 active per parent, 6 per environment). Inherited ceilings. Isolated worktree by default. Durable launch and result. Stop and restart end in "unknown" when evidence is missing.

**Request and result boundary.** The old `HandoffService.delegateFromThread` (`apps/server/src/symphony/HandoffService.ts:494`) validates a thread, then creates a manual Symphony work item with a generated ID. It carries no parent run, task identity or result path. It is not a managed-child protocol, and a `code_child` literal is not appended to it. W6's earlier reuse of the H-1 `symphony_delegation_requests` table is withdrawn for children, because that table is keyed on work item and attempt. The shared piece is a schema-only delegation contract and pure lifecycle logic (request, receipt, state union, evidence-typed result). Storage stays per target. Symphony may later project into the same types.
