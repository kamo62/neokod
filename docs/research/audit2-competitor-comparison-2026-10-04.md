## Area 1: file and project API safety

### CP-01 (P1) Workspace write follows symlinks and is non-atomic; no revision check

Neokod: workspace/WorkspaceFileSystem.ts writeFile (L262-295): resolveRelativePathWithinRoot is lexical only, then fileSystem.makeDirectory(recursive) and writeFileString on the unresolved path. readFile does realpath containment (same file, L135-175) but writeFile has none. A symlink inside the project pointing outside (or a symlinked dir) is followed for mkdir and write. Truncating writeFileString, so a crash or ENOSPC mid-write leaves a zero or partial file. No expected revision or mtime parameter, so an editor save silently overwrites an agent edit.
Best reference: Paseo packages/server/src/server/file-explorer/service.ts:

- resolveScopedPath L803-817: lexical check, then realpath(root) and realpath(target), both containment-checked.
- writeExplorerFile L433-530: 1 MiB cap (L98, L441), O_NOFOLLOW read handle (L100), dev:ino:size:mtimeNs revision (L103), conflict result checked before and again after temp write (L463-515), temp file `.name.paseo-<uuid>.tmp` opened `wx` with original mode, fsync, rename (L496-518), temp unlinked in finally.
  Paseo gaps to avoid: does not create new files (missing target returns conflict L476); revision recheck then rename is still a TOCTOU window; no parent dir fsync.
  T3 upstream is NOT a reference for write: t3code apps/server/src/workspace/WorkspaceFileSystem.ts L305-340 is the same as Neokod (mkdir + writeFileString, lexical). Orca (src/main/ipc/filesystem/filesystem-write-handlers.ts L31-42) does realpath against registered roots (good) but a plain writeFile (non-atomic) and an lstat only to refuse directories.
  Copy: reuse atomicWrite.ts (already in Neokod) but add Paseo-style realpath containment of the nearest existing ancestor before mkdir, then `wx` temp in the same dir and rename, plus optional expectedRevision input in contracts. T3's atomicWrite.ts (resolveSymlinkTarget, packages/shared/src/symlink.ts) keeps a link alive on rename; Neokod's atomicWrite.ts L19-23 does not (it would replace a symlink by a regular file, and makeTempDirectoryScoped leaves a temp dir next to the target, visible in git status if the process dies).

## Area 3: git and source control (see CP-12 to CP-17 below)

### CP-12 (P1) Option injection in switchRef: refName "-f" becomes `git checkout -f` and discards local changes

Neokod apps/server/src/vcs/GitVcsDriverCore.ts L2618-2690 switchRef: probes `show-ref --verify refs/heads/<ref>` and `refs/remotes/<ref>`, and when both fail the final branch of the ternary is `["checkout", input.refName]` (L2684) with no `--` and no leading-dash check. VcsSwitchRefInput.refName is only a TrimmedNonEmptyString (packages/contracts/src/git.ts L178-181, same for VcsCreateRefInput L166-170). A refName of `-f` produces `git checkout -f`. Verified the git semantics in a throwaway repo (rt-f/scratch/r): after `echo dirty >> f`, `show-ref --verify --quiet refs/heads/-f` exits 1 and `git checkout -f` resets the file to HEAD, losing the edit (evidence RUN at git level, not through the Neokod RPC). Same family: createRef L2700 `["branch", input.refName]` and createWorktree L2335-2338 pass refName/newRefName/path positionally.
Hardening that exists in Neokod: `git branch -m -- old new` (L969, L2608), `--literal-pathspecs ... add -A --` (L1613). So the pattern is known, just not applied to refs.
Best reference: none of the competitors has a validator I could find that rejects leading dashes at the contract level; Paseo uses `--` for mv (file-explorer/service.ts L730 `["mv", "--", ...]`). Orca validates push targets (src/main/git/push-target-validation.ts).
Copy: (1) in contracts add a `GitRefName` schema check: no leading `-`, no `..`, no control chars, no `@{`, not ending `.lock` (git check-ref-format subset); (2) in the driver, `checkout --end-of-options <ref>` is not available for all subcommands, so use `git switch --end-of-options` on git >= 2.24 or `git checkout <ref> --`. Also validate `path` for createWorktree against `-` prefix. (3) Treat the cwd of every git RPC as in CP-07.

### CP-13 (P2) Status polling takes the index lock: no GIT_OPTIONAL_LOCKS=0 anywhere

Neokod vcs/GitVcsDriverCore.ts L1385-1420 readStatusDetailsLocal runs `git status --porcelain=2 --branch` with env { LC_ALL: "C" } only (L895-905); grep for OPTIONAL_LOCKS across apps/server/src finds nothing. ### CP-15 (P2) Checkpoint restore can fail halfway on empty checkpoints and has no safety net
